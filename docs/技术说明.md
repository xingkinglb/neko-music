## 为什么不用普通网页而要用 Electron

浏览器里打开一个网页，**没法**自由地访问别的网站（叫"跨域限制"），也存不了本地文件。
Electron 相当于把"浏览器"和"Node.js"焊在一起，让我们的界面既有漂亮的样子，又有程序的权限。

## 文件都是干什么的

```
Music/
├── package.json          ← 项目说明书（叫什么名、要装哪些库）
├── 启动播放器.vbs         ← 双击启动（没有黑窗口）
├── 调试启动.bat           ← 出问题时双击它看日志
└── src/
    ├── main.js           ← 主进程（幕后老板，还负责开第二个歌词窗口）
    ├── preload.js        ← 传话筒（安全的沟通桥梁）
    ├── preload-lyric.js  ← 悬浮歌词窗专用的传话筒（权限更小）
    ├── bilibili.js       ← 和 B 站对话的翻译官
    ├── bg-protocol.js    ← 背景壁纸专用的 bg:// 协议（含视频分段传输）
    ├── win-mini.js       ← mini 模式的窗口尺寸（收起 420×132 / 展开 420×520）
    ├── app-menus.js      ← 托盘菜单 / 任务栏任务 / 关窗决策 / 命令行参数（纯数据，好测）
    ├── store-migrate.js  ← 存档补洞（老存档缺字段补默认值，不认识的字段原样留着）
    ├── assets/
    │   ├── app.png       ← 窗口图标（猫耳 + 音符，由 .verify/make-icon.js 手搓生成）
    │   ├── tray.ico      ← 托盘图标（16 + 32 双尺寸，由 .verify/make-icons.js 生成）
    │   ├── menu-*.png    ← 托盘菜单里的小图标（12 个）
    │   └── thumb-*.png   ← 任务栏缩略图按钮（上一首 / 播放 / 暂停 / 下一首）
    └── ui/
        ├── index.html    ← 骨架（页面上有哪些元素）
        ├── style.css     ← 化妆（长什么样）
        ├── app.js        ← 大脑（点了什么，做什么）
        ├── lyric.html    ← 桌面歌词窗的骨架（第二个窗口）
        ├── lyric.css     ← 桌面歌词的样式
        └── lyric.js      ← 桌面歌词的逻辑（算当前句、拖动、工具条）
```

**为什么分 main 和 ui 两个进程？**

- `ui/` 里的代码跑在"网页世界"，很安全但没权限
- `main.js` 跑在"系统世界"，有权限但没法画界面
- 两个世界通过 `preload.js` 喊话：界面说"帮我搜一下钢琴"，主进程搜完把结果递回来

> ⚠️ **信封约定**：主进程的 `ipcMain.handle()` 一律返回 `{ok, data}`。
> 界面侧必须用 `api('xxx')` 去拆信封；直接拿 `window.neko.xxx()` 得到的是**整个信封**，
> 不是数据本身 —— 这里踩过一次坑（存档读出来"看起来有值"其实永远不对）。

## 三个最关键的技术点

### 1. wbi 签名（`bilibili.js`）

B 站为了防止别人乱调接口，要求每个搜索请求带一个**签名**。算法是：
把参数按字母排序 → 拼成字符串 → 用一张固定的乱序表从"钥匙"里抽字符 → MD5。

这套算法藏在 `getWbiKeys()` 和 `signParams()` 里。你不需要理解它，只要知道**它是搜索能成功的前提**。

> ⚠️ 有个坑我在开发时踩过：取"钥匙"的那个接口（`nav`）在未登录时会返回 `code: -101`，
> 但数据里照样有钥匙。所以那一步不能走"必须 code=0"的通用函数，得手动解析。

### 2. bili:// 协议（`main.js`）—— 最巧妙的一步

B 站的音频地址有**防盗链**：必须带着 `Referer: https://www.bilibili.com` 才让下载。
可网页里的 `<audio>` 标签**没法自定义请求头**，这不是死路了吗？

解法是自己造一个协议：

```
网页写：  <audio src="bili://get?url=真实音频地址">
Electron 收到 → 由主进程代发请求，帮它加上 Referer → 把音频数据流回去
```

界面完全感觉不到中间这层，就像播放本地文件一样自然。
代码在 `registerBiliProtocol()` 里，一共 20 行。

### 3. 只要音频，不要视频

B 站把视频和声音**分开存放**（叫 DASH 格式）。
调 `playurl` 接口时传 `fnval=16`，就会返回一个 `dash.audio` 数组 —— 里面是**纯音频**的地址。

这样一首歌只要几 MB，还能秒开。如果下载整个视频，光是流量就浪费十倍。

### 4. 内容安全策略（CSP）与"封面破图"

页面 `<head>` 里有一行 `Content-Security-Policy`，它规定了网页**只允许从哪里加载资源**。
我们写的是 `img-src 'self' https: data:` —— 图片只准用 https。

而 B 站的搜索接口很"随意"，封面地址经常返回 `http://i1.hdslb.com/...`（少个 s）。
结果就是：所有封面被浏览器拦下，变成破图，控制台里刷满
`Refused to load the image ... violates the following Content Security Policy directive`。

**修法**是在 `bilibili.js` 里加一个 `toHttps()`，把所有图片地址统一成 https 再交给界面。
这个小函数解决了三种写法：`http://xxx`、`https://xxx`、`//xxx`（省略协议的）。

> 📌 顺便说一句：我们**没有**去放宽 CSP 让它接受 http，因为那样只是把问题藏起来；
> 正确的做法是把数据整理干净。当然，双保险也加了（CSP 里额外放行了 B 站的图片域名）。

### 5. bg:// 协议与动态背景（`src/bg-protocol.js`）

背景壁纸也走自己造的协议。页面安全策略里**没有**放行 `file://`，
与其把 CSP 开个大口子，不如造一个只能读取 `backgrounds/` 这一个目录的 `bg://` 协议：

- 选图 / 选视频时弹系统文件框，把文件**复制**进 `%APPDATA%\neko-music\backgrounds\`，换掉原文件也不会裂
- 协议有两道安全闸：文件名白名单（挡 `..`、反斜杠这类路径穿越写法）+ 路径越界检查（挡符号链接逃逸）
- **边读边传（支持视频）**：请求头带 `Range` 时用 `fs.createReadStream(file, {start, end})` 只发那一段，
  返回 `206 Partial Content` + `Content-Range` + `Accept-Ranges: bytes`；不带 `Range` 就发完整流。
  这样一段上百 MB 的视频**不用一次性读进内存**，内存占用跟文件大小脱钩。

（这一块单独拆成了 `src/bg-protocol.js`，好让自检脚本能直接把它注册起来、真发一个带 `Range` 的请求来验证。）

外观（主题色、背景、毛玻璃）全部由 CSS 变量驱动：切换主题**只改点缀色、绝不碰底色**，
所以你的自定义背景和主题色永远不会打架。

### 6. 动态背景的性能：为什么显卡会飙到 60%

这是 v1.9.0 修掉的一个真实问题，成因有四个，按权重排：

**根因 A（主因）：4 块常驻"毛玻璃"面板压在会动的画面上**

| 面板 | 位置 |
|---|---|
| `.titlebar` | 整宽（顶部标题栏） |
| `.sidebar` | 整高（左侧边栏） |
| `.topbar` | 整宽（搜索栏那一条） |
| `.player` | 整宽（底部播放条） |

`backdrop-filter: blur(18px)` 的含义是"**把我背后那块画面实时糊一遍**"。
背后是**静态图片**时，糊一次就缓存住了，几乎不花钱；
背后是**视频**时，**每一帧都要重新采样 + 重新模糊**这 4 块大面积区域。
60fps 下 ≈ 每秒 **240 次大区域高斯模糊** —— 显卡就是这么被吃掉的。

**根因 B**：模糊（`filter: blur()`）原先挂在 `.bg-layer` 上，而 `<video>` 是它的**子元素**，
等于"先解码一帧 → 整层（含视频）糊一遍 → 再合成"。

**根因 C**：`<video>` 是**替换元素**，对绝对定位的替换元素来说，`width/height` 为 `auto` 时
浏览器取的是它的**内在尺寸**（= 视频真实分辨率），`inset: 0` 里的 `right`/`bottom` 会被**直接忽略**。
所以"撑满父容器"那套写法**只对普通元素有效，对 `<video>` 无效** —— 视频盒子恒等于素材分辨率
（1920×1080 的素材就是 1920×1080，锚在左上角），窗口一小就只露左上角一块，全屏时才"看起来正常"。
**修法就是显式写上 `width: 100%; height: 100%`。**

**根因 D**：只有"最小化"会暂停。窗口失焦、被别的窗口盖住、打开设置面板时都不停。

**v1.9.0 的对策**：

| 对策 | 做法 |
|---|---|
| 修缩放 | `#bgVideo` 显式 `width/height: 100%` + `object-fit: cover` |
| 模糊隔离 | 拆出只管图片的 `.bg-image`，模糊挂在它身上；`.bg-layer` 不再挂 `filter` |
| 降毛玻璃 | 背景是视频时给 `<body>` 打 `perf-lite`，把 4 块面板的 `backdrop-filter` 设为 **`none`**（不是 `blur(0px)` —— 那个仍会把背后画面拷进纹理，省不下来），同时抬高面板底色 `--glass-boost: 0.12` 保持磨砂观感（该值 v2.0.1 起降为 0.04；**v2.0.2 起该机制连同 `--glass-boost` 一并移除**，改由「面板不透明度」`--frame-a` 统一控制） |
| 该停就停 | 窗口失焦 / 打开任意遮罩 / 最小化 → 暂停；统一由 `updateBgVideoPlayback()` 判定 |

> **为什么不把视频转成 GIF**：GIF 只有 256 色（星空 + 人物渐变会出色带）、**没有硬件解码**、
> 靠 CPU 逐帧解（GPU 60% 会变成 CPU 飙升）、同画质体积是 mp4 的 5~20 倍。
> 开源动态壁纸 Lively Wallpaper 这类工具**全都用视频而不是 GIF**，就是这个原因。
>
> **v2.0.0 的后续**：v1.9.0 用的"背景是视频就整体降级"那条路（`body.perf-lite`）已经被
> 下面第 7 节的"面板毛玻璃三档"取代 —— 现在不再由"背景是不是视频"决定，而是由**用户选哪一档**决定。

### 7. 面板毛玻璃三档 与 一个静默失效很久的颜色写法（v2.0.0）

**先说结论**：`backdrop-filter` 的成本不在"糊得多糊"，而在"**要糊多少次**"。
只要**合成器还在出帧**，`blur(18px)` 和 `blur(12px)` 的差距远小于"糊一次"和"每秒糊 240 次"的差距。
所以真正的省法只有两条：**① 让它不用实时糊（预先糊好）；② 让它别出帧（把无限动画停掉）**。

#### 三档怎么来的

存档里新增 `settings.glass.mode`，取值 `'plain'` | `'prebake'`（默认）| `'live'`，
对应设置界面里两个**互斥的平级开关**（只勾"省显卡"= `prebake`；只勾"实时毛玻璃"= `live`；两个都不勾 = `plain`）。

| 档 | 面板背景 | `backdrop-filter` | 成本 |
|---|---|---|---|
| `live` | 半透明底色 | `blur(var(--glass-blur))` 真模糊 | 每帧重算 |
| `prebake` | `--glass-img`（JS 预先 canvas 糊好的壁纸 data:URL）+ 半透明底色 + 全局 `--bg-dim` 压暗罩 | `none` | ≈0 |
| `plain` | 半透明底色 | `none` | ≈0 |

`prebake` 的三层背景写法（每层都用 `linear-gradient` 只为"能当一层用"）：

```css
background:
  /* ① 上层玻璃底色（v2.0.2：与四块框架共用 --frame-a，四块与内容区的差值就由它决定） */
  linear-gradient(rgb(var(--glass-rgb) / var(--frame-a)), rgb(var(--glass-rgb) / var(--frame-a))) center/cover no-repeat fixed,
  /* ② 中层压暗罩：与底图共用根级全局 --bg-dim，滑杆一拉四块面板和内容区一起变暗 */
  linear-gradient(rgb(0 0 0 / var(--bg-dim)), rgb(0 0 0 / var(--bg-dim))) center/cover no-repeat fixed,
  /* ③ 底层：预先糊好的壁纸 */
  var(--glass-img) center/cover no-repeat fixed;
```

> **v2.0.1 的两处修正**：① 面板底色"抬高量" `--glass-boost` 从 **0.12 降到 0.04**（之前面板太实，壁纸只在内容区透得出来）；
> ② `--bg-dim` 从"只挂在壁纸层"**提升为根级全局变量**（`applyAppearance()` 里 `root.style.setProperty('--bg-dim', …)`），
> 让"背景压暗"滑杆同时作用到底图与这四块面板 —— 否则会出现"只有内容区变暗、面板不动"。
> 因为只是叠罩、不重烘焙 `--glass-img`，拉滑杆是即时的。

> **v2.0.2 的重做**：上面 ① 里写死的 `0.26` 换成 `var(--frame-a)`，四块框架的压暗量**收敛成一个变量**。
> 详见下面第 8 节。

`background-attachment: fixed` 是关键：它让 4 块面板各自显示壁纸的**对应那一块**，位置才和真实壁纸对得上。

`--glass-img` 由 `app.js` 的 `buildGlassImage()` 生成：把壁纸画进 canvas，`ctx.filter = 'blur(Npx)'`，再 `toDataURL('image/jpeg', 0.86)`。
两个坑：**①** 图片必须以 `crossOrigin='anonymous'` 加载，否则 canvas 被污染、`toDataURL()` 抛 `SecurityError`（`bg://` 协议已经发了 `Access-Control-Allow-Origin: *`）；
**②** 写进 CSS 变量时必须包 `url("…")` —— 裸的 `data:image/jpeg;base64,…` 里有 `;`，会把 CSS 声明**提前截断**，属性被静默丢掉。

背景是**视频**时无法预糊 → 自动降级为 `plain`（不打 `has-imgbg`，那条规则自然落空）。

#### 那个静默失效很久的颜色写法

这是 v2.0.0 施工中挖出来的，**从 v1.9 甚至更早就存在**：

```css
rgba(var(--glass-rgb), 0.55)   /* --glass-rgb: 16 16 26 */
/* 展开后 → rgba(16 16 26, 0.55)  ← 非法 */
```

`rgb()` 的合法写法只有「全逗号」`rgba(16, 16, 26, 0.55)` 或「全空格 + 斜杠」`rgb(16 16 26 / 0.55)`。
**混着写不会报错，而是静默失效**；更麻烦的是因为用了 `var()`，报错被推到 computed-value 期，
属性会**直接取初始值**（`background-color` → `transparent`），**而不是回退到上一条声明** —— 表现就是"写了等于没写"。

项目里有 5 组"空格分隔三元组"变量，其中 4 组的半透明用法**全是坏的**：
`--glass-rgb`（面板底色）、`--accent-rgb`（主题色，33 处）、`--accent-2-rgb`（5 处）、`--sw` / `--sw2`（设置色块）。
修法：一律改成斜杠写法 `rgb(var(--x) / α)`；`verify.js` 第 46 类断言长期守住。

> **例外**：`lyric.css`（桌面歌词悬浮窗）里的 `rgba(var(--accent-rgb), 1)` 是**对的** ——
> 那份 `--accent-rgb` 是悬浮窗自己定义的、**逗号分隔**（`255, 111, 165`）。
> 这也是 `app.js` 里 `currentAccentRgb()` 要专门把空格形式转成逗号形式再推过去的原因。

#### 看不见的动画一律停掉

无限 CSS 动画会让合成器**永远在出帧**。性能暂停规则覆盖 `.idx .bars i`（列表里的跳动柱子）和 `.spinner`（加载占位转圈）；播放条封面不再添加 `.np-cover.spin::before` 旋转弧线，播放状态由播放 / 暂停按钮表示。播放条缓冲图标与歌词加载图标仍按各自状态显示，不属于这组暂停规则。
用三个 `<body>` 类统一控制这组动画暂停，由 `syncPauseClasses()` 一处维护：

| 类 | 何时打上 | 暂停哪些 |
|---|---|---|
| `has-overlay` | 任意弹窗/遮罩打开（把界面整个盖住） | 内容区柱子与加载转圈 |
| `lyric-open` | 整页歌词打开 | 内容区柱子与加载转圈；**并把内容区里的东西藏起来**（`#content > *`，v2.0.2） |
| `perf-idle` | 窗口失焦 / 最小化 | 内容区柱子与加载转圈 |

另外，「正在播放」那三根柱子从 **SVG 改成普通 `<i>` 元素**：Chromium 里 SVG 的 `transform` 动画**不走合成器**，
每帧都要重新光栅化；普通元素 + `transform` 才走合成。

### 8. 四块框架压暗统一为 `--frame-a` 与 歌词页藏内容（v2.0.2）

**要修的两件事**（Neo 真机反馈）：① 选视频背景时背景没铺满整个界面、四块框架深浅不一；② 打开歌词页背后还挂着上一个界面。

#### ① 四块框架的压暗量收敛成一个变量

**根因**：`prebake` 依赖"预先糊好的壁纸图"，而**视频没法预先糊**，于是视频背景下 `body` 拿不到 `has-imgbg`（`app.js` 里 `has-imgbg` 要求 `s.bg.kind !== 'video'`），四块面板就退回**一套给每块各写偏移量的备用规则**（`-0.05` / `+0.16` / `-0.12` / `+0.10`）——实测压暗 **47% / 54% / 69% / 75%**，彼此差最多 **28 个百分点**，而内容区是 **0%**。图片背景下四块虽一致，但又比内容区多压一层写死的 `rgba(16,16,26,0.26)`。

**改法**：删掉 `--glass-alpha`（旧「玻璃透明度」用的）与 `--glass-boost`，新增**一个**变量：

```css
:root { --frame-a: 0.12; }   /* 四块框架比内容区"多压"的不透明度 */
.titlebar, .sidebar, .topbar, .player { --panel-a: var(--frame-a); }
```

`prebake` 三层背景的上层也改读 `var(--frame-a)`。`app.js` 里 `applyAppearance()` 用 `--frame-a` 写根节点，存档字段 `settings.glass.frameAlpha`（缺省 `0.12`）。设置项从「玻璃透明度」改名重做成「**面板不透明度**」（0~40%）。

**为什么让老存档也走新默认**：旧值（0.55）对应的观感正是要修的"四块深浅不一"，沿用旧值就白改了 —— 所以 `migrateSettings()` 直接 `delete DB.settings.glass.alpha`。

**实测判据**（纯色壁纸逐像素采样）：`--frame-a=0` 时四块框架与内容区亮度**完全一致**（都 120）；`--frame-a=0.4` 时四块被压暗的幅度**都等于 40.7 个色阶**（理论 40.3），彼此**最大差 0.0**，内容区 **0.0**。

#### ② 歌词页背后藏掉内容区

**根因**：`.lyric-overlay` 只有 `rgba(8,8,14,0.34)`（这层 34% 黑纱是 v2.0.0 定的、**故意**透壁纸的，本轮不动），盖得住亮度、**盖不住列表形状**。

**改法**（纯 CSS，**不用改 JS** —— `syncPauseClasses()` 早就在维护 `lyric-open`）：

```css
body.lyric-open #content > * { visibility: hidden; }
```

**两个关键点**：

1. **藏"内容区里的东西"（`#content > *`），不藏"内容区这个框"（`#content`）**：藏框会连带丢掉滚动位置（退出歌词回来列表跳回顶部）；藏里面的东西布局不变、滚动位置不动。
2. 更要命的是**离屏实测踩的坑**：`#content` 是 `overflow-y:auto` 的**滚动容器**（自带合成层），"藏容器"走的是"合成器把整个滚动图层隐藏"这条优化，**在离屏软件光栅下它不重绘** —— DOM 里计算样式明明已是 `hidden`，画面上列表照旧挂着，**连拍多少张截图都是同一张旧图层**（实测跨多次运行、跨 CSS 三版，png md5 完全不变）。藏**子元素**才是让内容真正重绘成空，这条才靠谱；顺带也盖住了"歌词页开着时列表重新渲染"（子元素 `hidden`，其下新生成的行一律继承）。

**实测判据**（另开新窗口造 8 行列表 + 纯色壁纸）：歌词页开着时，内容区"有文字笔画"的格子 **0 个**；把内容区强行显示出来则是 **197 个** —— 说明列表真的被藏住了。像素差分：藏起来 81.7 ≈ 理论 82.6（壁纸过一层 34% 黑纱），强行显示后内容区 **4.1%** 的像素发生变化。

### 9. 「正在播放」高亮的判据（v2.0.3）

列表里"这一行算不算正在播放"，是 `app.js` 里一个叫 `rowIsPlaying(track)` 的小函数说了算。它只有两句话：

1. **它就是当前这一首**（`sameTrack(track, cur)`，比 `bvid` + `cid`）。
2. **它是"合集 / 分P 的入口行"** —— 一行代表整支视频，正在播它里面任意一集时保持高亮。

第 2 条是**必须**的：分P 视频摊开后，队列里躺的是"一集一集"，和列表里那**一整行**不是同一个对象 ——
只比第 1 条的话，你在发现页点开一条合集，界面上会**一行都不亮**。

**v2.0.3 修掉的 bug**：第 2 条以前写的是"**只要 `bvid` 一样就算在播**"，
而 **B 站的分P 视频，每一集共用同一个 `bvid`**（靠 `cid` 区分第几集）。
于是"最近播放"里，这一支视频里**播过的每一集全都显示成"正在播放"**（实测 6 集全亮）。

**改法 —— 给第 2 条加一道闸门**：

```js
if (sameTrack(track, cur)) return true;
if (!track.bvid || !cur.bvid) return false;

// ★ 闸门：这一行自己就是某合集里的一集 → 它是一首独立的歌，只有它自己正在播才算在播
if (isCollectPart(track)) return false;

if (track.bvid === cur.bvid) return true;                       // 分P：入口行 ↔ 它里面的某一集
const parts = DB.collectParts[track.bvid];
return !!(parts && parts.some((e) => sameTrack(e, cur)));       // UP 合集：每一集自带 bvid，查表认
```

**为什么闸门能成立**：`isCollectPart(track)` 要求这一行**有 `cid`、且能在摊开的曲目表里找到自己**；
而"入口行"（搜索结果 / 收藏夹 / UP 列表里那种）**根本没有 `cid`** —— 要播的时候才去补（`ensureCid`，`app.js:575`），
所以入口行**永远不会**被这道闸门挡住，第 2 条的原有行为完整保留。

顺手还**删掉了一条反向误判**：`DB.collectParts[cur.bvid]` 那段"拿正在播那首的曲目表去反查别的行"，
会让**同一个 UP 合集**里的其它集也一起点亮（UP 合集的每一集自带 `bvid`，走的是另一条路，同样被这条误伤）。

**实测判据**（离屏跑真界面，灌数据后数 DOM 里几行带 `.playing`）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 分P：听过 6 集，正在播第 5 集 | **6 行全亮** | **1 行** |
| UP 合集：3 集都在历史里，正在播第 1 集 | **3 行全亮** | **1 行** |
| 合集 / 分P 的**入口行**（回归） | 1 行 | 1 行 |
| 普通单曲列表（回归） | 1 行 | 1 行 |

> ⚠️ **静态断言有个坑**：`if (isCollectPart(track)) return false;` 这行在 `maybeCollection()` 里**也有一份**，
> 全文搜会假通过。所以 `verify.js` 里是**先把 `rowIsPlaying` 的函数体抠出来再查**。

### 10. 播放请求的健壮性：为什么会有「interrupted by a new load request」（v2.0.4 / v2.0.5）

**先给结论**：`The play() request was interrupted by a new load request.`
**不是"取歌失败"**，而是**两次播放请求叠在一起**时，后一次把前一次打断留下的报错。
它来自浏览器（Chromium），错误对象的 `name` 是 `AbortError`。

**它怎么产生的** —— `playAt(index)`（`app.js`）里有两段 `await`：

```js
await ensureCid(track);                        // ① 补"第几集"（可能要发网络请求）
const info = await api('audioUrl', …);         // ② 向 B 站要播放地址（也要发网络请求）
audio.src = info.url;                          // ③ 换掉音源
await audio.play();                            // ④ 播放
```

在 ① ② 这两段"等一等"的空隙里，**用户完全可能已经点了另一首**。于是**两个 `playAt` 叠在一起跑**：
后一个跑到 ③ 把 `audio.src` 换掉，前一个还挂在 ④ 上的 `audio.play()` 就被**强行打断**，
抛出的正是这句 `AbortError`。旧代码把它**当成真失败** → 弹「播放失败」+ 900ms 后自动跳下一首。

**改法：给每次切歌发一个序号**（`playSeq`）——

```js
const seq = ++playSeq;                 // 领号：本次播放的唯一身份
…
await ensureCid(track);
if (seq !== playSeq) return;           // ① 回来晚了 → 用户已经切歌，放弃（别动音源）
const info = await api('audioUrl', …);
if (seq !== playSeq) return;           // ② 同上
audio.src = info.url;
try { await audio.play(); }
catch (e) { if (isPlayInterrupted(e)) return; throw e; }   // ③ 被打断 ≠ 失败，静默
if (seq !== playSeq) return;           // ④ 播放期间被切走 → 不记历史、不刷界面
```

外加两处：

- `isPlayInterrupted(err)`：`err.name === 'AbortError'` 或消息里含 `interrupted by a new load request`
  / `interrupted by a call to pause` → 判为"被打断"。**只有"真失败"**（要不到地址等）才照旧提示 + 自动跳下一首，
  且那次自动跳歌**也加序号闸门**（`if (seq === playSeq) next(1);`），避免过期请求再触发一次跳歌。
- `safePlay()`：播放条上那几个按钮直接调 `audio.play()`（不 `await`）的地方统一包一层。
  原因：`play()` 返回的是 promise，被打断时会**以 `AbortError` 拒绝** —— 没人接就变成一条
  "未处理的 promise 拒绝"，控制台一片红。这里只把"被打断"吞掉（正常操作），其它错误照旧打日志。

**实测判据**（离屏跑真界面，桩里让 `audio.play()` 800ms 才 resolve、音源被换掉时以 `AbortError` 拒绝）：

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 连点两首歌（第二个打断第一个） | 弹「播放失败：…interrupted…」+ 可能跳歌 | **0 条提示、0 次多跳** |
| 播放条按钮在"上一次还没走完"时被点 | 1 条"未处理的 promise 拒绝" | **0 条** |
| 真失败（要不到地址） | 提示 + 自动跳下一首 | 提示 + 自动跳下一首（回归不变） |

> 💡 **记住这条判据**：只要看到 `AbortError` / `interrupted by a new load request`，
> 就说明**"用户换歌了"**，不是"这首歌有问题"。这类错**一律静默**，不提示、不跳歌。

**v2.0.5 的加固（三个点）**：

1. **判定不能用"整串相等"**：Chromium 会在这类消息**末尾再附一行媒体地址**，实际长这样 ——
   ```
   The play() request was interrupted by a new load request.
   https://goo.gl/LdLk22
   ```
   所以 `isPlayInterrupted()` 改成**包含**判断，并放宽到所有 `interrupted by …`
   （同时覆盖 "a new load request" 与 "a call to pause"）。
2. **再加一道不依赖消息文字的闸门**：模块级 `lastSetSrc` 记住"最后一次写进 `audio.src` 的地址"。
   如果本次设的 `mySrc` 已经**不是**它了，就说明中间有人换过歌 → 本次失败一律静默。
   （为什么不直接读 `audio.src` 来比：浏览器会对 URL 做规范化，比字符串容易误判。）
   ⚠️ 注意判据是 `(mySrc && lastSetSrc !== mySrc)` —— 先确认"我们确实设过地址"，
   否则"取地址就失败"（`mySrc` 为空）会被误判成过期，把真失败也吞掉。
3. **真失败时提示条只显示原因本身**（`cleanPlayError()` 剪掉末尾那串地址），
   完整信息（歌名 + 原始错误 + 地址）用 `console.error('[播放失败]', …)` 打到控制台，方便排查。

### 11. 播放条封面：为什么"重启后封面就没了"（v2.0.5）

**现象**：从**合集 / 选集**里播的歌，重启软件之后再播，播放条和列表里的封面**全空**（只剩一块占位底色）。

**真凶是一条"为了省存档"的链路**：

```
展开一个合集（如 134 集）
  ↓ 第一次联网查到曲目表（每条都带封面）
  ↓ 同时把这份表"剥掉封面"存进 DB.collectParts   ← 封面是长链接，上百集全存会把存档撑大
关掉软件，再打开 → 再播这个合集
  ↓ collectEntriesFor() 直接 return 缓存（不再联网）
  ↓ 缓存里的条目没有 cover → track.cover 为空 → 播放条 backgroundImage = none
```

**改法：每个合集只存一张封面**（不是每集都存，尊重"别把存档撑大"的初衷）

- `DB.collectCovers = { 合集bvid: 封面URL }`，写曲目表缓存时顺手记一条；
- 读缓存时用 `cachedCollectEntries()` 把这张封面**套给每一条**（带 memo，保持对象身份稳定）；
- 老存档没有这个字段 → `boot()` 里补成 `{}`，**零迁移**；
- 取舍：UP 合集里每一集原本可能各有封面，现在会**统一成合集封面**（同一个合集用一张反而更整齐）。

**顺手加的兜底**：真没封面时，`app.js` 给 `.np-cover` 挂 `.no-art` 类**并清空行内 `background-image`**
（清空很关键 —— 行内样式会盖掉 CSS），由 `.np-cover.no-art` 显示一个**内联 SVG 音符**（`img-src` 已放行 `data:`）。

**另一处小修**：`.np-cover.open::after { content:"收起"; opacity:1 }` 里那个 `opacity: 1` 是**故意**做的"常驻提示"，
但歌词页一开就一直挡住封面 —— v2.0.5 去掉它，出现时机交给已有的 `.np-cover:hover::after`。

### 12. mini 模式：同一个窗口换布局（v2.1.0）

#### 核心决定：**不新开窗口**

第一反应可能是"再开一个 420×132 的小窗口"。那样做的问题：第二个窗口要**重新加载一遍界面、重新读一遍存档、播放状态要跨窗口同步** —— 播放条、歌词、队列全得再搭一套通信。得不偿失。

所以走的是**同一个窗口 + 一个模式标记**：

| 谁 | 管什么 |
|---|---|
| **界面**（`style.css` + `app.js`） | 给 `<body>` 加 / 去 `mini` 类（CSS 换布局）、渲染展开态的队列列表、把状态写进存档 |
| **主进程**（`win-mini.js` + `main.js`） | 把**窗口本身**缩成 420×132（展开 420×520）、记住并还原完整模式的位置尺寸 |

两边各管一半，谁也不越界。所以"进去"是**布局和窗口同时变**的，不会先闪一下再缩。

> 参考项目 `wood3n/biu` 用的是同一招（它把标记挂在 URL hash 上并另开窗口）。区别只是我们**共用本窗口**，少一整套跨窗口同步。

#### CSS 那一半：三处关键写法

**① `display: contents` 让"分组盒"消失。**
播放条的 HTML 结构是 `.np`（封面 + 歌名 + ♡）/ `.controls` / `.volume`（词 / 打开 / 队列 / 音量）三块。
但 mini 要的是"封面左、控制中、杂项右、歌名**单独一行**" —— 歌名得从 `.np` 里**拆出来**。
改 HTML 结构风险大，于是用：

```css
body.mini .np,
body.mini .volume { display: contents; }
```

盒子本身消失，里面的子元素**直接变成 `.player` 的 flex 项**，再用 `order` 排个序、`flex: 0 0 100%` 把歌名顶到第二行。
**不用动一行 HTML**。

**② 铁律：`body.mini` 下绝不给 `.app`（或 `body`）加 `transform` / `filter` / `opacity` / `will-change`。**
原因见上面第 7 节 —— 它们会生成 "backdrop root"，把子元素的 `backdrop-filter`（毛玻璃）**打成一块纯色**。
`verify.js` 第 48 区块有一条专门的正则守着这件事。

**③ 第一行的宽度是算出来的，不是拍脑袋。**
窗口 420 − 左内边距 14 = **406** 的可用宽度。第一行要放：
封面 48 + 控制键 128 + ♡ 30 + 🔊 28 + ☰ 28 + ✕▢ 68 = **330**，加 5 个 9px 间隔（45）和 ✕▢ 左边那 8px = **383**，余 23。
**余量必须留够** —— `flex-wrap` 是"**先按假设尺寸断行、再收缩**"的，第一行一旦超宽，`✕▢` 会被整个挤到第二行去。
（离线实测第 3 组就是这么抓到的：第一版总宽 412 > 406，`✕▢` 掉到第二行、贴不到右边缘。）

#### 主进程那一半：`setResizable` 的坑

`win-mini.js` 里两个函数，**调用顺序都是踩出来的**：

```js
// 进 mini
win.setMinimumSize(MINI_W, MINI_H_COLLAPSED);
win.setMaximumSize(MINI_W, MINI_H_EXPANDED);
win.setBounds({ x, y, width: MINI_W, height: h });
win.setResizable(false);

// 出 mini —— 顺序和上面**不一样**，而且不能换
win.setResizable(true);                      // ① 必须先解钉
win.setMaximumSize(wa.width, wa.height);     // ② 再放大上限
win.setMinimumSize(FULL_MIN_W, FULL_MIN_H);  // ③ 最后才调最小值
win.setBounds(fullBounds);
```

**为什么"出"的①必须在最前**：Windows 上 `setResizable(false)` 会把 min/max **一起钉死成"当前尺寸"**
（这就是"不可缩放"的实现方式）。不解开它，后面那两句 `setMinimumSize` / `setMaximumSize` **全都会被无视** ——
表现就是**点了 ▢ 窗口还原不回去、一直卡在 mini 那个大小上**。离线实测第 6 组先失败、加了诊断打印才定位到。

**为什么②必须在③前面**：顺序反了会出现"`min > max`"的瞬时冲突，这一句会被直接丢掉。

**记"还原目标"要用 `getNormalBounds()` 而不是 `getBounds()`**：窗口正最大化时后者给的是**全屏尺寸**，
拿它当还原目标，退出 mini 会得到一个全屏那么大的窗口。

#### 为什么单独抽一个 `src/win-mini.js`

理由和 `bg-protocol.js` 一样：**离线实测没法 `require` 整个 `main.js`**（那会把 app 启动一遍）。
抽出来之后，`test-round10.js` 能拿**真窗口**跑**真逻辑**（`handleMiniRequest` / `applyMiniBounds` / `restoreFullBounds`），
而不是在测试里照抄一份、最后测的是自己写的桩。上面那个 `setResizable` 的坑就是这么抓到的。

#### 存档与零迁移

```js
settings.window = { mini: false, fullBounds: null, miniExpanded: false }
```

- **缺省 = 非 mini**，老存档没有这一项 → `migrateSettings()` 补成缺省，**行为跟以前完全一样**；
- 启动时主进程**照存档开窗**（`createWindow()` 里读 `settings.window`），界面再把 `body.mini` 补上 ——
  少了后半步就会"窗口是小的、界面还是完整布局"；
- 完整模式下窗口被拖动 / 缩放，**停下 0.5 秒**后由主进程推 `win:bounds` 给界面存档
  （用 `getNormalBounds()`；mini 模式下不推，否则会把 `fullBounds` 覆盖掉）。

#### 顺手堵掉自绘标题栏的三个副作用

| 加固 | 做法 |
|---|---|
| 拦 Windows 系统菜单 | `mainWindow.hookWindowMessage(0x0116, …)`：拦下 `WM_INITMENU`，把窗口**瞬间禁用再启用**（100ms）。⚠️ 实验性 API，**只在 Windows 有效**，用 `process.platform === 'win32'` + `typeof` 双重保护 |
| 拦 `Ctrl+R` | `webContents.on('before-input-event', …)` → `preventDefault()`。误按会把界面重载回首页，歌却还在响，看着像崩了 |
| 拦 Chromium 默认右键菜单 | `webContents.on('context-menu', …)` → `preventDefault()`。**但输入框里放行**（`params.isEditable` / `params.selectionText`）—— 搜索框、Cookie 输入框里右键要用系统的"粘贴 / 全选"，全禁掉就没法粘 Cookie 了 |

#### 顺手补的窗口图标

项目原来**一个图标文件都没有**（`build/` 不存在、`package.json` 里也没写图标），任务栏 / Alt+Tab 里是 Electron 的默认灰图标。
`assets/app.png` 由 `.verify/make-icon.js` **纯 Node 手搓**生成：`zlib.deflateSync` + 手写 CRC32 + IHDR/IDAT/IEND，
每个像素取 4×4 子采样按覆盖率混色（这就是全部"画图"的功夫）。**没加任何依赖**，也不用画图软件。
打包用的 `.ico` 属于"出安装包"的事，这一版不做。

### 13. 托盘 / 任务栏 / 关窗弹窗（v2.2.0）

这一版加的四块东西都跟"窗口之外"有关：屏幕右下角的**托盘图标**、任务栏图标上的**缩略图按钮**和**右键任务**、以及点 ✕ 时先问一句的**关窗弹窗**。它们碰到的坑各不相同。

#### ① 关窗行为：`before-quit` 标记 比"手动设 forceQuit"覆盖更全

需求是：点 ✕ 时可以选「缩小到任务栏」，但**从托盘菜单点「退出」必须永远真退**，不能又被拦回去藏起来。

一开始想的是"在托盘「退出」的点击处理里手动设一个 `forceQuit = true`"。但这样漏掉一堆路径：`Ctrl+Q`、系统关机、任务管理器结束进程、任何别处调的 `app.quit()`。于是改成**监听 `before-quit`**：

```js
app.on('before-quit', () => { app.quitting = true; });
```

Electron 保证**任何**走向退出的路都会先过 `before-quit`。窗口的 `close` 处理里第一件事就是问 `app.quitting`：

```js
mainWindow.on('close', (event) => {
  if (allowCloseOnce) { allowCloseOnce = false; return; }   // 我们自己发起的真关闭，放行
  event.preventDefault();
  const action = decideCloseAction({ quitting: !!app.quitting, action: uiState.closeAction });
  if (action === 'quit') { requestMainWindowClose(); return; }   // 真退：仍走存盘握手
  if (action === 'tray') { hideMainWindow(); return; }           // 缩到托盘：只是 hide
  mainWindow.webContents.send('win:ask-close');                  // 其余：弹窗问
});
```

> **★ 这里有个容易抄错的点**：参考项目 `wood3n/biu` 关窗前**不存盘**（它实时写 store），所以它的 `close` 处理里 `if (quitting) return;` 直接放行就行。
> **Neko 不是** —— 我们的存档是"攒一会儿再写"的，窗口关之前必须跟界面**握一次手**（`requestMainWindowClose()` 让界面把该存的存完再回话）。
> 所以我们的规则是：**`before-quit` 标记只跳过"询问"，不跳过"存盘"**。少了这一步，「托盘退出」虽然退得掉，但最后几秒的操作会丢。

#### ② 单实例锁：JumpList 的每一项都是"用参数启动新进程"

任务栏右键「任务」和托盘菜单的某些项，实现方式是"带参数再启动一次本程序"。要是没有单实例锁，**点一下就会开出第二个软件、两份存档互相抢**。

```js
const got = app.requestSingleInstanceLock();
if (!got) { app.quit(); }               // 第二个实例：立刻退出
else {
  app.on('second-instance', (_e, argv) => {
    showMainWindow();                     // 把已有窗口叫到前面
    handleExternalCmd(parseSecondInstanceCmd(argv) || 'show');
  });
}
```

`showMainWindow()` 里**必须三步**：`isMinimized() → restore()` → `show()` → `focus()`。只 `show()` 的话，窗口处于最小化状态时**不会还原**，看着像"没反应"。

命令行参数走**白名单**解析（`--cmd=toggle` / `--cmd=prev` / …），认不出来的**一律当 `show`**，不给外部传任意命令的口子。

#### ③ 托盘菜单：抽成 `app-menus.js`，压成纯数据来测

菜单本身是 `Menu.buildFromTemplate(模板)` 的模板数组。**难点不在建，在测** —— 模板里塞满了 `click` 回调，没法直接比对。

做法：把菜单的**构造**搬进 `src/app-menus.js`（这个文件**不 `require('electron')`**，纯函数），`buildTrayMenu(state, h)` 里所有动作都通过传入的 `h`（handlers）调用；再写一个 `describeMenu(tpl)` 把模板**压成纯数据**（`click` 只记"有没有"，不记函数体）：

```js
function describeMenu(tpl) {
  return tpl.map((it) => ({
    label: it.label, type: it.type || 'normal', enabled: it.enabled !== false,
    checked: !!it.checked, hasClick: typeof it.click === 'function',
    submenu: it.submenu ? describeMenu(it.submenu.items || it.submenu) : null,
  }));
}
```

于是离线实测里能直接 `require` 真模块、`JSON.stringify(describeMenu(...))` 跟预期**逐项对比** —— 菜单结构、哪个子菜单打了勾、哪项是灰的，全都测得到。

菜单里的**动态项**（当前歌名那一行 `enabled: false`、歌词项的开/关标签）靠"**状态一变就整个重建菜单**"来刷新（`refreshTrayMenu()`）。比"拿到菜单项对象再改它的 label"稳，因为后者依赖 Electron 内部的 `MenuItem` 引用。

#### ④ 任务栏缩略图：Electron 只给了一半

| 想要的效果 | Electron 有没有 | 我们怎么做的 |
|---|---|---|
| 预览里放 ⏮ ▶ ⏭ 三个按钮 | ✅ `setThumbarButtons` | 三个 `nativeImage`。**注意它只吃 `nativeImage`、不认 SVG**；**只要有一个图标是空的，整组按钮都不显示**；播放/暂停是**同一个按钮换图标**，所以状态一变就得**重设**一遍 |
| 缩略图换成专辑封面（网易云那种） | ❌ 用的是 Windows 私有 `DwmSetIconicThumbnail`，Electron **没暴露** | 近似做法：`setThumbnailClip({x,y,width,height})` **裁窗口的一块**。全 0 表示复位成"整个窗口预览" |
| 鼠标悬停时的一行提示 | ✅ `setThumbnailToolTip` | 顺手写上当前歌名 |
| 右键任务栏图标 → 「任务」 | ✅ `app.setUserTasks` | 5 项 + 1 条分隔线。**★ Windows 硬限制：这里不支持子菜单** —— 这就是"带层级的播放模式菜单一定挂在托盘上"的原因 |
| 图标右下角小角标 | ❌ | 没做（收益不大、容易显得花） |

**★ `coverRect` 为什么由界面量好再交给主进程**：封面在界面的什么位置，是**布局**的事（mini 下封面在左、全尺寸下在播放条最左）。要是把坐标写死在主进程里，**改一次 CSS 就错一次**。所以流程是：

```
界面量 getBoundingClientRect()  →  随 uiState 一起报给主进程  →  主进程 setThumbnailClip()
```

退出 mini 时界面报 `coverRect: null`，主进程收到就 `setThumbnailClip({0,0,0,0})` 复位。

#### ⑤ 状态上报的"去重缓存"会和主进程自己改状态打架

界面把 `playing / title / playMode / closeAction / coverRect …` 打包成一个 `uiState` 报给主进程，中间加了一层**去重**（`lastUiStateKey` 一样就不发，免得每秒都发）。

问题出在：**勾了"设为默认值"时，是主进程自己**把 `uiState.closeAction` 改成 `tray`。而界面侧的 `lastUiStateKey` 还停在旧值 `ask`。之后用户在设置里改回 `ask` —— 算出来的 key 又变回 `ask`，**正好撞上缓存，这次上报被吞掉**，主进程还以为没改。

修法：加一个 `forceReportUiState()`（先把 `lastUiStateKey = ''` 再上报），在"改了设置"和"勾了设为默认值"这两个地方用它，**绕过缓存强制上报一次**。

> 教训：**去重缓存只对"我这边驱动状态"成立**；只要有**另一方也会改同一个状态**，就必须留一个"强制上报"的出口。

#### ⑥ 托盘图标：`.ico` 是个多分辨率容器

托盘图标用 `.ico`。它的格式说穿了很简单：**6 字节文件头 + 每张图 16 字节目录项 + 直接跟图片数据**。Vista 之后允许目录项里的数据**直接就是 PNG**（不用老的 BMP）。`.ico` 本身是**多分辨率容器**，系统按当前 DPI **自己挑**合适的那张。

所以 `.verify/make-icons.js` 一次生成 **16×16 + 32×32 两张 PNG 塞进一个 `.ico`**，外加 12 个菜单小图标 + 4 个缩略图按钮 PNG（都是纯 Node：`zlib.deflateSync` + 手写 CRC32 + 每像素 4×4 子采样抗锯齿，**零依赖**）。

> **★ 白底图标的坑**：托盘菜单的小图标是**深色**的（浅粉 `#ff8ab8`），缩略图按钮的图标是**白色**的（要压在深色预览底上）—— 两套颜色不能混用，混了在某一侧就会"看不见"。

#### ⑦ 顺带堵掉的安全口子 + 稳定性

| 加固 | 做法 | 为什么 |
|---|---|---|
| 拦 `window.open` | `webContents.setWindowOpenHandler(() => ({ action: 'deny' }))` | 页面里要是被注入了外链，一点就开一个裸窗口，白给一个界面 |
| 未捕获异常 | `process.on('uncaughtException', …)` → 打日志 + `app.quitting = true` + `app.quit()` | 主进程崩了别留个"看着还在、其实已经死了"的残影，干脆干净退出 |
| 退出时销毁托盘 | `app.on('will-quit', destroyTray)` | 托盘图标是**独立于窗口**存在的，不主动销毁，进程退了图标还可能挂着 |

#### ⑧ 这一版修掉的三个真 bug（都是实测抓出来的）

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | `settings.window`（mini 状态）/ `playMode` / `lyricWin`（桌面歌词位置字号）**存得进去、读不出来**，每次启动被抹成默认值 | v2.1.0 埋下：`main.js` 读档时的"补洞"是**白名单重建** —— `const s = { theme, volume, bg, glass, autoLyric }` 只列当时认识的 5 个字段，其余**全丢** | 抽成 `src/store-migrate.js`，改成 `const s = Object.assign({}, old)` **只补不删**；不认识的新字段（比如以后的 `futureThing`）也能活下来 |
| 2 | 第一次进 mini，封面位置没传给主进程（`coverRect` 是 `null`）→ 缩略图裁不了 | `reportUiState()` 写在了 `onWinMiniState` 的"状态没变就 return"**里面**；进 mini 时界面已先把 `mini.on = true`，主进程回推的状态"没变"就被跳过 | 把 `reportUiState()` 挪到跳过判断的**外面** |
| 3 | 关窗弹窗可能**永久点不动**；改了设置**不生效** | ① `closeChoiceBusy` 置 true 后成功路径不复位；② 见上面 ⑤ 的去重缓存打架 | ① 包 `try / finally` 保证复位；② 加 `forceReportUiState()` |

> **bug 1 是最重要的一个** —— 它说明"读档补洞"这种代码**不能写成白名单**。只要将来加一个新设置项，就会静默丢一次；而且症状（"改了设置下次打开又变回去"）很难往"读档"上想。
> `verify.js` 里为此加了两条**哨兵**：`store-migrate.js` 里**不许出现** `const s = {`、**必须**有 `Object.assign({}, old)`。

### 14. 真机反馈修的四个问题（v2.2.1）

v2.2.0 发布后，用户真机上试出四个问题。这一节记**根因和教训** —— 四个都不是"功能没做"，而是"看着对、其实是坏的"。

#### ① 图标：画图函数的形参写错了（★ 最值得记的一条）

`.verify/make-icons.js` 里生成菜单图标的地方：

```js
// 错的样子
const paint = (size, x, y) => { const k = 16 / size; ... };
fs.writeFileSync(file, renderPNG(16, paint));
// 而 renderRGBA 内部是这样调的：
const [r, g, b, a] = paint(px + (sx + 0.5) / SS, py + (sy + 0.5) / SS);   // 只传两个！
```

`size` 那一格被 **x 坐标**占了，`y` 是 `undefined` → `k = 16 / x`（乱的）、`shape(garbage, NaN)`。
`NaN` 参与的比较一律为 false，于是：

- 一部分图标**每个像素都被判定为"画上了"** → **纯色块**（用户看到的粉色方块）
- 一部分图标**一个像素都没画** → **完全透明**（那些项前面一片空白）

**★ 为什么我没发现**：我生成了一张接触表 `icons-preview.png`（所有图标放大排在一起），**它是正确的** —— 因为接触表走的是另一条代码路径（`(x, y)` 两个形参，写对了）。**"预览图"和"真产物"用了两套代码，于是检查白做了。**

**教训**：
- **预览不能当验收** —— 预览和产物必须走同一条路径，否则就是在检查另一件事。
- **凡是"只在最后一步才写盘"的产物，都要把写盘的东西读回来验一遍。**

于是新增 **`.verify/check-icons.js`**：不看图，直接**把 `src/assets/` 里的 .png 解码回来数像素** —— 全透明 / 几乎全不透明 / 着墨比例不对 / 最亮处不到 200（线条没对齐像素中心）/ 两个图标长得一模一样，都会报错。

它立刻又抓出一个：`menu-lyric`（三行横杠）压在**像素边界**上，1.6 的线宽骑在两边，每个像素最多只被覆盖 3/4 → 最亮只有 191（≈75%），整枚图标比别的淡一档。把三条线挪到**像素中心**（5.5 / 8.5 / 11.5）就实了。

> 顺带：图标现在出**两档**（16×16 与 `@2x` 的 32×32），主进程用 `nativeImage.addRepresentation({ scaleFactor: 2, buffer })` 挂上去 —— 125% / 150% 缩放下系统挑清楚的那张，而不是把 16×16 硬放大。

#### ② `setThumbarButtons` 会**静默失败**

```
报告：悬停任务栏图标，预览出来了，但 ⏮ ▶ ⏭ 一个都没有。
```

两个原因叠着：

1. 图标本身是坏的（见①）—— Windows 的规矩是"**只要有一个图标是空的，整组按钮都不显示**"。
2. **时机**：原来在 `app.whenReady()` 里、`createWindow()` 之后立刻调 `refreshThumbar()`。但那个窗口是 `show: false` 建的，**真正显示要等 `ready-to-show`**。窗口还没显示时，Explorer 那边还没给它建任务栏按钮 —— `setThumbarButtons` 返回 `false` 并且**什么都不做、不报错**。

改法：在 `ready-to-show` 里 `show()` **之后**再设；另外监听 `show` 事件补一次（从托盘回来时 Explorer 偶尔会弄丢）；并把**返回值记下来**（`if (!okSet) console.error(...)`）。

> 教训：**这类"返回布尔值表示成功"的系统 API，一定要看返回值** —— 它失败得太安静了。

#### ③ 点 ✕ 绕过了一整套决策

```
报告：第一次点 ✕，弹窗根本没出现，软件直接退干净了。
```

链路是这样的：

```
#winClose（自绘标题栏的 ✕）
   → window.neko.winClose()
   → ipcRenderer.send('win-close')
   → ipcMain.on('win-close', () => requestMainWindowClose())   ← ★ 这里
   → 存盘握手 → 窗口关闭
```

而我们写的"询问 / 缩小到任务栏 / 彻底退出"三态分流，挂在 **`mainWindow.on('close')`** 上。上面的 `win-close` 直接调 `requestMainWindowClose()`，**根本没触发 `close` 事件** —— 那套判断被整段跳过。

改法一行：

```js
ipcMain.on('win-close', () => { if (mainWindow && !mainWindow.isDestroyed()) mainWindow.close(); });
```

`close()` 会触发 `close` 事件 → `preventDefault()` → `decideCloseAction()` → 分流；真要退的时候，那个处理里**再**回头调 `requestMainWindowClose()` 走存盘握手。

> 教训：**"用户点 ✕"这件事只有一条入口是对的**。任何"抄近路直接关"的地方，都会把挂在"关闭事件"上的逻辑整段绕开。同理，`window-all-closed → app.quit()` 那条路也必须是唯一出口。

#### ④ 合集封面：存档里是 32 / 0

```
报告：合集音乐播放条没有封面（显示音符兜底）。
```

查真实存档（`%APPDATA%\neko-music\neko-data.json`）：

| 键 | 实际 |
|---|---|
| `collectParts`（曲目表缓存） | **32 个合集**（134 集、328 集…） |
| `collectCovers`（每合集一张封面） | **0 条** |

背景（v2.0.5 的设计）：`DB.collectParts` 存曲目表时**故意剥掉封面**（上百集的长链接会把存档撑大），封面另存 `DB.collectCovers[bvid]`。**★ 但它只在"重新拉一遍曲目表"时才写** —— 而 `collectEntriesFor()` 一旦发现本地有缓存就**直接早退**：

```js
async function collectEntriesFor(track) {
  const cached = DB.collectParts[track.bvid];
  if (cached && cached.length > 1) return cachedCollectEntries(track.bvid, cached);  // ← 早退，永不写 collectCovers
  ...
}
```

所以对**已经缓存过**的合集，`collectCovers` 永远填不上 —— v2.0.5 那个修复对老用户等于没生效。

**改法（三层，让老存档自己长好）**：

1. `cachedCollectEntries()` 发现没封面 → 触发 `backfillCover(bvid)`（异步、去重）。
2. `ensureCid()` 顺手把封面记进 `collectCovers`（只要这个 bvid 存过曲目表）。
3. **★ `playAt()` 里单独立一道**：`if (!track.cover) backfillCover(track.bvid).then(...)`。

第 3 条是**实测逼出来的**：合集里的曲目**自带 `cid`**，`ensureCid()` 一进来发现"cid 已经有了"就直接早退、**根本不去查 `videoInfo`** —— 封面拿不到。这正是播放条一直空着的最直接原因，我第一版漏了它。

补到之后：贴到播放条（`applyTrackCover`）、写进存档、队列里同 bvid 的其它集一起补上、丢掉 memo 并重画。同一个 bvid 只补一次。

> 顺带把"贴封面"抽成了 `applyTrackCover(track)` —— 封面经常是**后到的**（要先查一次才有），所以"什么时候拿到就什么时候贴"，不能只在开播那一刻贴一次。

## 15. 快捷键为什么改成"表驱动"（v2.3.0）

### 15.1 以前的样子：一个功能一条 if

v2.3.0 之前，全部 11 条快捷键是这么写的（`app.js` 的全局 keydown）：

```js
if (e.key === 'F11') { … }
if (ctrl && (e.key === 'l' || e.key === 'L')) { … }   // Ctrl+L
if (ctrl && (e.key === 'd' || e.key === 'D')) { … }   // Ctrl+D
if (e.code === 'Space' || e.key === ' ') { … }
if (ctrl && e.key === 'ArrowLeft')  { … }   // 上一首
if (e.key === 'ArrowLeft') { … }            // 快退 —— 写在上一首后面！
```

**加一条要改三处**（if、界面提示、存档），迟早漏一处；而且用户**改不了键位**。

### 15.2 现在的样子：一张表当唯一准绳

```js
const KEY_ACTIONS = [
  { id: 'togglePlay',  name: '播放 / 暂停', def: 'Space',          hint: '…' },
  { id: 'prevTrack',   name: '上一首',     def: 'Ctrl+ArrowLeft',  hint: '' },
  { id: 'seekBack',    name: '快退 5 秒',  def: 'ArrowLeft',       hint: '' },
  // … 共 12 条（11 条老的 + 新加的「打开设置 Ctrl+,）
];
```

三件事**全部从它来**：界面画几行（`renderKeyList`）、按下去做什么（`runKeyAction` 的 switch）、提示写什么键（`keyHint`）。**以后加一条快捷键 = 表里加一行 + switch 里加一个 case。**

### 15.3 ★★ 最大的坑：修饰键必须"完全一致"

注意上面老代码的注释：**"快退"写在"上一首"后面** —— 以前是靠**代码顺序**让 `Ctrl+←` 先命中的（如果反过来写，按一次 Ctrl+← 会同时触发上一首和快退）。

改成"查表"之后，匹配是把一次按键规范化成字符串再**整串比对**：

```js
function keyFromEvent(e) {
  const k = normalizeKeyName(e.key || '');       // ' ' → 'Space'、单字母统一小写
  if (k === 'Control' || k === 'Shift' || k === 'Alt' || k === 'Meta') return null;
  const parts = [];
  if (e.ctrlKey || e.metaKey) parts.push('Ctrl');   // ★ 修饰键也进比对串
  if (e.altKey)   parts.push('Alt');
  if (e.shiftKey) parts.push('Shift');
  parts.push(k);
  return parts.join('+');                          // 'Ctrl+ArrowLeft' ≠ 'ArrowLeft'
}
```

所以 `Ctrl+←` 只会命中 `Ctrl+ArrowLeft` 那一条，`←` 只会命中 `ArrowLeft` —— **不再依赖谁写在前面**。这条由 `test-keys.js` 第 [6] 组守着（给 `runKeyAction` 挂个记录器，各按三遍盯着计数），`verify.js` 第 51 类也有对应断言。

### 15.7 Neo 选定的纯色小猫图标

软件窗口图标（任务栏 / Alt+Tab）和托盘图标统一换成**5 号「几何方块猫」**：圆角方块脸 + 两只尖耳朵，纯粉色、透明背景、没有渐变。脚本 `.verify/make-cat-icons.js` 用同一份图形分别生成 `src/assets/app.png`（256×256）和 `src/assets/tray.ico`（16 / 32 / 48 / 256 四档；前三档供托盘按 DPI 选择，256 档供 Windows 安装程序和 exe 图标）。

图标**必须验写盘的真文件**，不能只看接触表——v2.2.1 曾经发生过「预览图对、写盘图坏」；所以最后跑 `.verify/check-icons.js`，把 PNG 解码回来数着墨率、透明边缘与抗锯齿。托盘图标由旧版的 16+32 档扩为 16+32+48，并额外加入安装包所需的 256 档；全部 **38 项像素检查通过**。

### 15.4 两个一直没写下来的老规矩

1. **焦点在输入框里时快捷键一律让路**（`isTypingTarget`）—— 你在搜索框打"深夜"，按空格还是打空格。改造前后这条**一个字没动**。
2. **Esc 永远不进表** —— 它是所有面板的逃生键（关设置 / 关歌词大屏 / 关合集面板），绑走了面板就关不掉。所以录制时按 Esc = 取消录制，界面里也永远不会把它存成键位。录制期间键盘监听在捕获阶段运行，并用 `stopImmediatePropagation()` 阻止同一个 Esc 再传给「关闭设置 / 收起歌词」监听；冲突弹窗里按 Esc 也会同时丢掉待确认操作，不会关整个设置页。离屏实测第 [7] / [8] 组专门断言这一点。

### 15.5 改键位时的一个隐蔽时序 bug（实测抓出来的）

"点键位框以外的地方 = 取消录制"这个监听器一开始挂在 **document 的冒泡阶段**。结果：

```
点键位框 → 本页 click 处理先跑 → startRecordKey() 里 renderKeyList()
        把整个列表 innerHTML 重建 → 原来那个按钮被从 DOM 上摘下来
→ 这一下冒泡到 document 时，closest('.key-list') 顺着断链的节点找爹
        → 找不到 → 误判成"点在外面" → 立刻取消录制
```

表现为**怎么点都进不了录制态**。修法：那个监听器改挂**捕获阶段**（`addEventListener(…, true)`）—— 捕获在 target 处理**之前**跑，那时候节点还挂在树上。这个坑写进了 `test-keys.js` 第 [3] 组（`test-keys.js` 第一次跑就是它失败的）。

### 15.6 存档与"撞车"

- `settings.keys` **只存和默认不一样的**（空对象 = 全默认），所以**老存档零迁移**；存档被手改坏（`keys` 变成 `[]` / `null`）会被 `sanitizeKeys` 洗成空对象，不会崩。
- 想绑一个已被占用的键 → **弹冲突提示**（不静默改）。选「让出来」时旧的那条先回默认；如果它的默认**恰好就是这个键**，就存一个特殊值 `'none'`（`keyFromEvent` 永远产生不出它，等于"这条没绑键"）—— 否则两条会同时指着同一个键，谁生效全看表里的顺序。

## 16. 三个"看着没问题其实有坑"的地方（v2.4.0）

这一版修的三条都很小，但每一条都值得单独记一笔 —— 因为它们都属于"代码读起来完全正常、跑起来才炸"的类型。

### 16.1 ★★ `display: contents` 会连"约束"一起吃掉

**症状**（Neo 报的）：mini 模式下歌名一长，右边那排 `♡ 🔊 ☰ ✕ ▢` 图标会一起往右移，最后**跑到窗口外面**。

**根因是一条四环的链**，只有实测才能一节一节挖出来：

1. `.np` 用了 `display: contents` —— 这个属性会把元素**自己的盒子整个抹掉**，让子元素直接"穿透"上去参与父级的布局。抹掉的不只是盒子，**还有挂在这个盒子上的约束**，包括 `min-width: 0`。
   > 这一条最反直觉：`.np { min-width: 0 }` 明明写着，但因为有 `display: contents`，它**一点作用都没有**。
2. `.np-title` 是 `white-space: nowrap`，于是它的**最小内容宽度 = 整条歌名的宽度**（不会换行）。
3. `.player` 是**网格项**，而网格项的 `min-width` 默认是 `auto` —— 它**不会**缩到内容最小宽度以下。
4. 于是播放条被整条歌名撑宽，`.np-meta`（`flex: 0 0 100%`）跟着走，右边那排图标自然被顶出窗外。

**实测数据**（`.verify/test-round13.js` 在离屏真窗口里量的）：

| 歌名长度 | 播放条实际宽度 | 结果 |
|---|---|---|
| 6 字 | 420 | 正常 |
| 27 字 | 420 | 正常 |
| **50 字** | **684** | ✕▢ 越界 264px |
| **100 字** | **992** | ✕▢ 越界 572px |

窗口只有 420 —— 图标当然全在窗外。

**修法**：给真正会被撑宽的那个网格项补上 `min-width: 0`，并规定**让位的顺序**：

```css
body.mini .player   { min-width: 0; }              /* 网格项：允许缩到比内容更窄 */
body.mini .np-title { flex: 1 1 auto; min-width: 0; }   /* 标题先让位 */
body.mini .np-sub   { flex: 0 0 auto; max-width: 45%; } /* 作者名最多占 45% */
```

只加 `min-width: 0` 是不够的：第一版只加了这一条，结果 100 字歌名下**作者名被挤成 6px 宽**。所以还得让**标题先让位**（`flex: 1 1 auto`）、作者名**后让位**（不缩、但有 45% 上限）。

**教训**：`display: contents` 不是"这个元素不存在"，而是"它的盒子和盒子上的所有约束都不存在"。以后凡是看到 `display: contents`，都要去查它**原本打算承担的那些约束**现在落在谁身上。

### 16.2 mini 置顶必须用 `screen-saver` 这一档

`setAlwaysOnTop(true)` 不带第二个参数时，用的是默认档（`floating`）—— 普通窗口压得住它，但**别的软件全屏时会被盖住**。桌面歌词窗早就用了更高的 `screen-saver` 档，mini 这次对齐。

两个容易漏的时机：

- **进出 mini 双向都要切**：进 mini 开、退 mini 关。只做一半就会出现"退出 mini 后完整窗口一直赖在所有软件上面"。
- **存档就是 mini 时，开窗那一刻就要带上**：`createWindow()` 里加 `alwaysOnTop: startMini`，否则启动后会先以普通层级显示一帧、再升档，肉眼能看到闪一下。真正的最高档则在 `ready-to-show` 里升 —— **窗口还没显示出来就调，Windows 会一声不响地失败**（这个坑 v2.2.1 设任务栏按钮时已经踩过一次）。

为什么把它抽进 `win-mini.js`：和 `bg-protocol.js` 一样的理由 —— 抽成独立模块之后，`.verify/test-round13.js` 能 **require 它、拿真窗口验 `isAlwaysOnTop()`**，而不是在测试里照抄一份桩、最后测的是自己写的代码。

### 16.3 网格 / flex 里的"最小宽度"是一类通用坑

16.1 的本质不是"歌名太长"，而是 **CSS 里有两处默认值会让元素拒绝收缩**：

- **网格项**：`min-width: auto`（默认）→ 不会小于内容最小宽度；
- **flex 项**：同样是 `min-width: auto`。

所以"内容一长就把容器撑爆"这类问题，**先怀疑这两处**，而不是去给内容加 `overflow: hidden` 硬盖。同理，`flex-shrink: 0` 的元素在空间不够时会把别人挤没 —— 这正是 16.1 里"作者名被挤成 6px"的原因。

> **本机跑 electron 测试的两个坑**（都是环境产物，不是应用缺陷）：
> **①** 若 shell 里存在 `ELECTRON_RUN_AS_NODE=1`，electron 会被当成普通 node 跑（`app` 是 `undefined`）——
> 先 `unset ELECTRON_RUN_AS_NODE`。**②** electron 在这个环境里**不会自己退出**，
> 用 `timeout N npx electron …` 包一层，**以 `*-report.txt` 的内容为准**（结尾会写"退出码 N"）。
> 另外离屏窗口**不产生帧**，带 `transition` 的属性会"卡在切换前的旧值"上 ——
> 取样这类属性前要先注入 `* { transition: none !important }` 并强制一次重排。

> 这些脚本**不参与打包**，只是开发期的保险。
