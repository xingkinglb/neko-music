## 为什么不用普通网页而要用 Electron

浏览器里打开一个网页，**没法**自由地访问别的网站（叫"跨域限制"），也存不了本地文件。  
Electron 相当于把"浏览器"和"Node.js"焊在一起，让我们的界面既有漂亮的样子，又有程序的权限。

## 文件都是干什么的

```
Music/
├── package.json          ← 项目说明书（叫什么名、要装哪些库）
├── 启动播放器.vbs         ← 双击启动（没有黑窗口）
├── 调试启动.bat           ← 出问题时双击它看日志
└── src/
    ├── main.js           ← 主进程（幕后老板，还负责开第二个歌词窗口）
    ├── preload.js        ← 传话筒（安全的沟通桥梁）
    ├── preload-lyric.js  ← 悬浮歌词窗专用的传话筒（权限更小）
    ├── bilibili.js       ← 和 B 站对话的翻译官
    ├── bg-protocol.js    ← 背景壁纸专用的 bg:// 协议（含视频分段传输）
    ├── win-mini.js       ← mini 模式的窗口尺寸（收起 420×132 / 展开 420×520）
    ├── app-menus.js      ← 托盘菜单 / 任务栏任务 / 关窗决策 / 命令行参数（纯数据，好测）
    ├── store-migrate.js  ← 存档补洞（老存档缺字段补默认值，不认识的字段原样留着）
    ├── assets/
    │   ├── app.png       ← 窗口图标（猫耳 + 音符，由 .verify/make-icon.js 手搓生成）
    │   ├── tray.ico      ← 托盘图标（16 + 32 双尺寸，由 .verify/make-icons.js 生成）
    │   ├── menu-*.png    ← 托盘菜单里的小图标（12 个）
    │   └── thumb-*.png   ← 任务栏缩略图按钮（上一首 / 播放 / 暂停 / 下一首）
    └── ui/
        ├── index.html    ← 骨架（页面上有哪些元素）
        ├── style.css     ← 化妆（长什么样）
        ├── app.js        ← 大脑（点了什么，做什么）
        ├── lyric.html    ← 桌面歌词窗的骨架（第二个窗口）
        ├── lyric.css     ← 桌面歌词的样式
        └── lyric.js      ← 桌面歌词的逻辑（算当前句、拖动、工具条）
```

**为什么分 main 和 ui 两个进程？**

- `ui/` 里的代码跑在"网页世界"，很安全但没权限
- `main.js` 跑在"系统世界"，有权限但没法画界面
- 两个世界通过 `preload.js` 喊话：界面说"帮我搜一下钢琴"，主进程搜完把结果递回来

> ⚠️ **信封约定**：主进程的 `ipcMain.handle()` 一律返回 `{ok, data}`。  
> 界面侧必须用 `api('xxx')` 去拆信封；直接拿 `window.neko.xxx()` 得到的是**整个信封**，  
> 不是数据本身 —— 这里踩过一次坑（存档读出来"看起来有值"其实永远不对）。

## 三个最关键的技术点

### 1. wbi 签名（`bilibili.js`）

B 站为了防止别人乱调接口，要求每个搜索请求带一个**签名**。算法是：  
把参数按字母排序 → 拼成字符串 → 用一张固定的乱序表从"钥匙"里抽字符 → MD5。

这套算法藏在 `getWbiKeys()` 和 `signParams()` 里。你不需要理解它，只要知道**它是搜索能成功的前提**。

> ⚠️ 有个坑我在开发时踩过：取"钥匙"的那个接口（`nav`）在未登录时会返回 `code: -101`，  
> 但数据里照样有钥匙。所以那一步不能走"必须 code=0"的通用函数，得手动解析。

### 2. bili:// 协议（`main.js`）—— 最巧妙的一步

B 站的音频地址有**防盗链**：必须带着 `Referer: https://www.bilibili.com` 才让下载。  
可网页里的 `<audio>` 标签**没法自定义请求头**，这不是死路了吗？

解法是自己造一个协议：

```
网页写：  <audio src="bili://get?url=真实音频地址">
Electron 收到 → 由主进程代发请求，帮它加上 Referer → 把音频数据流回去
```

界面完全感觉不到中间这层，就像播放本地文件一样自然。  
代码在 `registerBiliProtocol()` 里，一共 20 行。

### 3. 只要音频，不要视频

B 站把视频和声音**分开存放**（叫 DASH 格式）。  
调 `playurl` 接口时传 `fnval=16`，就会返回一个 `dash.audio` 数组 —— 里面是**纯音频**的地址。

这样一首歌只要几 MB，还能秒开。如果下载整个视频，光是流量就浪费十倍。

### 4. 内容安全策略（CSP）与"封面破图"

页面 `<head>` 里有一行 `Content-Security-Policy`，它规定了网页**只允许从哪里加载资源**。  
我们写的是 `img-src 'self' https: data:` —— 图片只准用 https。

而 B 站的搜索接口很"随意"，封面地址经常返回 `http://i1.hdslb.com/...`（少个 s）。  
结果就是：所有封面被浏览器拦下，变成破图，控制台里刷满  
`Refused to load the image ... violates the following Content Security Policy directive`。

**修法**是在 `bilibili.js` 里加一个 `toHttps()`，把所有图片地址统一成 https 再交给界面。  
这个小函数解决了三种写法：`http://xxx`、`https://xxx`、`//xxx`（省略协议的）。

> 📌 顺便说一句：我们**没有**去放宽 CSP 让它接受 http，因为那样只是把问题藏起来；  
> 正确的做法是把数据整理干净。当然，双保险也加了（CSP 里额外放行了 B 站的图片域名）。

### 5. bg:// 协议与动态背景（`src/bg-protocol.js`）

背景壁纸也走自己造的协议。页面安全策略里**没有**放行 `file://`，  
与其把 CSP 开个大口子，不如造一个只能读取 `backgrounds/` 这一个目录的 `bg://` 协议：

- 选图 / 选视频时弹系统文件框，把文件**复制**进 `%APPDATA%\neko-music\backgrounds\`，换掉原文件也不会裂
- 协议有两道安全闸：文件名白名单（挡 `..`、反斜杠这类路径穿越写法）+ 路径越界检查（挡符号链接逃逸）
- **边读边传（支持视频）**：请求头带 `Range` 时用 `fs.createReadStream(file, {start, end})` 只发那一段，  
  返回 `206 Partial Content` + `Content-Range` + `Accept-Ranges: bytes`；不带 `Range` 就发完整流。  
  这样一段上百 MB 的视频**不用一次性读进内存**，内存占用跟文件大小脱钩。

（这一块单独拆成了 `src/bg-protocol.js`，好让自检脚本能直接把它注册起来、真发一个带 `Range` 的请求来验证。）

外观（主题色、背景、毛玻璃）全部由 CSS 变量驱动：切换主题**只改点缀色、绝不碰底色**，  
所以你的自定义背景和主题色永远不会打架。

### 6. 动态背景的性能：为什么显卡会飙到 60%

这是 v1.9.0 修掉的一个真实问题，成因有四个，按权重排：

**根因 A（主因）：4 块常驻"毛玻璃"面板压在会动的画面上**

| 面板          | 位置         |
| ----------- | ---------- |
| `.titlebar` | 整宽（顶部标题栏）  |
| `.sidebar`  | 整高（左侧边栏）   |
| `.topbar`   | 整宽（搜索栏那一条） |
| `.player`   | 整宽（底部播放条）  |

`backdrop-filter: blur(18px)` 的含义是"**把我背后那块画面实时糊一遍**"。  
背后是**静态图片**时，糊一次就缓存住了，几乎不花钱；  
背后是**视频**时，**每一帧都要重新采样 + 重新模糊**这 4 块大面积区域。  
60fps 下 ≈ 每秒 **240 次大区域高斯模糊** —— 显卡就是这么被吃掉的。

**根因 B**：模糊（`filter: blur()`）原先挂在 `.bg-layer` 上，而 `<video>` 是它的**子元素**，  
等于"先解码一帧 → 整层（含视频）糊一遍 → 再合成"。

**根因 C**：`<video>` 是**替换元素**，对绝对定位的替换元素来说，`width/height` 为 `auto` 时  
浏览器取的是它的**内在尺寸**（= 视频真实分辨率），`inset: 0` 里的 `right`/`bottom` 会被**直接忽略**。  
所以"撑满父容器"那套写法**只对普通元素有效，对 `<video>` 无效** —— 视频盒子恒等于素材分辨率  
（1920×1080 的素材就是 1920×1080，锚在左上角），窗口一小就只露左上角一块，全屏时才"看起来正常"。  
**修法就是显式写上 `width: 100%; height: 100%`。**

**根因 D**：只有"最小化"会暂停。窗口失焦、被别的窗口盖住、打开设置面板时都不停。

**v1.9.0 的对策**：

| 对策   | 做法                                                                                                                                                                                                                                        |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 修缩放  | `#bgVideo` 显式 `width/height: 100%` + `object-fit: cover`                                                                                                                                                                                  |
| 模糊隔离 | 拆出只管图片的 `.bg-image`，模糊挂在它身上；`.bg-layer` 不再挂 `filter`                                                                                                                                                                                      |
| 降毛玻璃 | 背景是视频时给 `<body>` 打 `perf-lite`，把 4 块面板的 `backdrop-filter` 设为 **`none`**（不是 `blur(0px)` —— 那个仍会把背后画面拷进纹理，省不下来），同时抬高面板底色 `--glass-boost: 0.12` 保持磨砂观感（该值 v2.0.1 起降为 0.04；**v2.0.2 起该机制连同 `--glass-boost` 一并移除**，改由「面板不透明度」`--frame-a` 统一控制） |
| 该停就停 | 窗口失焦 / 打开任意遮罩 / 最小化 → 暂停；统一由 `updateBgVideoPlayback()` 判定                                                                                                                                                                                 |

> **为什么不把视频转成 GIF**：GIF 只有 256 色（星空 + 人物渐变会出色带）、**没有硬件解码**、  
> 靠 CPU 逐帧解（GPU 60% 会变成 CPU 飙升）、同画质体积是 mp4 的 5~20 倍。  
> 开源动态壁纸 Lively Wallpaper 这类工具**全都用视频而不是 GIF**，就是这个原因。
>
> **v2.0.0 的后续**：v1.9.0 用的"背景是视频就整体降级"那条路（`body.perf-lite`）已经被  
> 下面第 7 节的"面板毛玻璃三档"取代 —— 现在不再由"背景是不是视频"决定，而是由**用户选哪一档**决定。

### 7. 面板毛玻璃三档 与 一个静默失效很久的颜色写法（v2.0.0）

**先说结论**：`backdrop-filter` 的成本不在"糊得多糊"，而在"**要糊多少次**"。  
只要**合成器还在出帧**，`blur(18px)` 和 `blur(12px)` 的差距远小于"糊一次"和"每秒糊 240 次"的差距。  
所以真正的省法只有两条：**① 让它不用实时糊（预先糊好）；② 让它别出帧（把无限动画停掉）**。

#### 三档怎么来的

存档里新增 `settings.glass.mode`，取值 `'plain'` | `'prebake'`（默认）| `'live'`，  
对应设置界面里两个**互斥的平级开关**（只勾"省显卡"= `prebake`；只勾"实时毛玻璃"= `live`；两个都不勾 = `plain`）。

| 档         | 面板背景                                                                  | `backdrop-filter`             | 成本   |
| --------- | --------------------------------------------------------------------- | ----------------------------- | ---- |
| `live`    | 半透明底色                                                                 | `blur(var(--glass-blur))` 真模糊 | 每帧重算 |
| `prebake` | `--glass-img`（JS 预先 canvas 糊好的壁纸 data:URL）+ 半透明底色 + 全局 `--bg-dim` 压暗罩 | `none`                        | ≈0   |
| `plain`   | 半透明底色                                                                 | `none`                        | ≈0   |

`prebake` 的三层背景写法（每层都用 `linear-gradient` 只为"能当一层用"）：

```css
background:
  /* ① 上层玻璃底色（v2.0.2：与四块框架共用 --frame-a，四块与内容区的差值就由它决定） */
  linear-gradient(rgb(var(--glass-rgb) / var(--frame-a)), rgb(var(--glass-rgb) / var(--frame-a))) center/cover no-repeat fixed,
  /* ② 中层压暗罩：与底图共用根级全局 --bg-dim，滑杆一拉四块面板和内容区一起变暗 */
  linear-gradient(rgb(0 0 0 / var(--bg-dim)), rgb(0 0 0 / var(--bg-dim))) center/cover no-repeat fixed,
  /* ③ 底层：预先糊好的壁纸 */
  var(--glass-img) center/cover no-repeat fixed;
```

> **v2.0.1 的两处修正**：① 面板底色"抬高量" `--glass-boost` 从 **0.12 降到 0.04**（之前面板太实，壁纸只在内容区透得出来）；  
> ② `--bg-dim` 从"只挂在壁纸层"**提升为根级全局变量**（`applyAppearance()` 里 `root.style.setProperty('--bg-dim', …)`），  
> 让"背景压暗"滑杆同时作用到底图与这四块面板 —— 否则会出现"只有内容区变暗、面板不动"。  
> 因为只是叠罩、不重烘焙 `--glass-img`，拉滑杆是即时的。

> **v2.0.2 的重做**：上面 ① 里写死的 `0.26` 换成 `var(--frame-a)`，四块框架的压暗量**收敛成一个变量**。  
> 详见下面第 8 节。

`background-attachment: fixed` 是关键：它让 4 块面板各自显示壁纸的**对应那一块**，位置才和真实壁纸对得上。

`--glass-img` 由 `app.js` 的 `buildGlassImage()` 生成：把壁纸画进 canvas，`ctx.filter = 'blur(Npx)'`，再 `toDataURL('image/jpeg', 0.86)`。  
两个坑：**①** 图片必须以 `crossOrigin='anonymous'` 加载，否则 canvas 被污染、`toDataURL()` 抛 `SecurityError`（`bg://` 协议已经发了 `Access-Control-Allow-Origin: *`）；  
**②** 写进 CSS 变量时必须包 `url("…")` —— 裸的 `data:image/jpeg;base64,…` 里有 `;`，会把 CSS 声明**提前截断**，属性被静默丢掉。

背景是**视频**时无法预糊 → 自动降级为 `plain`（不打 `has-imgbg`，那条规则自然落空）。

#### 那个静默失效很久的颜色写法

这是 v2.0.0 施工中挖出来的，**从 v1.9 甚至更早就存在**：

```css
rgba(var(--glass-rgb), 0.55)   /* --glass-rgb: 16 16 26 */
/* 展开后 → rgba(16 16 26, 0.55)  ← 非法 */
```

`rgb()` 的合法写法只有「全逗号」`rgba(16, 16, 26, 0.55)` 或「全空格 + 斜杠」`rgb(16 16 26 / 0.55)`。  
**混着写不会报错，而是静默失效**；更麻烦的是因为用了 `var()`，报错被推到 computed-value 期，  
属性会**直接取初始值**（`background-color` → `transparent`），**而不是回退到上一条声明** —— 表现就是"写了等于没写"。

项目里有 5 组"空格分隔三元组"变量，其中 4 组的半透明用法**全是坏的**：  
`--glass-rgb`（面板底色）、`--accent-rgb`（主题色，33 处）、`--accent-2-rgb`（5 处）、`--sw` / `--sw2`（设置色块）。  
修法：一律改成斜杠写法 `rgb(var(--x) / α)`；`verify.js` 第 46 类断言长期守住。

> **例外**：`lyric.css`（桌面歌词悬浮窗）里的 `rgba(var(--accent-rgb), 1)` 是**对的** ——  
> 那份 `--accent-rgb` 是悬浮窗自己定义的、**逗号分隔**（`255, 111, 165`）。  
> 这也是 `app.js` 里 `currentAccentRgb()` 要专门把空格形式转成逗号形式再推过去的原因。

#### 看不见的动画一律停掉

无限 CSS 动画会让合成器**永远在出帧**。性能暂停规则覆盖 `.idx .bars i`（列表里的跳动柱子）和 `.spinner`（加载占位转圈）；播放条封面不再添加 `.np-cover.spin::before` 旋转弧线，播放状态由播放 / 暂停按钮表示。播放条缓冲图标与歌词加载图标仍按各自状态显示，不属于这组暂停规则。  
用三个 `<body>` 类统一控制这组动画暂停，由 `syncPauseClasses()` 一处维护：

| 类             | 何时打上               | 暂停哪些                                               |
| ------------- | ------------------ | -------------------------------------------------- |
| `has-overlay` | 任意弹窗/遮罩打开（把界面整个盖住） | 内容区柱子与加载转圈                                         |
| `lyric-open`  | 整页歌词打开             | 内容区柱子与加载转圈；**并把内容区里的东西藏起来**（`#content > *`，v2.0.2） |
| `perf-idle`   | 窗口失焦 / 最小化         | 内容区柱子与加载转圈                                         |

另外，「正在播放」那三根柱子从 **SVG 改成普通 `<i>` 元素**：Chromium 里 SVG 的 `transform` 动画**不走合成器**，  
每帧都要重新光栅化；普通元素 + `transform` 才走合成。

### 8. 四块框架压暗统一为 `--frame-a` 与 歌词页藏内容（v2.0.2）

**要修的两件事**（Neo 真机反馈）：① 选视频背景时背景没铺满整个界面、四块框架深浅不一；② 打开歌词页背后还挂着上一个界面。

#### ① 四块框架的压暗量收敛成一个变量

**根因**：`prebake` 依赖"预先糊好的壁纸图"，而**视频没法预先糊**，于是视频背景下 `body` 拿不到 `has-imgbg`（`app.js` 里 `has-imgbg` 要求 `s.bg.kind !== 'video'`），四块面板就退回**一套给每块各写偏移量的备用规则**（`-0.05` / `+0.16` / `-0.12` / `+0.10`）——实测压暗 **47% / 54% / 69% / 75%**，彼此差最多 **28 个百分点**，而内容区是 **0%**。图片背景下四块虽一致，但又比内容区多压一层写死的 `rgba(16,16,26,0.26)`。


**改法**：删掉 `--glass-alpha`（旧「玻璃透明度」用的）与 `--glass-boost`，新增**一个**变量：

```css
:root { --frame-a: 0.12; }   /* 四块框架比内容区"多压"的不透明度 */
.titlebar, .sidebar, .topbar, .player { --panel-a: var(--frame-a); }
```

`prebake` 三层背景的上层也改读 `var(--frame-a)`。`app.js` 里 `applyAppearance()` 用 `--frame-a` 写根节点，存档字段 `settings.glass.frameAlpha`（缺省 `0.12`）。设置项从「玻璃透明度」改名重做成「**面板不透明度**」（0~40%）。

**为什么让老存档也走新默认**：旧值（0.55）对应的观感正是要修的"四块深浅不一"，沿用旧值就白改了 —— 所以 `migrateSettings()` 直接 `delete DB.settings.glass.alpha`。

**实测判据**（纯色壁纸逐像素采样）：`--frame-a=0` 时四块框架与内容区亮度**完全一致**（都 120）；`--frame-a=0.4` 时四块被压暗的幅度**都等于 40.7 个色阶**（理论 40.3），彼此**最大差 0.0**，内容区 **0.0**。

#### ② 歌词页背后藏掉内容区

**根因**：`.lyric-overlay` 只有 `rgba(8,8,14,0.34)`（这层 34% 黑纱是 v2.0.0 定的、**故意**透壁纸的，本轮不动），盖得住亮度、**盖不住列表形状**。

**改法**（纯 CSS，**不用改 JS** —— `syncPauseClasses()` 早就在维护 `lyric-open`）：

```css
body.lyric-open #content > * { visibility: hidden; }
```

**两个关键点**：

1. **藏"内容区里的东西"（`#content > *`），不藏"内容区这个框"（`#content`）**：藏框会连带丢掉滚动位置（退出歌词回来列表跳回顶部）；藏里面的东西布局不变、滚动位置不动。
2. 更要命的是**离屏实测踩的坑**：`#content` 是 `overflow-y:auto` 的**滚动容器**（自带合成层），"藏容器"走的是"合成器把整个滚动图层隐藏"这条优化，**在离屏软件光栅下它不重绘** —— DOM 里计算样式明明已是 `hidden`，画面上列表照旧挂着，**连拍多少张截图都是同一张旧图层**（实测跨多次运行、跨 CSS 三版，png md5 完全不变）。藏**子元素**才是让内容真正重绘成空，这条才靠谱；顺带也盖住了"歌词页开着时列表重新渲染"（子元素 `hidden`，其下新生成的行一律继承）。

**实测判据**（另开新窗口造 8 行列表 + 纯色壁纸）：歌词页开着时，内容区"有文字笔画"的格子 **0 个**；把内容区强行显示出来则是 **197 个** —— 说明列表真的被藏住了。像素差分：藏起来 81.7 ≈ 理论 82.6（壁纸过一层 34% 黑纱），强行显示后内容区 **4.1%** 的像素发生变化。

### 9. 「正在播放」高亮的判据（v2.0.3）

列表里"这一行算不算正在播放"，是 `app.js` 里一个叫 `rowIsPlaying(track)` 的小函数说了算。它只有两句话：

1. **它就是当前这一首**（`sameTrack(track, cur)`，比 `bvid` + `cid`）。
2. **它是"合集 / 分P 的入口行"** —— 一行代表整支视频，正在播它里面任意一集时保持高亮。

第 2 条是**必须**的：分P 视频摊开后，队列里躺的是"一集一集"，和列表里那**一整行**不是同一个对象 ——  
只比第 1 条的话，你在发现页点开一条合集，界面上会**一行都不亮**。

**v2.0.3 修掉的 bug**：第 2 条以前写的是"**只要 `bvid` 一样就算在播**"，  
而 **B 站的分P 视频，每一集共用同一个 `bvid`**（靠 `cid` 区分第几集）。  
于是"最近播放"里，这一支视频里**播过的每一集全都显示成"正在播放"**（实测 6 集全亮）。

**改法 —— 给第 2 条加一道闸门**：

```js
if (sameTrack(track, cur)) return true;
if (!track.bvid || !cur.bvid) return false;

// ★ 闸门：这一行自己就是某合集里的一集 → 它是一首独立的歌，只有它自己正在播才算在播
if (isCollectPart(track)) return false;

if (track.bvid === cur.bvid) return true;                       // 分P：入口行 ↔ 它里面的某一集
const parts = DB.collectParts[track.bvid];
return !!(parts && parts.some((e) => sameTrack(e, cur)));       // UP 合集：每一集自带 bvid，查表认
```

**为什么闸门能成立**：`isCollectPart(track)` 要求这一行**有 `cid`、且能在摊开的曲目表里找到自己**；  
而"入口行"（搜索结果 / 收藏夹 / UP 列表里那种）**根本没有 `cid`** —— 要播的时候才去补（`ensureCid`，`app.js:575`），  
所以入口行**永远不会**被这道闸门挡住，第 2 条的原有行为完整保留。

顺手还**删掉了一条反向误判**：`DB.collectParts[cur.bvid]` 那段"拿正在播那首的曲目表去反查别的行"，  
会让**同一个 UP 合集**里的其它集也一起点亮（UP 合集的每一集自带 `bvid`，走的是另一条路，同样被这条误伤）。

**实测判据**（离屏跑真界面，灌数据后数 DOM 里几行带 `.playing`）：

| 场景                      | 修复前       | 修复后     |
| ----------------------- | --------- | ------- |
| 分P：听过 6 集，正在播第 5 集      | **6 行全亮** | **1 行** |
| UP 合集：3 集都在历史里，正在播第 1 集 | **3 行全亮** | **1 行** |
| 合集 / 分P 的**入口行**（回归）    | 1 行       | 1 行     |
| 普通单曲列表（回归）              | 1 行       | 1 行     |

> ⚠️ **静态断言有个坑**：`if (isCollectPart(track)) return false;` 这行在 `maybeCollection()` 里**也有一份**，  
> 全文搜会假通过。所以 `verify.js` 里是**先把 `rowIsPlaying` 的函数体抠出来再查**。

### 10. 播放请求的健壮性：为什么会有「interrupted by a new load request」（v2.0.4 / v2.0.5）

**先给结论**：`The play() request was interrupted by a new load request.`  
**不是"取歌失败"**，而是**两次播放请求叠在一起**时，后一次把前一次打断留下的报错。  
它来自浏览器（Chromium），错误对象的 `name` 是 `AbortError`。

**它怎么产生的** —— `playAt(index)`（`app.js`）里有两段 `await`：

```js
await ensureCid(track);                        // ① 补"第几集"（可能要发网络请求）
const info = await api('audioUrl', …);         // ② 向 B 站要播放地址（也要发网络请求）
audio.src = info.url;                          // ③ 换掉音源
await audio.play();                            // ④ 播放
```

在 ① ② 这两段"等一等"的空隙里，**用户完全可能已经点了另一首**。于是**两个 `playAt` 叠在一起跑**：  
后一个跑到 ③ 把 `audio.src` 换掉，前一个还挂在 ④ 上的 `audio.play()` 就被**强行打断**，  
抛出的正是这句 `AbortError`。旧代码把它**当成真失败** → 弹「播放失败」+ 900ms 后自动跳下一首。

**改法：给每次切歌发一个序号**（`playSeq`）——

```js
const seq = ++playSeq;                 // 领号：本次播放的唯一身份
…
await ensureCid(track);
if (seq !== playSeq) return;           // ① 回来晚了 → 用户已经切歌，放弃（别动音源）
const info = await api('audioUrl', …);
if (seq !== playSeq) return;           // ② 同上
audio.src = info.url;
try { await audio.play(); }
catch (e) { if (isPlayInterrupted(e)) return; throw e; }   // ③ 被打断 ≠ 失败，静默
if (seq !== playSeq) return;           // ④ 播放期间被切走 → 不记历史、不刷界面
```

外加两处：

- `isPlayInterrupted(err)`：`err.name === 'AbortError'` 或消息里含 `interrupted by a new load request`  
  / `interrupted by a call to pause` → 判为"被打断"。**只有"真失败"**（要不到地址等）才照旧提示 + 自动跳下一首，  
  且那次自动跳歌**也加序号闸门**（`if (seq === playSeq) next(1);`），避免过期请求再触发一次跳歌。
- `safePlay()`：播放条上那几个按钮直接调 `audio.play()`（不 `await`）的地方统一包一层。  
  原因：`play()` 返回的是 promise，被打断时会**以 `AbortError` 拒绝** —— 没人接就变成一条  
  "未处理的 promise 拒绝"，控制台一片红。这里只把"被打断"吞掉（正常操作），其它错误照旧打日志。

**实测判据**（离屏跑真界面，桩里让 `audio.play()` 800ms 才 resolve、音源被换掉时以 `AbortError` 拒绝）：

| 场景                 | 修复前                         | 修复后               |
| ------------------ | --------------------------- | ----------------- |
| 连点两首歌（第二个打断第一个）    | 弹「播放失败：…interrupted…」+ 可能跳歌 | **0 条提示、0 次多跳**   |
| 播放条按钮在"上一次还没走完"时被点 | 1 条"未处理的 promise 拒绝"        | **0 条**           |
| 真失败（要不到地址）         | 提示 + 自动跳下一首                 | 提示 + 自动跳下一首（回归不变） |

> 💡 **记住这条判据**：只要看到 `AbortError` / `interrupted by a new load request`，  
> 就说&#x660E;**"用户换歌了"**，不是"这首歌有问题"。这类错**一律静默**，不提示、不跳歌。

**v2.0.5 的加固（三个点）**：

1. **判定不能用"整串相等"**：Chromium 会在这类消息**末尾再附一行媒体地址**，实际长这样 ——
   ```
   The play() request was interrupted by a new load request.
   https://goo.gl/LdLk22
   ```
   所以 `isPlayInterrupted()` 改成**包含**判断，并放宽到所有 `interrupted by …`  
   （同时覆盖 "a new load request" 与 "a call to pause"）。
2. **再加一道不依赖消息文字的闸门**：模块级 `lastSetSrc` 记住"最后一次写进 `audio.src` 的地址"。  
   如果本次设的 `mySrc` 已经**不是**它了，就说明中间有人换过歌 → 本次失败一律静默。  
   （为什么不直接读 `audio.src` 来比：浏览器会对 URL 做规范化，比字符串容易误判。）  
   ⚠️ 注意判据是 `(mySrc && lastSetSrc !== mySrc)` —— 先确认"我们确实设过地址"，  
   否则"取地址就失败"（`mySrc` 为空）会被误判成过期，把真失败也吞掉。
3. **真失败时提示条只显示原因本身**（`cleanPlayError()` 剪掉末尾那串地址），  
   完整信息（歌名 + 原始错误 + 地址）用 `console.error('[播放失败]', …)` 打到控制台，方便排查。

### 11. 播放条封面：为什么"重启后封面就没了"（v2.0.5）

**现象**：从**合集 / 选集**里播的歌，重启软件之后再播，播放条和列表里的封面**全空**（只剩一块占位底色）。

**真凶是一条"为了省存档"的链路**：

```
展开一个合集（如 134 集）
  ↓ 第一次联网查到曲目表（每条都带封面）
  ↓ 同时把这份表"剥掉封面"存进 DB.collectParts   ← 封面是长链接，上百集全存会把存档撑大
关掉软件，再打开 → 再播这个合集
  ↓ collectEntriesFor() 直接 return 缓存（不再联网）
  ↓ 缓存里的条目没有 cover → track.cover 为空 → 播放条 backgroundImage = none
```

**改法：每个合集只存一张封面**（不是每集都存，尊重"别把存档撑大"的初衷）

- `DB.collectCovers = { 合集bvid: 封面URL }`，写曲目表缓存时顺手记一条；
- 读缓存时用 `cachedCollectEntries()` 把这张封面**套给每一条**（带 memo，保持对象身份稳定）；
- 老存档没有这个字段 → `boot()` 里补成 `{}`，**零迁移**；
- 取舍：UP 合集里每一集原本可能各有封面，现在会**统一成合集封面**（同一个合集用一张反而更整齐）。

**顺手加的兜底**：真没封面时，`app.js` 给 `.np-cover` 挂 `.no-art` 类**并清空行内 `background-image`**  
（清空很关键 —— 行内样式会盖掉 CSS），由 `.np-cover.no-art` 显示一个**内联 SVG 音符**（`img-src` 已放行 `data:`）。

**另一处小修**：`.np-cover.open::after { content:"收起"; opacity:1 }` 里那个 `opacity: 1` 是**故意**做的"常驻提示"，  
但歌词页一开就一直挡住封面 —— v2.0.5 去掉它，出现时机交给已有的 `.np-cover:hover::after`。

### 12. mini 模式：同一个窗口换布局（v2.1.0）

#### 核心决定：**不新开窗口**

第一反应可能是"再开一个 420×132 的小窗口"。那样做的问题：第二个窗口要**重新加载一遍界面、重新读一遍存档、播放状态要跨窗口同步** —— 播放条、歌词、队列全得再搭一套通信。得不偿失。

所以走的是**同一个窗口 + 一个模式标记**：

| 谁                                  | 管什么                                                   |
| ---------------------------------- | ----------------------------------------------------- |
| **界面**（`style.css` + `app.js`）     | 给 `<body>` 加 / 去 `mini` 类（CSS 换布局）、渲染展开态的队列列表、把状态写进存档 |
| **主进程**（`win-mini.js` + `main.js`） | 把**窗口本身**缩成 420×132（展开 420×520）、记住并还原完整模式的位置尺寸        |

两边各管一半，谁也不越界。所以"进去"是**布局和窗口同时变**的，不会先闪一下再缩。

> 参考项目 `wood3n/biu` 用的是同一招（它把标记挂在 URL hash 上并另开窗口）。区别只是我们**共用本窗口**，少一整套跨窗口同步。

#### CSS 那一半：三处关键写法

**① `display: contents` 让"分组盒"消失。**  
播放条的 HTML 结构是 `.np`（封面 + 歌名 + ♡）/ `.controls` / `.volume`（词 / 打开 / 队列 / 音量）三块。  
但 mini 要的是"封面左、控制中、杂项右、歌名**单独一行**" —— 歌名得从 `.np` 里**拆出来**。  
改 HTML 结构风险大，于是用：

```css
body.mini .np,
body.mini .volume { display: contents; }
```

盒子本身消失，里面的子元素**直接变成 `.player` 的 flex 项**，再用 `order` 排个序、`flex: 0 0 100%` 把歌名顶到第二行。  
**不用动一行 HTML**。

**② 铁律：`body.mini` 下绝不给 `.app`（或 `body`）加 `transform` / `filter` / `opacity` / `will-change`。**  
原因见上面第 7 节 —— 它们会生成 "backdrop root"，把子元素的 `backdrop-filter`（毛玻璃）**打成一块纯色**。  
`verify.js` 第 48 区块有一条专门的正则守着这件事。

**③ 第一行的宽度是算出来的，不是拍脑袋。**  
窗口 420 − 左内边距 14 = **406** 的可用宽度。第一行要放：  
封面 48 + 控制键 128 + ♡ 30 + 🔊 28 + ☰ 28 + ✕▢ 68 = **330**，加 5 个 9px 间隔（45）和 ✕▢ 左边那 8px = **383**，余 23。  
**余量必须留够** —— `flex-wrap` 是"**先按假设尺寸断行、再收缩**"的，第一行一旦超宽，`✕▢` 会被整个挤到第二行去。  
（离线实测第 3 组就是这么抓到的：第一版总宽 412 > 406，`✕▢` 掉到第二行、贴不到右边缘。）

#### 主进程那一半：`setResizable` 的坑

`win-mini.js` 里两个函数，**调用顺序都是踩出来的**：

```js
// 进 mini
win.setMinimumSize(MINI_W, MINI_H_COLLAPSED);
win.setMaximumSize(MINI_W, MINI_H_EXPANDED);
win.setBounds({ x, y, width: MINI_W, height: h });
win.setResizable(false);

// 出 mini —— 顺序和上面**不一样**，而且不能换
win.setResizable(true);                      // ① 必须先解钉
win.setMaximumSize(wa.width, wa.height);     // ② 再放大上限
win.setMinimumSize(FULL_MIN_W, FULL_MIN_H);  // ③ 最后才调最小值
win.setBounds(fullBounds);
```

**为什么"出"的①必须在最前**：Windows 上 `setResizable(false)` 会把 min/max **一起钉死成"当前尺寸"**  
（这就是"不可缩放"的实现方式）。不解开它，后面那两句 `setMinimumSize` / `setMaximumSize` **全都会被无视** ——  
表现就是**点了 ▢ 窗口还原不回去、一直卡在 mini 那个大小上**。离线实测第 6 组先失败、加了诊断打印才定位到。

**为什么②必须在③前面**：顺序反了会出现"`min > max`"的瞬时冲突，这一句会被直接丢掉。

**记"还原目标"要用 `getNormalBounds()` 而不是 `getBounds()`**：窗口正最大化时后者给的是**全屏尺寸**，  
拿它当还原目标，退出 mini 会得到一个全屏那么大的窗口。

#### 为什么单独抽一个 `src/win-mini.js`

理由和 `bg-protocol.js` 一样：**离线实测没法 `require` 整个 `main.js`**（那会把 app 启动一遍）。  
抽出来之后，`test-round10.js` 能拿**真窗口**跑**真逻辑**（`handleMiniRequest` / `applyMiniBounds` / `restoreFullBounds`），  
而不是在测试里照抄一份、最后测的是自己写的桩。上面那个 `setResizable` 的坑就是这么抓到的。

#### 存档与零迁移

```js
settings.window = { mini: false, fullBounds: null, miniExpanded: false }
```

- **缺省 = 非 mini**，老存档没有这一项 → `migrateSettings()` 补成缺省，**行为跟以前完全一样**；
- 启动时主进程**照存档开窗**（`createWindow()` 里读 `settings.window`），界面再把 `body.mini` 补上 ——  
  少了后半步就会"窗口是小的、界面还是完整布局"；
- 完整模式下窗口被拖动 / 缩放，**停下 0.5 秒**后由主进程推 `win:bounds` 给界面存档  
  （用 `getNormalBounds()`；mini 模式下不推，否则会把 `fullBounds` 覆盖掉）。

#### 顺手堵掉自绘标题栏的三个副作用

| 加固                | 做法                                                                                                                                                                    |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 拦 Windows 系统菜单    | `mainWindow.hookWindowMessage(0x0116, …)`：拦下 `WM_INITMENU`，把窗口**瞬间禁用再启用**（100ms）。⚠️ 实验性 API，**只在 Windows 有效**，用 `process.platform === 'win32'` + `typeof` 双重保护        |
| 拦 `Ctrl+R`        | `webContents.on('before-input-event', …)` → `preventDefault()`。误按会把界面重载回首页，歌却还在响，看着像崩了                                                                                |
| 拦 Chromium 默认右键菜单 | `webContents.on('context-menu', …)` → `preventDefault()`。**但输入框里放行**（`params.isEditable` / `params.selectionText`）—— 搜索框、Cookie 输入框里右键要用系统的"粘贴 / 全选"，全禁掉就没法粘 Cookie 了 |

#### 顺手补的窗口图标

项目原来**一个图标文件都没有**（`build/` 不存在、`package.json` 里也没写图标），任务栏 / Alt+Tab 里是 Electron 的默认灰图标。

打包用的 `.ico` 属于"出安装包"的事，这一版不做。


### 14. 真机反馈修的四个问题（v2.2.1）

v2.2.0 发布后，用户真机上试出四个问题。这一节记**根因和教训** —— 四个都不是"功能没做"，而是"看着对、其实是坏的"。

#### ① 图标：画图函数的形参写错了（★ 最值得记的一条）

`.verify/make-icons.js` 里生成菜单图标的地方：

```js
// 错的样子
const paint = (size, x, y) => { const k = 16 / size; ... };
fs.writeFileSync(file, renderPNG(16, paint));
// 而 renderRGBA 内部是这样调的：
const [r, g, b, a] = paint(px + (sx + 0.5) / SS, py + (sy + 0.5) / SS);   // 只传两个！
```

`size` 那一格被 **x 坐标**占了，`y` 是 `undefined` → `k = 16 / x`（乱的）、`shape(garbage, NaN)`。  
`NaN` 参与的比较一律为 false，于是：

- 一部分图标**每个像素都被判定为"画上了"** → **纯色块**（用户看到的粉色方块）
- 一部分图标**一个像素都没画** → **完全透明**（那些项前面一片空白）

**★ 为什么我没发现**：我生成了一张接触表 `icons-preview.png`（所有图标放大排在一起），**它是正确的** —— 因为接触表走的是另一条代码路径（`(x, y)` 两个形参，写对了）。**"预览图"和"真产物"用了两套代码，于是检查白做了。**

**教训**：

- **预览不能当验收** —— 预览和产物必须走同一条路径，否则就是在检查另一件事。
- **凡是"只在最后一步才写盘"的产物，都要把写盘的东西读回来验一遍。**

于是新增 **`.verify/check-icons.js`**：不看图，直接**把 `src/assets/` 里的 .png 解码回来数像素** —— 全透明 / 几乎全不透明 / 着墨比例不对 / 最亮处不到 200（线条没对齐像素中心）/ 两个图标长得一模一样，都会报错。

它立刻又抓出一个：`menu-lyric`（三行横杠）压在**像素边界**上，1.6 的线宽骑在两边，每个像素最多只被覆盖 3/4 → 最亮只有 191（≈75%），整枚图标比别的淡一档。把三条线挪到**像素中心**（5.5 / 8.5 / 11.5）就实了。

> 顺带：图标现在出**两档**（16×16 与 `@2x` 的 32×32），主进程用 `nativeImage.addRepresentation({ scaleFactor: 2, buffer })` 挂上去 —— 125% / 150% 缩放下系统挑清楚的那张，而不是把 16×16 硬放大。

#### ② `setThumbarButtons` 会**静默失败**

```
报告：悬停任务栏图标，预览出来了，但 ⏮ ▶ ⏭ 一个都没有。
```

两个原因叠着：

1. 图标本身是坏的（见①）—— Windows 的规矩是"**只要有一个图标是空的，整组按钮都不显示**"。
2. **时机**：原来在 `app.whenReady()` 里、`createWindow()` 之后立刻调 `refreshThumbar()`。但那个窗口是 `show: false` 建的，**真正显示要等 `ready-to-show`**。窗口还没显示时，Explorer 那边还没给它建任务栏按钮 —— `setThumbarButtons` 返回 `false` 并且**什么都不做、不报错**。

改法：在 `ready-to-show` 里 `show()` **之后**再设；另外监听 `show` 事件补一次（从托盘回来时 Explorer 偶尔会弄丢）；并把**返回值记下来**（`if (!okSet) console.error(...)`）。

> 教训：**这类"返回布尔值表示成功"的系统 API，一定要看返回值** —— 它失败得太安静了。

#### ③ 点 ✕ 绕过了一整套决策

```
报告：第一次点 ✕，弹窗根本没出现，软件直接退干净了。
```

链路是这样的：

```
#winClose（自绘标题栏的 ✕）
   → window.neko.winClose()
   → ipcRenderer.send('win-close')
   → ipcMain.on('win-close', () => requestMainWindowClose())   ← ★ 这里
   → 存盘握手 → 窗口关闭
```

而我们写的"询问 / 缩小到任务栏 / 彻底退出"三态分流，挂在 **`mainWindow.on('close')`** 上。上面的 `win-close` 直接调 `requestMainWindowClose()`，**根本没触发 `close` 事件** —— 那套判断被整段跳过。

改法一行：

```js
ipcMain.on('win-close', () => { if (mainWindow && !mainWindow.isDestroyed()) mainWindow.close(); });
```

`close()` 会触发 `close` 事件 → `preventDefault()` → `decideCloseAction()` → 分流；真要退的时候，那个处理里**再**回头调 `requestMainWindowClose()` 走存盘握手。

> 教训：**"用户点 ✕"这件事只有一条入口是对的**。任何"抄近路直接关"的地方，都会把挂在"关闭事件"上的逻辑整段绕开。同理，`window-all-closed → app.quit()` 那条路也必须是唯一出口。

#### ④ 合集封面：存档里是 32 / 0

```
报告：合集音乐播放条没有封面（显示音符兜底）。
```

查真实存档（`%APPDATA%\neko-music\neko-data.json`）：

| 键                        | 实际                       |
| ------------------------ | ------------------------ |
| `collectParts`（曲目表缓存）    | **32 个合集**（134 集、328 集…） |
| `collectCovers`（每合集一张封面） | **0 条**                  |

背景（v2.0.5 的设计）：`DB.collectParts` 存曲目表时**故意剥掉封面**（上百集的长链接会把存档撑大），封面另存 `DB.collectCovers[bvid]`。**★ 但它只在"重新拉一遍曲目表"时才写** —— 而 `collectEntriesFor()` 一旦发现本地有缓存就**直接早退**：

```js
async function collectEntriesFor(track) {
  const cached = DB.collectParts[track.bvid];
  if (cached && cached.length > 1) return cachedCollectEntries(track.bvid, cached);  // ← 早退，永不写 collectCovers
  ...
}
```

所以对**已经缓存过**的合集，`collectCovers` 永远填不上 —— v2.0.5 那个修复对老用户等于没生效。

**改法（三层，让老存档自己长好）**：

1. `cachedCollectEntries()` 发现没封面 → 触发 `backfillCover(bvid)`（异步、去重）。
2. `ensureCid()` 顺手把封面记进 `collectCovers`（只要这个 bvid 存过曲目表）。
3. **★ `playAt()` 里单独立一道**：`if (!track.cover) backfillCover(track.bvid).then(...)`。

第 3 条是**实测逼出来的**：合集里的曲目**自带 `cid`**，`ensureCid()` 一进来发现"cid 已经有了"就直接早退、**根本不去查 `videoInfo`** —— 封面拿不到。这正是播放条一直空着的最直接原因，我第一版漏了它。

补到之后：贴到播放条（`applyTrackCover`）、写进存档、队列里同 bvid 的其它集一起补上、丢掉 memo 并重画。同一个 bvid 只补一次。

> 顺带把"贴封面"抽成了 `applyTrackCover(track)` —— 封面经常是**后到的**（要先查一次才有），所以"什么时候拿到就什么时候贴"，不能只在开播那一刻贴一次。

## 15. 快捷键为什么改成"表驱动"（v2.3.0）

### 15.1 以前的样子：一个功能一条 if

v2.3.0 之前，全部 11 条快捷键是这么写的（`app.js` 的全局 keydown）：

```js
if (e.key === 'F11') { … }
if (ctrl && (e.key === 'l' || e.key === 'L')) { … }   // Ctrl+L
if (ctrl && (e.key === 'd' || e.key === 'D')) { … }   // Ctrl+D
if (e.code === 'Space' || e.key === ' ') { … }
if (ctrl && e.key === 'ArrowLeft')  { … }   // 上一首
if (e.key === 'ArrowLeft') { … }            // 快退 —— 写在上一首后面！
```

**加一条要改三处**（if、界面提示、存档），迟早漏一处；而且用户**改不了键位**。

### 15.2 现在的样子：一张表当唯一准绳

```js
const KEY_ACTIONS = [
  { id: 'togglePlay',  name: '播放 / 暂停', def: 'Space',          hint: '…' },
  { id: 'prevTrack',   name: '上一首',     def: 'Ctrl+ArrowLeft',  hint: '' },
  { id: 'seekBack',    name: '快退 5 秒',  def: 'ArrowLeft',       hint: '' },
  // … 共 12 条（11 条老的 + 新加的「打开设置 Ctrl+,）
];
```


三件事**全部从它来**：界面画几行（`renderKeyList`）、按下去做什么（`runKeyAction` 的 switch）、提示写什么键（`keyHint`）。**以后加一条快捷键 = 表里加一行 + switch 里加一个 case。**

### 15.3 ★★ 最大的坑：修饰键必须"完全一致"

注意上面老代码的注释：**"快退"写在"上一首"后面** —— 以前是靠**代码顺序**让 `Ctrl+←` 先命中的（如果反过来写，按一次 Ctrl+← 会同时触发上一首和快退）。

改成"查表"之后，匹配是把一次按键规范化成字符串再**整串比对**：

```js
function keyFromEvent(e) {
  const k = normalizeKeyName(e.key || '');       // ' ' → 'Space'、单字母统一小写
  if (k === 'Control' || k === 'Shift' || k === 'Alt' || k === 'Meta') return null;
  const parts = [];
  if (e.ctrlKey || e.metaKey) parts.push('Ctrl');   // ★ 修饰键也进比对串
  if (e.altKey)   parts.push('Alt');
  if (e.shiftKey) parts.push('Shift');
  parts.push(k);
  return parts.join('+');                          // 'Ctrl+ArrowLeft' ≠ 'ArrowLeft'
}
```

所以 `Ctrl+←` 只会命中 `Ctrl+ArrowLeft` 那一条，`←` 只会命中 `ArrowLeft` —— **不再依赖谁写在前面**。这条由 `test-keys.js` 第 [6] 组守着（给 `runKeyAction` 挂个记录器，各按三遍盯着计数），`verify.js` 第 51 类也有对应断言。

### 15.7 Neo 选定的纯色小猫图标

软件窗口图标（任务栏 / Alt+Tab）和托盘图标统一换成**5 号「几何方块猫」**：圆角方块脸 + 两只尖耳朵，纯粉色、透明背景、没有渐变。脚本 `.verify/make-cat-icons.js` 用同一份图形分别生成 `src/assets/app.png`（256×256）和 `src/assets/tray.ico`（16 / 32 / 48 / 256 四档；前三档供托盘按 DPI 选择，256 档供 Windows 安装程序和 exe 图标）。

图标**必须验写盘的真文件**，不能只看接触表——v2.2.1 曾经发生过「预览图对、写盘图坏」；所以最后跑 `.verify/check-icons.js`，把 PNG 解码回来数着墨率、透明边缘与抗锯齿。托盘图标由旧版的 16+32 档扩为 16+32+48，并额外加入安装包所需的 256 档；全部 **38 项像素检查通过**。

### 15.4 两个一直没写下来的老规矩

1. **焦点在输入框里时快捷键一律让路**（`isTypingTarget`）—— 你在搜索框打"深夜"，按空格还是打空格。改造前后这条**一个字没动**。
2. **Esc 永远不进表** —— 它是所有面板的逃生键（关设置 / 关歌词大屏 / 关合集面板），绑走了面板就关不掉。所以录制时按 Esc = 取消录制，界面里也永远不会把它存成键位。录制期间键盘监听在捕获阶段运行，并用 `stopImmediatePropagation()` 阻止同一个 Esc 再传给「关闭设置 / 收起歌词」监听；冲突弹窗里按 Esc 也会同时丢掉待确认操作，不会关整个设置页。离屏实测第 [7] / [8] 组专门断言这一点。

### 15.5 改键位时的一个隐蔽时序 bug（实测抓出来的）

"点键位框以外的地方 = 取消录制"这个监听器一开始挂在 **document 的冒泡阶段**。结果：

```
点键位框 → 本页 click 处理先跑 → startRecordKey() 里 renderKeyList()
        把整个列表 innerHTML 重建 → 原来那个按钮被从 DOM 上摘下来
→ 这一下冒泡到 document 时，closest('.key-list') 顺着断链的节点找爹
        → 找不到 → 误判成"点在外面" → 立刻取消录制
```

表现为**怎么点都进不了录制态**。修法：那个监听器改挂**捕获阶段**（`addEventListener(…, true)`）—— 捕获在 target 处理**之前**跑，那时候节点还挂在树上。这个坑写进了 `test-keys.js` 第 [3] 组（`test-keys.js` 第一次跑就是它失败的）。

### 15.6 存档与"撞车"

- `settings.keys` **只存和默认不一样的**（空对象 = 全默认），所以**老存档零迁移**；存档被手改坏（`keys` 变成 `[]` / `null`）会被 `sanitizeKeys` 洗成空对象，不会崩。
- 想绑一个已被占用的键 → **弹冲突提示**（不静默改）。选「让出来」时旧的那条先回默认；如果它的默认**恰好就是这个键**，就存一个特殊值 `'none'`（`keyFromEvent` 永远产生不出它，等于"这条没绑键"）—— 否则两条会同时指着同一个键，谁生效全看表里的顺序。

## 16. 三个"看着没问题其实有坑"的地方（v2.4.0）

这一版修的三条都很小，但每一条都值得单独记一笔 —— 因为它们都属于"代码读起来完全正常、跑起来才炸"的类型。

### 16.1 ★★ `display: contents` 会连"约束"一起吃掉

**症状**（Neo 报的）：mini 模式下歌名一长，右边那排 `♡ 🔊 ☰ ✕ ▢` 图标会一起往右移，最后**跑到窗口外面**。

**根因是一条四环的链**，只有实测才能一节一节挖出来：

1. `.np` 用了 `display: contents` —— 这个属性会把元素**自己的盒子整个抹掉**，让子元素直接"穿透"上去参与父级的布局。抹掉的不只是盒子，**还有挂在这个盒子上的约束**，包括 `min-width: 0`。
   > 这一条最反直觉：`.np { min-width: 0 }` 明明写着，但因为有 `display: contents`，它**一点作用都没有**。
2. `.np-title` 是 `white-space: nowrap`，于是它的**最小内容宽度 = 整条歌名的宽度**（不会换行）。
3. `.player` 是**网格项**，而网格项的 `min-width` 默认是 `auto` —— 它**不会**缩到内容最小宽度以下。
4. 于是播放条被整条歌名撑宽，`.np-meta`（`flex: 0 0 100%`）跟着走，右边那排图标自然被顶出窗外。

**实测数据**（`.verify/test-round13.js` 在离屏真窗口里量的）：

| 歌名长度      | 播放条实际宽度 | 结果          |
| --------- | ------- | ----------- |
| 6 字       | 420     | 正常          |
| 27 字      | 420     | 正常          |
| **50 字**  | **684** | ✕▢ 越界 264px |
| **100 字** | **992** | ✕▢ 越界 572px |

窗口只有 420 —— 图标当然全在窗外。

**修法**：给真正会被撑宽的那个网格项补上 `min-width: 0`，并规定**让位的顺序**：

```css
body.mini .player   { min-width: 0; }              /* 网格项：允许缩到比内容更窄 */
body.mini .np-title { flex: 1 1 auto; min-width: 0; }   /* 标题先让位 */
body.mini .np-sub   { flex: 0 0 auto; max-width: 45%; } /* 作者名最多占 45% */
```

只加 `min-width: 0` 是不够的：第一版只加了这一条，结果 100 字歌名下**作者名被挤成 6px 宽**。所以还得让**标题先让位**（`flex: 1 1 auto`）、作者名**后让位**（不缩、但有 45% 上限）。

**教训**：`display: contents` 不是"这个元素不存在"，而是"它的盒子和盒子上的所有约束都不存在"。以后凡是看到 `display: contents`，都要去查它**原本打算承担的那些约束**现在落在谁身上。

### 16.2 mini 置顶必须用 `screen-saver` 这一档

`setAlwaysOnTop(true)` 不带第二个参数时，用的是默认档（`floating`）—— 普通窗口压得住它，但**别的软件全屏时会被盖住**。桌面歌词窗早就用了更高的 `screen-saver` 档，mini 这次对齐。

两个容易漏的时机：

- **进出 mini 双向都要切**：进 mini 开、退 mini 关。只做一半就会出现"退出 mini 后完整窗口一直赖在所有软件上面"。
- **存档就是 mini 时，开窗那一刻就要带上**：`createWindow()` 里加 `alwaysOnTop: startMini`，否则启动后会先以普通层级显示一帧、再升档，肉眼能看到闪一下。真正的最高档则在 `ready-to-show` 里升 —— **窗口还没显示出来就调，Windows 会一声不响地失败**（这个坑 v2.2.1 设任务栏按钮时已经踩过一次）。

为什么把它抽进 `win-mini.js`：和 `bg-protocol.js` 一样的理由 —— 抽成独立模块之后，`.verify/test-round13.js` 能 **require 它、拿真窗口验 `isAlwaysOnTop()`**，而不是在测试里照抄一份桩、最后测的是自己写的代码。

### 16.3 网格 / flex 里的"最小宽度"是一类通用坑

16.1 的本质不是"歌名太长"，而是 **CSS 里有两处默认值会让元素拒绝收缩**：

- **网格项**：`min-width: auto`（默认）→ 不会小于内容最小宽度；
- **flex 项**：同样是 `min-width: auto`。

所以"内容一长就把容器撑爆"这类问题，**先怀疑这两处**，而不是去给内容加 `overflow: hidden` 硬盖。同理，`flex-shrink: 0` 的元素在空间不够时会把别人挤没 —— 这正是 16.1 里"作者名被挤成 6px"的原因。

## 17. UP 主页分页：为什么必须"先取总数"（v2.5.0）

Neo 的原话是：「进入作者主页默认加载 30 条，想要更多需要点击右上角的『加载更多』，这操作体验很不好」。要求改成**先获取总共有多少，再按每页 30 划分**。

### 17.1 "加载更多"不是按钮丑，是这个模型本身缺信息

很容易误判成"把「加载更多」按钮换个样子、改叫「下一页」就行"。**不行**，因为：

> 「加载更多」只知道自己要**再来 30 条**，它**没有任何关于"总共有多少、我在第几页"的信息**。

`upState` 里当时只有 `list`（累加的那一坨）和一个 `hasMore` 布尔值。`hasMore` 只能回答"还有没有"，回答不了"还有几页"、"现在是第几页"。所以：

- 画不出页码条（不知道总页数，画几个格子？）；
- 副标题写不出「第 x / y 页」；
- 更致命的是 —— **列表是 `concat` 累加的**，翻到第 5 页时列表里躺着 150 条，你想"跳"到第 3 页也没有对应的数据。

**结论**：必须先从 B 站拿到**总投稿数**，才有"页"这个概念。这就是计划里第 1 步（后端带出 `total`）排在最前面的原因 —— 它是后面三步的前提。

### 17.2 每页条数只能有一个来源

后端返回的 `ps`（请求"每页几条"）和 `pageSize`（告诉界面"每页几条"）必须是**同一个数**，否则界面按 30 算页数、后端按 20 给数据，页码立刻全错位。

所以收敛成一个常量，两边都引用它：

```js
// src/bilibili.js
const UP_PAGE_SIZE = 30;   // ★ 每页 30 条（和下面的 ps 参数是同一个数，别只改一处）

const query = await signParams({ mid, ps: UP_PAGE_SIZE, pn, ... });
...
return {
  list: vlist.map(...),
  total: page.count || 0,      // 总投稿数（界面靠它算总页数）
  pageSize: UP_PAGE_SIZE,      // 每页几条（界面**不**硬编码 30）
  hasMore: pn * UP_PAGE_SIZE < (page.count || 0),
};
```

界面侧同样不写死 30：`upState.pageSize = res.pageSize || upState.pageSize || 30`，总页数 = `Math.ceil(total / pageSize)`。自检里专门有一条断言 `ps` 和 `pageSize` **同源**。

> `hasMore` 留着没删 —— 它是后端自己的关注点，只是界面不再用它了（界面改用 `total / pageSize` 算页数）。

### 17.3 翻页是"替换"，不是"累加"

这一步改的是一行代码，但影响整个模型：

```js
// 以前（累加）：翻到第 5 页，列表里躺着 150 条
upState.list = pn === 1 ? mapped : upState.list.concat(mapped);

// 现在（替换）：列表里永远只有当前这一页
upState.list = mapped;                       // ★ 只装这一页
upState.page = pn;
upState.pageSize = res.pageSize || upState.pageSize || 30;
upState.total = res.total || mapped.length;  // 后端给不出总数就退回"本页条数"
```

自检里放了一条**反向断言**守着它：`if (/upState\.list\s*=\s*pn\s*===\s*1\s*\?/.test(appjs)) err('loadUp 又变回"累加"写法了')` —— 一旦有人手滑改回去，自检立刻报错。

实测（`test-round14.js` 第 3 组）量的就是这条：点第 2 页后列表必须是 **30 行**；如果是 60 行，说明累加写法复活了。

### 17.4 页码省略规则

页数一多，页码不能全列（137 个视频 5 页还好，837 个就是 28 页）。规则是**只留「首 + 当前页前后各 2 + 尾」**，中间断开处补一个 `…`：

```js
const nums = [];
if (total <= 7) {
  for (let p = 1; p <= total; p += 1) nums.push(p);   // 页数少就全列，不省略
} else {
  const picked = new Set([1, total]);                  // 首、尾必留
  for (let p = cur - 2; p <= cur + 2; p += 1) {        // 当前页前后各 2
    if (p >= 1 && p <= total) picked.add(p);
  }
  nums.push(...[...picked].sort((a, b) => a - b));
}
```

效果（实测输出，`…` 的位置由"和上一个页码差 > 1"决定）：

| 情况           | 页码条                        |
| ------------ | -------------------------- |
| 共 5 页，第 1 页  | `1 2 3 4 5`（≤ 7 页，全列，无省略）  |
| 共 28 页，第 1 页 | `1 2 3 … 28`               |
| 共 28 页，第 3 页 | `1 2 3 4 5 … 28`           |
| 共 28 页，第 5 页 | `1 … 3 4 5 6 7 … 28`（两处省略） |

顺带：**只有 1 页时整条分页条不画**（`totalPages > 1 ? paginationHTML(...) : ''`），别让只投了 2 个视频的 UP 底下挂一条只有「1」的页码。

### 17.5 分页按钮的点击必须"抢在" `closest('[id]')` 前面

这个软件有一张**全局点击代理**（`document.addEventListener('click', ...)`），一路按 `closest()` 往下判。分页按钮只有 `data-page`、**没有 `id`**，所以如果不单独拦下来，它会一路漏到最后那段「点整行 = 播放」的逻辑里去 —— 点个页码顺手把歌播了。

所以必须**插在 `closest('[id]')` 之前**，并且自己处理"到头了"的情况：

```js
// 分页条：上一页 / 下一页 / 具体页码。
// ★ 得放在下面 closest('[id]') 之前 —— 这些按钮只有 data-page，没有 id，
//   不单独拦下的话会一路漏到最后"点整行 = 播放"那段去。
const pager = e.target.closest('.pager-num, .pager-btn');
if (pager) {
  if (pager.disabled) return;              // 首页的「上一页」/ 末页的「下一页」
  const p = Number(pager.dataset.page);
  if (upState && p >= 1 && p !== upState.page) loadUp(p);
  return;
}
```

`p !== upState.page` 是**防重复请求**：点当前页不该再发一次网络请求。

### 17.6 一个"测试脚本自己写错"的坑（值得记）

`test-round14.js` 第一版有 3 条 FAIL，看起来像功能坏了，其实是**测试点错了按钮**。

第 5 组把总数调成 837（28 页）后，脚本直接 `querySelector('[data-page="5"]')` 想跳到第 5 页 —— 但 **28 页时第 1 页的页码条只画 `1 2 3 … 28`，压根没有「5」这个按钮**，`querySelector` 返回 `null`，`click` 静默失败，页面还停在第 1 页。而第 4 组能点中「5」，是因为那时只有 5 页、页码全列出来了 —— 两组的可点击页码集合根本不同。

**修法**：先点「3」滑到中间页（页码变成 `1 2 3 4 5 … 28`），这时才点得到「5」。同时给 `click()` 的返回值加了断言（`if (!hit5) bad('第 3 页上找不到「5」按钮')`），**以后空点会当场报出来，而不是伪装成"功能不对"**。

**教训**：离屏测试里 `element.click()` 对 `null` 是**静默**的。凡是"点了没反应"的 FAIL，先确认元素**真的存在**，再去怀疑功能代码。

## 18. 导入自己的收藏夹：为什么选择集必须是 Map（v2.6.0）

Neo 想要一个"把自己 B 站收藏夹搬进来"的入口，并且提了一个关键要求：

> 在收藏夹 A 里挑 3 个 → 回列表 → 进收藏夹 B 再挑 2 个 → **最后一起导入成一个歌单**。

这条要求决定了整个功能的数据结构怎么设计。下面按"为什么"讲。

### 18.1 认人：`/x/space/myinfo`

要列**自己的**收藏夹（尤其私密收藏夹 —— 那是本人登录才看得见的），得先知道自己是谁。`getMyInfo()` 打 `https://api.bilibili.com/x/space/myinfo`，认证方式就是 SESSDATA，返回 `{ mid, name, face }`。

两个必须分开报的失败（界面据此给不同引导）：

| 情况               | 表现             | reason           |
| ---------------- | -------------- | ---------------- |
| 没填 Cookie        | 不发请求，直接引导去设置里填 | `no-cookie`      |
| Cookie 过期 / 被挤下线 | B 站回 `-101`    | `cookie-expired` |

**没填 Cookie 时提前退出**，和字幕那条是同一个规矩 —— 既然注定拿不到，就别白跑一趟、白挨一次限流：

```js
async function getMyInfo() {
  if (!hasLoginCookie()) {
    const e = new Error('还没填 B 站 Cookie，认不出你是谁');
    e.reason = 'no-cookie';
    throw e;                       // ← 一个请求都不发
  }
  ...
}
```

> ★ 这一条在**界面**里也守了一遍（先问 `hasCookie` 再决定要不要调 `myInfo`）——  
> 后端那道闸是双保险。实测 `test-round15.js` 第 1 组量的就是"没填 Cookie 时 `myInfo` 调用次数 === 0"。

### 18.2 ★★ 为什么是 `Map` 而不是数组

这是整节最要紧的一条。

「已选」这份清单有个容易忽略的性质：**B 站收藏夹里，同一个视频可以同时存在于多个收藏夹**。用户完全可能：

- 在「深夜爵士」里勾了某个视频；
- 又进「游戏音乐」看到它（它也在里面）；
- 再勾一次。

如果用**数组**存已选，就会变成两条记录，最后导入出一个**重复两遍**的歌单。要修就得自己写一遍 `find` + 判重 —— 而且每加一个入口（整夹导入 / 全选本页）都要记得再判一次。

用 **`Map` + bvid 当键**，这件事**天然就成立了**：

```js
impState.selected = new Map();   // bvid -> { track, from }
```

- 存：`selected.set(t.bvid, {...})` —— 同一个 bvid 第二次 set 只是覆盖，不会多一条；
- 查：行的勾选状态**从选择集反查** `selected.has(track.bvid)`，所以进另一个收藏夹看到同一个视频时，**它已经是勾上的**；
- 删：`selected.delete(t.bvid)` —— 在哪儿取消都干净。

`from` 记着"这一条是从哪儿选的"（收藏夹 id 或 `'up'`），用来算收藏夹卡片上的「已选 3」角标。

### 18.3 三条铁律

`selected` 是**独立于"你正在看哪一页"**&#x7684;一等状态。所以：

```js
/* ★★ 这个功能最容易做错的地方就是 selected：它是跨收藏夹累积的。
      三条铁律：
        1. 只有两件事会清空它：导入成功之后、用户点「清空选择」。
           翻页 / 换收藏夹 / 返回列表 / 回到来源选择 —— 一律不动它。
        2. 进任何一个收藏夹时，行的勾选状态从 selected 反查 ——
           所以同一个视频出现在两个收藏夹里时，第二次进去它已经是勾上的。
        3. from 用来算收藏夹卡片上的「已选 N」角标。 */
```


**铁律 1 最容易破**。最典型的写法错误是"点返回就把状态重置"：

```js
// ✗ 错：返回时顺手清空 —— 跨收藏夹累积当场失效（返回一次就白挑了）
function impBack() { impState.selected.clear(); impGo('home'); }
```

自检里专门放了一条**反向断言**钉住它：

```js
const backBody = (appjs.match(/function impBack\(\)[\s\S]*?\n}/) || [''])[0];
if (/selected\.clear\(\)/.test(backBody)) {
  err('★ impBack 里清了选择集 —— 跨收藏夹累积会当场失效（返回一次就白挑了）');
}
```

还顺手数了一下清空的总处数 —— **必须正好 2 处**：

```js
const clearCount = (appjs.match(/selected\.clear\(\)/g) || []).length;
if (clearCount !== 2) err(`★ 清空选择集的地方有 ${clearCount} 处，应该正好 2 处`);
```

这条比"检查某一处有没有写错"更强：以后谁在任何地方多加一次清空（比如"换收藏夹时重置一下"），自检立刻报错。

### 18.4 换"屏"要保留滚动，换"页"才回到顶部

导入页有三屏（选来源 / 选收藏夹 / 挑视频），共用同一个 `#content`。两种重画要分开：

```js
/** 换"屏"（step 变了）→ 重画并回到顶部 */
function impGo(step) { impState.step = step; renderImportMine(); content().scrollTop = 0; }

/** 重画但**保留滚动位置** —— 勾选 / 全选这种不该把人弹回顶部 */
function impRerender() { const top = content().scrollTop; renderImportMine(); content().scrollTop = top; }
```

勾一行就 `impGo` 的话，勾到第 30 行会被弹回顶部 —— 这种体验问题测试量不出来，但用起来很难受。

### 18.5 挑歌行的"点整行 = 勾选"必须抢在"点整行 = 播放"之前

全站有一张**全局点击代理**，最后一段是"点整行 = 播放"。挑歌那一屏点一下行却把歌播了，就是这里没拦：

```js
// 挑歌模式：点整行 = 勾选 / 取消，**不播放**。
// ★ 必须放在下面"点整行 = 播放"之前。
const pickRow = e.target.closest('.track.pickable');
if (pickRow) { impToggle(Number(pickRow.dataset.i)); return; }
```

同一类问题在收藏夹卡片上又出现了一次：卡片的**右下角那个「整个导入」按钮在卡片里面**，所以判断顺序必须是「先看是不是点了那个按钮，再看是不是点了卡片」：

```js
const wholeBtn = e.target.closest('[data-imp-whole]');   // ← 必须先判
if (wholeBtn) { ...; return; }
const folderCard = e.target.closest('[data-imp-folder]');
if (folderCard) { openImpFolder(...); return; }
```

顺序反了，点「整个导入」就会顺带跳进收藏夹。自检里用**下标比较**把顺序也钉住了：

```js
const wholeIdx = appjs.indexOf("closest('[data-imp-whole]')");
const cardIdx  = appjs.indexOf("closest('[data-imp-folder]')");
if (wholeIdx > cardIdx) err('★「整个导入」的判断排在"点卡片"之后 —— 点它会顺带进收藏夹');
```

> **一条通用规律**：DOM 事件委托里，"里层元素的判断"永远要排在"外层元素的判断"之前。
> v2.5.0 的分页条（`.pager-num` 要先于 `closest('[id]')`）踩的是同一类坑。

### 18.6 挑歌行为什么是"改列数"而不是"多插一列"

普通行是六列：`40px 56px 1fr auto auto auto`（序号 / 封面 / 信息 / 徽章 / 时长 / 操作）。
挑歌行把**序号列整个拿掉**，复选框顶上去：

```css
.track.pickable { grid-template-columns: 26px 56px 1fr auto; }
.track.pickable .idx { display: none; }   /* 序号让位 */
.track.pickable .ops { display: none; }   /* 右侧操作按钮让位 */
```

两个"让位"都不是可选的：

- `.ops` 不藏起来的话，「收藏 / 加歌单 / 详情」三个按钮在挑歌时是**干扰**，而且它们自己带 `data-act`，会**抢走点击**；
- 序号不藏起来的话就是五列挤四列的网格，错位。

顺带：`display: none` 的元素**不参与网格自动排布**，所以"藏两列、留四列"和 `grid-template-columns` 写的四列正好对上。另外挑歌模式下也**不画「选集 N」徽章**（`showBadge = !opts.pick && ...`）—— 多一个 `auto` 列就会把网格挤乱。自检里有一条断言守着它。

### 18.7 分页条：一个组件，两个页面

v2.5.0 做的 `paginationHTML(page, totalPages)` 这一版**原样复用**（没有抄第二份）。但点击代理得按"当前在哪一页"分流，否则在导入页点页码会去翻 UP 主页：

```js
const pager = e.target.closest('.pager-num, .pager-btn');
if (pager) {
  if (pager.disabled) return;
  const p = Number(pager.dataset.page);
  if (currentView === 'importMine') {
    if (impState && p >= 1 && p !== impState.page) loadImpList(p);
  } else if (upState && p >= 1 && p !== upState.page) {
    loadUp(p);
  }
  return;
}
```

### 18.8 错误码要挂成字段，不要靠字符串匹配

`requestJSON` 以前把 B 站的错误码只写在**消息字符串**里（`B 站返回错误 -101：账号未登录`）。界面想识别"Cookie 过期了"就得去 `message.includes('-101')` —— 改一次文案就失效。

这一版加了一行，把它挂成字段：

```js
const e = new Error(`B 站返回错误 ${json.code}：${json.message}`);
e.retryable = limited;
e.code = json.code;        // ★ 调用方直接读 e.code === -101，不碰字符串
throw e;
```

**教训**：凡是"调用方需要据此做判断"的信息，都不要只放在给人看的字符串里。

## 19. 收藏夹封面全空：为什么是"接口选错了"而不是 CSS（v2.6.1）

v2.6.0 上线后，Neo 一眼就发现**收藏夹卡片一个封面都没有**，全是空色块。

### 19.1 先别猜 —— 先看接口到底返回了什么

界面那一侧的代码看不出问题：`cover` 有值就画、没值就是空。所以怀疑点只有两个：
**数据里没封面**，或者**图片加载被拦**。

用真实 Cookie 直接打接口，把返回原样打出来：

```js
const a = await requestJSON('.../folder/created/list-all?up_mid=179778169');
// data.list[0] = { id, fid, mid, attr, title, fav_state, media_count,
//                  is_kid_playlist, kid_playlist_desc }
```

**根本没有 `cover` 这个字段。** 69 个收藏夹，一个封面都没有 —— `f.cover` 是 `undefined`，
过一遍 `toHttps()` 变成 `''`，界面最后拿到 `background-image: url('')`。

顺带把"图片被拦"这个假设也排掉了：拿返回的封面地址直接发请求（带 / 不带 Referer 都试），
两种都是 `200 image/jpeg`。所以**不是防盗链，也不是 CSP**。

### 19.2 换接口：分页版才带 cover

| 接口 | 一次拿几个 | 有 `cover` |
|---|---|---|
| `/x/v3/fav/folder/created/list-all` | 全部 | ❌ **没有这个字段** |
| `/x/v3/fav/folder/created/list?pn=&ps=` | 最多 100 | ✅ 有（还带 `attr_desc` / `intro` / `view_count` / `cover_type`） |

实测同一账号：`list-all` → **0/69** 有封面；`list` → **59/69**。

代价是要分页，所以加了循环，拿满 `data.count` 就收工：

```js
for (let pn = 1; pn <= 10; pn++) {
  const json = await requestJSON(`.../created/list?up_mid=${mid}&pn=${pn}&ps=${FAV_FOLDER_PAGE_SIZE}`);
  const d = json.data || {};
  const list = d.list || [];
  all.push(...list);
  // ★ count 拿不到时的兜底：没有它就会一直翻到第 10 页
  const total = typeof d.count === 'number' ? d.count : all.length;
  if (!list.length || all.length >= total) break;
}
```

### 19.3 换接口前先确认不会带坏别的字段

`list-all` 里唯一还在用的是 `attr`（判断「私密」）。换接口前**逐条比对**了 69 个收藏夹的
`attr`：两个接口**完全一致，0 处不同** —— 所以 `private: f.attr === 1` 原样保留。

> ★ 这一步值得单独拎出来：换数据源时，凡是"界面拿它做判断"的字段都要先对齐一遍，
>   不能只看"新接口字段更多"就直接换。

### 19.4 剩下 10 个怎么办：占位，不是留白

那 10 个是 B 站自己没生成封面（`cover_type: 0`，多半是夹子里最早收藏的内容已失效）。
试过"取第一条视频的封面"兜底 —— 结果 4 个夹子返回的都是**同一张「稿件已失效」灰图**，
比留白还难看，于是放弃。

最终用**音符占位**（跟播放条 `.np-cover.no-art` 同一套做法，内联 SVG data-URI）：

```js
<div class="thumb${f.cover ? '' : ' no-cover'}"${f.cover ? ` style="background-image:url('${esc(f.cover)}')"` : ''}></div>
```

**关键在后面那个三元**：没封面时**连行内 `background-image` 都不写**。
只加 `.no-cover` 类是不够的 —— 行内样式的优先级高于样式表，那条空的
`background-image: url('')` 会把 CSS 占位**盖掉**，卡片又变回空色块。

### 19.5 这种 bug 怎么用测试钉住

"字段缺失"本身静态查不出来，但**"用了哪个接口"**能查。所以 `verify.js` 第 53 类里
钉了一条反向断言：源码里不许出现 `created/list-all?up_mid=`。

另外新写了 `test-round16.js`，它的第 1 组**直接打桩 `https.request`**，
把所有请求 URL 记下来再断言 —— 这样"打了哪个接口"就成了可执行的事实，
而不是注释里的一句话：

```js
const realRequest = https.request;
https.request = (opts, cb) => { seenUrls.push(`https://${opts.hostname}${opts.path}`); /* 返回桩数据 */ };
const folders = await bili.getFavFolders(MY_MID);
// 断言：150 个收藏夹 → 正好 2 次请求；URL 里是 created/list? 而不是 list-all?
```

**判别力**：把源码回退到 v2.6.0（`git stash push -- src/`）后这一组报 **11 处失败**。

**教训**：这类"接口 A 和接口 B 长得差不多、但少一个字段"的坑，靠读文档和看命名都躲不掉 ——
只有把**真实返回打印出来**、并把**请求 URL 断言住**，这两件事做了才算真的知道。

### 19.6 顺带修掉的：安装包里 260 项垃圾

查封面时顺手看了一眼打包内容，发现 `package.json` 的 `build` 里**从来没设过 `files`**
—— electron-builder 于是走默认的"整个目录全收"。313 项里只有 53 项是运行时需要的，
剩下 260 项全是开发期的东西：

| 打进包的东西 | 条目数 | 备注 |
|---|---|---|
| `.tmp/` | 111 | **61 MB**：winCodeSign 镜像、`wc-orig.7z`、三个 8MB 的 raw、日志、草稿 |
| `.verify/` | 100 | 开发期的自检与实测脚本 |
| `docs/` | 30 | README 的截图和文档 |
| `.workbuddy` / `.workbuddy-ai` | 13 | **项目笔记**（本不该发给用户） |
| `README.md` / `CHANGELOG.md` / `.npmrc` / 三个源启动脚本 | 8 | |

加一条白名单，只收运行时真正要用的：

```json
"build": {
  "files": ["src/**", "package.json", "LICENSE"]
}
```

结果：**119,644,993 B → 81,798,011 B（省 37,846,982 B，31.6%）**。

#### ★ 这种改动最怕"排掉不该排的"，所以分三步验证

1. **先存基线**：改之前 `asar list` 把旧包的 313 项导出成清单。
2. **重建后逐条比对**：新包 53 项；`comm` 出来的"被排除 260 项"里**没有一条 `src/`**，
   "新增项"为**空** —— 也就是说没有意外多出/少掉任何 `src` 文件。
3. **对打好的 `app.asar` 跑冒烟**：用 Electron 直接加载它，确认 `main.js` 依赖的
   5 个本地模块（`app-menus` / `bg-protocol` / `bilibili` / `store-migrate` / `win-mini`）、
   `ui/` 全套、`src/assets/` 全部图标都在，应用能正常起来。

> 冒烟里出现过一条 `[userTasks] 设置任务栏任务失败`。为了确认它不是"打包丢文件"引起的，
> 又用**未打包的源码**跑了一遍 —— 报的是**完全一样**的错（沙箱不支持任务栏跳转列表），
> 于是排除。**这条对照很关键**：单看一次报错，很容易误判成自己改坏了。

#### JSON 里写不了注释，就用断言守住

`files` 写在 `package.json` 里，没法加注释解释"为什么只有这三项"。
所以在 `verify.js` 第 54 类里做成断言：白名单不许为空、必须含 `src/**` / `package.json` /

## 20. 歌词碎句：如何在不误并的前提下修复（v2.7.0）

Neo 反馈歌词显示有时把一个完整句式拆成两段。界面不是在切句：旧实现完全照抄 B 站字幕分段，
只拿 `from`（开始时间）和 `content`（文本），再按开始时间排序。B 站字幕 JSON 还提供了 `to`（结束时间）
和 `music`（歌唱置信度），之前没有利用。

### 20.1 先测真实数据：有些时间轴能判断，有些不能

在用户本机已有的真实 Cookie 下，检查播放历史里 9 首有效字幕：

- 《花海》：49 行，`music` 均值 1.00；相邻片段有 88% 的边界存在超过 0.4 秒的间隙。被切碎的「距离」+「隔不开」之间 gap=0，真句子边界有明显停顿。这种时间轴有足够信息，可以保守修复。
- 《处处吻》：74 行，只有 1% 的边界有真停顿，字幕把 `to` 填到下一句的 `from`。所有边界看起来都一样，无法推断哪里该合并；按无缝合并会把 74 行压到 42 行，明显错误。
- 漫展口播：209 行，`music` 均值只有 0.01。它的时间轴也大多无缝，但不应该被当作歌词。
- 《霓虹甜心》边界可信度 55%，略低于设定门槛；其中确有两句真歌词时间上相接，所以也选择不动。

这说明不能「见到无缝就合并」：必须先判断这是一首歌、再判断整条时间轴是否可信，最后还要限制合并后的长度。

### 20.2 三道闸门：不确定就原样返回

算法位于 `src/bilibili.js` 的 `mergeShatteredLines()`，只在取到字幕后运行。阈值集中定义：

| 闸门 | 条件 | 要避免的问题 |
|---|---|---|
| 1. 是歌吗 | 所有片段 `music` 均值 ≥ 0.5 | 过滤对白、vlog、口播 |
| 2. 时间轴可信吗 | `gap > 0.4s` 的边界比例 ≥ 60% | 过滤 `to` 铺满、没有句界信息的字幕 |
| 3. 这个点该并吗 | 当前 gap ≤ 0.05s，合并后纯文本 ≤ 15 字 | 只并无缝碎片；避免把长句的两句话粘在一起 |

距离阈值比较额外加 `1e-6`，防止浮点数把理论上 0.05 秒的边界误判成大于阈值。长度统计按 Unicode 码点，剔除 `♪` 和空白。

- `♪ 距离 ♪` + `♪ 隔不开 ♪` → `♪距离隔不开♪`（中文直接相连）
- `♪hello♪` + `♪world♪` → `♪hello world♪`（英文词之间保留空格）
- `to` 缺失、非数字或早于 `from`，整首 fail-closed；不拿未知 / 脏时间轴推断句式。
- 缺失 `music` 按 0 处理，导致唱歌闸门不过，不误修。

合并后每句开始时间沿用第一段的 `t`，其余内部字段不进入 UI。对外数据契约仍是 `[{t, text}]`，
所以整页歌词和桌面歌词**共用同一个结果**，不用各做一套逻辑。

### 20.3 为什么 15 字是安全上限

B 站一行字幕常有显示长度限制。相邻片段合并后若超过 15 个可见字符，有可能是作者为了让字幕不超宽而有意拆成两行；
因此宁可保留分段，也不把长句黏起来。实测花海副歌里「手中的风筝 放太快回不来」再接「不要你离开」会达到 16 字，
成功挡在上限之外。

### 20.4 回归结果与覆盖范围

- 真实字幕 9 首：花海 49→44 行，5 次合并；另外 8 首都原样返回。结果详见 `.verify/verify-real-merge-report.txt`。
- `.verify/test-round17.js` 使用离线 HTTP 打桩走过真实 `getSubtitle()`，验证三道闸门、缺字段 / 脏时间、短句 / 长句、
  中英文拼接、公开格式和开始时间。
- 判别力实测：把 `src/bilibili.js` 暂存回改前版本，新测试报 5 项失败；恢复后通过。
- 算法是刻意保守的：它主要帮助有精确 `to` 的字幕；`to` 铺满的字幕仍会原样显示。要覆盖后者，需要另一种歌词来源，见施工图第九节归档的第三方 LRC 计划，本版没有接外部服务。

## 21. 下载与本地歌曲：白名单协议、任务不进主存档、断流自愈（v2.8.0）

这一版加了「下载到本地」和「本地歌曲库」两块。功能本身不复杂，但有三处**必须先把设计定死**的地方，
否则会在后面变成安全漏洞或性能悬崖。分两批落地（批次 A 下载核心 → 批次 B 本地库），下面逐条讲。

### 21.1 为什么要给「本地文件」单开一个 `local://` 协议

界面是渲染进程，`contextIsolation` 开着、没有 Node 权限 —— 想播电脑里的音频文件，不能直接 `audio.src = 'C:\\...'`
（`file://` 也被 CSP 挡着）。所以照 `bili://` 的样子，主进程注册一个自定义特权协议 `local://`，由它去读磁盘。

**关键安全点：这个协议只认白名单。**

- 白名单来自 `refreshLibraryCache()`：它从 `DB.local` 的每条 `path` 里取出绝对路径，**折叠成规范形态**后放进一个 `Set`。
- `local://get?p=<路径>` 到主进程后，**先 `path.resolve`**，再拿结果去 `Set.has()` **精确匹配**：
  ```js
  if (!wl.has(target)) { /* 403，不读任何文件 */ }
  ```
- **绝对不用「拼接 + `startsWith`」**。那种写法能被 `..` 之类的相对路径穿越绕过（`C:\music\..\..\Windows\...` 也会 `startsWith` 前缀）。
  静态自检第 56 类专门钉了这条，并配了判别力实测（改成 `startsWith` 写法时断言会响）。
- 文件不存在时返回 **404**（fail-closed）—— 所以**播放会报错、但状态不会静默变坏**。
- 封面走同一个协议的另一条 route（`local://cover`），文件名用 `safeCoverName()` 生成 + 校验，中文名也不会出问题。

一句话：**`local://` 能读的，永远只有「你的本地库档案里真实登记过的那几行路径」**，渲染层拿到别的路径也换不出内容。

### 21.2 下载任务为什么不进 `neko-data.json`

主存档 `neko-data.json`（歌单 / 收藏 / 历史 / Cookie / 设置）有个特点：**体积大（实测 6MB 级）、但写入频率极低**。
而下载进度是**每 300ms 就变一次**的。如果把任务列表塞进主存档，等于每 300ms 重写一个 6MB 的 JSON —— 磁盘会哭。

所以任务单独存 `downloads.json`：

- 主进程攒 **1.5 秒**写一次（节流），退出时**强制落盘**一次。
- 写盘走 `.tmp` + 原子 rename（和背景 / 图标一样的套路），半截文件不会污染存档。
- **老存档零迁移**：`neko-data.json` 的结构一个字段没加，所以老用户直接开新版本不会有任何迁移问题。
- 静态自检第 56 类有一条**反向断言**：`store-migrate.js` 里**不许**出现 `d.downloads = ...` —— 谁哪天把任务塞回主存档，测试立刻报错。

### 21.3 本地歌为什么只需要扩 `sameTrack` 一处

「这首歌是不是同一首」这个判断，全项目只有**一个**地方定义 —— `sameTrack(a, b)`。收藏高亮、历史去重、
队列里的「正在播放」高亮、播放条的当前曲目，全靠它。

本地歌有一个天然的麻烦：它们**没有 bvid / cid**（不是 B 站的歌），那套按 `bvid` 比对的逻辑对它们完全失效。
最省力的做法不是到处加分支，而是**在 `sameTrack` 里补一条按路径判等的规则**：

```js
if (a.localPath || b.localPath) return !!a.localPath && a.localPath === b.localPath;
```

这条**必须放在按 `bvid` 比较之前**（否则两边都没有 bvid 时会误判）。
再把 `DB.local` 的条目用 `localTrack(entry)` 适配成统一的 track 形状（多带一个 `localPath` 当身份证），
于是「收藏 / 历史 / 队列 / 高亮」这些**原本就依赖 `sameTrack` 的功能，一行都不用改**就能用在本地歌上。

播放同理：`playAt` 加一条本地分支 —— 本地歌不走「解析 cid → 问 B 站要音频地址」那套，
直接 `audio.src = 'local://get?p=' + encodeURIComponent(track.localPath)` 开播；
第一次播放时若时长未知，从 `loadedmetadata` 里回填。

### 21.4 失联文件：为什么是「标记」而不是「删除」

用户会在文件管理器里直接删歌、或者换盘符，导致本地库里的某条路径指向一个**已经不存在**的文件。
旧问题：下载按钮的「绿勾」是**纯字符串并集**算出来的（`DB.local[].key` ∪ 已完成任务的 key），**从不查磁盘** →
外部删了文件，绿勾还在，再点它又不肯重下（因为程序"以为"已经有了）。

修法分两层：

1. **体检（`checkLocalMissing` / `sweepMissingLocal`）**：启动时 + 进相关视图时，批量用现成的 `local:stat` IPC
   问磁盘「这些路径还在不在」。**只把不在的标记成 `missing`，绝不删记录**（用户可能只是暂时拔了移动硬盘）。
   `local:stat` 查不到（IPC 出错）时**按「还在」处理**——宁可不标记，也不误伤。
2. **点击兜底（`revealOrRedownload`）**：点那个绿勾时**当场**再 `stat` 一次；文件在 → 打开所在文件夹；不在 →
   删掉那条 `DB.local` 记录 + 顺手清掉对应的滞留 `done` 任务 → 允许重新下载，并给一条明确提示。

界面上，失联的行压暗 + 一个「文件不见了」小标，页顶弹一条黄条带「清理失效项」按钮
（用户**主动**点才清，符合"标记 vs 删除"的边界）。

> 这里和 store-migrate 的「只许补、不许删」不冲突：那条铁律针对的是**结构字段**
> （不能把老存档里没有的字段丢掉）；删 `DB.local` 里的**数据条目**是允许的、也是用户期望的。

### 21.5 播放自愈：为什么「断流」要重新解析地址

用户报「播到一半一卡一卡，最后彻底卡死，拖进度条、重播都卡在同一个位置」。根因是一条**地址过期**的链：

- B 站给的音频地址带 `deadline` 签名，拿到后**一直用到歌曲结束、从不刷新** → 中途过期 →
  接下来发的 Range 请求被拒 → 缓冲耗尽 → audio 进入 `stalled` / `waiting`。
- 而旧代码**只监听了 8 个 audio 事件，没有 `stalled` / `waiting`** → 断流时**零自愈**。
- 拖进度条 / 重播用的还是**同一个死地址** → 所以卡在**同一个位置**（与用户描述逐字吻合）。

修法（都在 `src/ui/app.js`）：

- 解析地址里的 `deadline`（`srcDeadlineAt`，并校验它落在合理的 Unix 秒区间，避免误解析）；
- **提前刷新**：`armDeadlineTimer` 在过期前（留 60 秒余量）主动换一次地址；
- **断流自愈**：监听 `stalled` / `waiting` → `healOnStall()` → 重新解析地址；
  **换 `src` 前先记下 `currentTime`，等 `loadedmetadata`/`canplay` 再把播放位置接回去**，用户几乎无感；
- **节流**：8 秒冷却（`HEAL_COOLDOWN`），避免断流时疯狂重试；暂停状态下不动。

> 写代码前先写了探针（`.verify/probe-stall.js` / `probe-heal.js`）：确认 `deadline` 实际可解析、
> 确认 audio 真的没监听 `stalled`、确认自愈能把播放位置接回去 —— **先证明再改**，没有凭描述猜。

### 21.6 一个必须记住的布局陷阱（mini 模式）

下载按钮加在播放条的 `.volume` 组里。mini 模式下 `.volume` 是 `display: contents`（盒子消失、子元素上浮到播放条那一行），
于是**新加的 `#btnDownload` 忘了在 mini 下收起**，它以默认 `order: 0` 插到封面**前面**，整行右移 37px，
把「✕ ▢」挤到第二行。`test-round10` 第 3 组的坐标断言当场逮住了它。

## 22. 本地歌曲分文件夹：分组信息必须来自"用户选的那个目录"（v2.8.1）

v2.8.0 的「本地歌曲」页是一个平铺列表。歌一多就不好找，于是 v2.8.1 把这一页改成**左右两栏**：
左栏是文件夹列表，右栏是当前分组下的歌，右上角多一个「批量选择」按钮。这节只说其中**最容易做错**的两处。

### 22.1 `folderRoot` 的唯一来源：主进程

分组看起来很简单——"按文件夹分"嘛。但**"这个文件属于哪个文件夹"不能靠反推**：

- 导入是**递归**的（`scanAudioFolder` 最多下探 6 层）。`D:\Music\专辑A\子目录\第三首.flac` 属于
  `专辑A` 还是 `子目录`？按"父目录名"分组，同一批导入的歌会散进两个组。
- 两个不同的文件夹可能**同名**（`D:\音乐` 和 `E:\音乐`）。只记名字就会把它们合成一组。

所以记的是**用户点「导入文件夹」时选的那个根目录的完整路径**。它只能由主进程给 ——
`local:pickFolder` 从 v2.8.1 起返回 `{ root, paths, truncated }`，界面**只用 `root`**，
绝不自己从每首歌的 `path` 去 `dirname` / `split`（静态自检有一条反向断言专门盯这个）。

> 一句话：**分组信息是"用户的选择"，不是"从路径推导出来的结论"。** 前者要存，后者会错。

### 22.2 老存档的 `folderRoot` 兜底（只补不删）

v2.8.0 建的条目没有 `folderRoot`。`store-migrate.js` 里给它补 `null`，渲染时归到「导入的歌曲」一组。

★ 注意补法是**原地 `forEach` 补字段**，不是 `d.local = d.local.filter(...).map(...)`。
后者看着更"函数式"，但它会把任何不认识/坏掉的条目**顺手丢掉** —— 而铁律是
**这个函数只许补、不许删**（它以前就是"白名单重建"，把 `lyricWin` / `playMode` / `window` 全吃过）。
判别力实测里专门有一条：把 `forEach` 改成 `filter(...).forEach(...)`，静态自检必须报错。

### 22.3 批量选择：身份键必须是 `localPath`

v2.8.0 已经有"批量勾选"这套渲染（`.track.pickable` + 一个 `Map` 选择集），用的是 `bvid` 当键。
本地歌**没有 bvid**（恒为 `null`）—— 直接复用会让所有本地歌共享同一个 `null` 键，勾一首等于勾全部。

所以 `trackRow` 抽出了一个 `opts.pickKey`（默认 `'bvid'`，本地歌传 `'localPath'`）：

```js
const pickKey = opts.pickKey || 'bvid';
const pickId  = track[pickKey];
const picked  = !!(pickSet && pickId && pickSet.has(pickId));
```

下载勾选 / 导入勾选走 `bvid`，一个字不用改；本地批量选择走 `localPath`。
`localPick.selected` 是 `Map<localPath, track>`，和 `dlPick.selected`（`Map<bvid, track>`）是**两个独立的选择集**。

### 22.4 三条"自动退出"与一条"顺序"

- **换文件夹** → 退出勾选态（选择集是按上一个分组选的，留着会串）。
- **离开本地页** → 退出勾选态（`renderAll` 里统一清，和 `dlPick` 同一条规则）。
- **移出库干完** → 退出勾选态。
- **删掉正在看的分组** → 筛选退回「全部歌曲」，否则停在一个已经不存在的分组上、右栏空白。
- **左栏行的 ✕ 必须排在"点整行切分组"之前判**：✕ 是行内的按钮，点击会冒泡到行 ——
  不先拦下来就会被整行点击吃掉，表现为"点 ✕ 没反应"。静态自检盯这个顺序。

## 23. 播完一首却彻底停住：一个没有超时的 `net.fetch` 有多致命（v2.8.2）

> 现象：一首唱完、该接下一首的时候，界面像还在播，但**一点声音都没有、也不往下走**。
> 点暂停再播、拖进度条都没用。有时一首就中，有时连着几首才中。

### 23.1 先探针，别猜

两个探针分工：

- **`probe-transition.js`** —— 用**真实 B 站音源**跑一条 3 首的队列，每首 `seek` 到结尾前 2 秒，
  让它自然走到 `ended → next(1) → playAt()`。记录每个 audio 事件、每次 `api()` 调用、每次 `playAt` 进出。
  结论：**切歌链路本身是通的**（3/3 成功），但**每首歌都取了两次音频地址**。
- **`probe-hang.js`** —— 本机起一个"accept 之后一个字节都不回"的黑洞 HTTP 服务当音源，
  第二首指向它。结论（改前）：

  ```
  +1053ms ended        ct=5  → 正常进入下一首
  +1069ms loadstart    ct=0  → 新地址已设，开始加载
  +4390ms stalled      ct=0  → 断了，但……
  [30 秒后] paused=false readyState=0 toast=""   ← 永久停在这里
  ```

### 23.2 真因：三层都没有超时

1. **`bili://` 代理没有超时**。`net.fetch` 只负责发请求，CDN"连上却不回数据"时它不会自己放弃，
   会一直挂着。媒体元素于是停在 `readyState=0`：**既不 `error`，也不 `ended`**。
2. **`await audio.play()` 永远不返回**。`play()` 的 promise 只有在"真的开始播"或"出错"时才结算，
   而上面那个状态两者都不是 —— 于是 `playAt()` 卡在这一行，**不记历史、不刷界面、不跳下一首**。
3. **自愈被自己的闸门挡住**。`healOnStall` 第一句是 `if (audio.paused) return;`（"用户按了暂停就别自作主张"），
   可挂着 `play()` 的时候 `paused` **恰好是 `true`** —— 唯一能救它的那条路被当成了"用户暂停"。

### 23.3 为什么总在切歌那一下撞上

每首歌开播时的第一次 `waiting`（正常缓冲）都会触发一次自愈：重新解析地址 + 换 `src` 重载整条流。
**每切一首歌就多一次"可能挂住"的机会**，而挂在开头，看起来就是"上一首完了、下一首没声"。

### 23.4 四道闸门

| 闸门 | 位置 | 作用 |
|---|---|---|
| 首字节超时 | `main.js` `registerBiliProtocol` | 12 秒拿不到响应头就 `abort`，返回 504 → 媒体元素报错 → 界面那套自愈/跳歌接上 |
| 取消传递 | 同上 | 把 `request.signal` 接到 `AbortController`，换歌时真的断开底层连接（不再挂着占连接） |
| 开播看门狗 | `app.js` `onStartGuardTimeout` | 设了地址 12 秒还不出声 → 重试一次 → 还不行跳下一首并提示 |
| 别瞎折腾 | `app.js` `healOnStall` | ① 还没播起来（`currentTime ≈ 0`）的 `waiting` 不重载；② 刚 `seek` 过 2 秒内的不重载；③ 已到结尾（差 <1 秒）直接切歌 |

### 23.5 两个必须记住的坑

- **"按时间算的开播宽限"是错的**。第一版写成"开播 8 秒内不自愈"，`test-ui` 的自愈用例当场就红了：
  它模拟的是"播到一半断流"，也被一起挡掉了。正确的判据是**有没有真的播起来**（`currentTime`），
  不是"开播多久"。
- **结尾主动切歌要先把这首停掉**。`healOnStall` 在结尾直接 `next(1)` 之后，原曲还会在几十毫秒后
  走到真正的结尾再发一次 `ended` → **连跳两首**（`test-round22` C 组抓到 seq 1→3）。
  先 `audio.pause()` 再切，`ended` 就不会再来。

### 23.6 验证

- `probe-transition`：真实音源 3/3 切歌成功；地址请求 **4 次 / 4 首**（改前每首 2 次）。
- `probe-hang`：改前 40 秒静默不动 → 改后约 18 秒自己跳走，提示「这一首的音频流连不上，换下一首」。
- 新增 `test-round22`（5 组：开播缓冲不重载 / 拖进度不重载 / 结尾直接切歌且不连跳 / 挂住必须兜底 / 无新报错）。
- 静态自检第 56 类新增 9 条（含 4 条反向断言）；判别力 **52/52** 会响、还原后全绿。

## 24. 三处体验修正：mini 词开关 / 工具条常显 / 导入落地（v2.9.0）

这一版没有新页面，改的是三个"用起来别扭"的地方。每条都有一处**反直觉的地方**值得记下来。

### 24.1 mini 条：✕ → 「词」，但关程序的入口不能一起消失

mini 小窗上原来左边是 ✕（关程序）、右边是 ▢（回完整模式）。现在 ✕ 换成「词」（桌面歌词开关）。

**为什么要换**：`body.mini .lyric-wrap { display: none }` —— 完整模式那个「词」按钮在 mini 里是藏着的，
所以缩在小窗里时**根本没有任何歌词入口**，想开桌面歌词必须先回完整模式。而 mini 的常用姿势恰恰是
"缩在角落、把词浮在桌面上"。

**为什么敢拿掉 ✕**：关程序还剩三条路 —— 托盘菜单的「退出」、Alt+F4、回完整模式后点右上角 ✕。
（早期计划里还想加"右键 mini 条弹菜单"，最后按需求方意见砍掉了：不需要多一个入口。）

**宽度必须算**：新按钮和原来的 ✕ 都是 32px，`.mini-actions` 的 `margin-left: 8px` 也没动，
所以 `.player` 第一行的排版余量**一点没变**。这一条不是小事 —— mini 的 `flex-wrap` 是
"先按假设尺寸断行、再收缩"的，第一行一旦超宽，▢ 会被整个挤到第二行（v2.1.0 和 v2.8.0 各踩过一次）。

**状态同步**：`updateLyricBtn()` 里顺手把 `#miniLyric` 的三态（`.on` / `.none` / `.loading`）
和 `#btnLyric` 一起刷 —— 同一个真相来源（`lw().on` + `lyricState`），不给它另开一套判断。

### 24.2 工具条常显：能做得这么轻，是因为它本来就是"透明的"而不是"不存在的"

```css
.track .ops { display: flex; gap: 6px; opacity: 0; transition: opacity .15s; }
.track:hover .ops { opacity: 1; }
```

注意是 `opacity: 0`，**不是 `display: none`** —— 那排按钮一直占着宽度，只是看不见。
所以"一直显示"只是把不透明度提上来，**零布局跳动**：

```css
body.ops-always .track .ops { opacity: var(--ops-alpha, 0.55); }
body.ops-always .track:hover .ops { opacity: 1; }
```

两个决定：

- **常显不等于全亮**。一屏十几行、每行 4 个实心按钮，全亮会变成"按钮墙"，歌名的视觉重心被抢走。
  默认压到 55%，鼠标到哪一行哪一行提亮（Apple Music / Spotify 的做法）。想要全亮就把亮度拉满。
- **只能动 opacity，不能动 display**。改成 `display: none` 看着"更彻底"，但切档时整行会跳一下。
  静态自检里专门有一条反向断言盯这个（`body.ops-always .track .ops { ... display: ... }` 出现就报错）。

顺带保住了一条既有规矩：`.track.pickable .ops { display: none }`（挑视频那一屏）仍然有效 ——
它是 `display`，和 `opacity` 互不干扰，所以常显档下那一屏还是一个按钮都不显示。

亮度走 CSS 变量 `--ops-alpha`，由 `applyOpsMode()` 写到 `<html>` 上。
**`:root` 里必须给一个默认值**，否则 JS 还没跑起来的那一帧 `var(--ops-alpha)` 取不到值、
整条规则失效（静态自检第 7 类"用了未定义的变量"当场抓到过一次）。

### 24.2b 真机反馈后的两处修订

**① mini 的「词」用汉字，不用图标。** `#i-lyric` 是"三横 + 一个小圆点"，和播放队列的 ☰
并排放几乎认不出谁是谁。改成纯汉字 `<span>词</span>`，字号 12.5px（比 14px 的图标略大一点，
否则在 32px 的按钮里显得空）。取词时没有图标可转，改用透明度呼吸（`ml-breathe`）。

**② 歌曲行右侧按钮对不齐（差 13px）。** 这是个**网格自动排布**的坑：

```css
.track { display: grid; grid-template-columns: 40px 56px 1fr auto auto auto; gap: 13px; }
```

行里的元素是**按条件拼出来的**：

```
序号 / 封面 / 信息 / [文件不见了] / [合集 N 徽章] / 时长 / 操作
```

- 有徽章的行 = 6 个元素 → 正好对上 6 列；
- 没有徽章的行 = **5 个元素** → 自动排布把它们依次塞进第 1~5 列，
  于是**「时长」占了徽章那列、「操作」占了时长那列，第 6 列空着**。
  空列宽度是 0，但 `gap: 13px` 不会消失 → 那一行的按钮组整体**左移 13px**。

修法是把三样按"从右往左数"钉死（`-1` 是最右那条列线）：

```css
.track:not(.pickable) .ops       { grid-column: -2 / -1; }   /* 第 6 列 */
.track:not(.pickable) .dur       { grid-column: -3 / -2; }   /* 第 5 列 */
.track:not(.pickable) .badge,
.track:not(.pickable) .miss-chip { grid-column: -4 / -3; }   /* 第 4 列 */
```

三个要点：

- **必须限定 `:not(.pickable)`**。勾选态是另一套 4 列布局（复选框 + 封面 + 信息 + 时长），
  在这里插手会把那一屏挤乱。静态自检里有一条反向断言盯这个。
- **`.badge` 和 `.miss-chip` 共用第 4 列是安全的** —— `maybeCollection()` 里
  `if (track.localPath || !track.bvid) return false;`，而「文件不见了」只可能出现在本地歌上，
  两者不会同时存在。
- `test-round23` 的 B6 组**量的是 `getBoundingClientRect().right`**（不是看代码），
  有徽章 / 没徽章两行必须相等；判别力里也加了一条"把 `grid-column` 改回 `auto` 会响"。

### 24.3 导入落地：一个 `showPrompt()` 让整条流程静默卡住

导入页原本只有一条路（新建歌单）。现在点「导入」先问「导入 N 首到哪儿」：列出已有歌单（带首数）
+「新建一个歌单…」。并进已有歌单时用 `sameTrack()` 判重，提示分三种（全新 / 部分重复 / 全重复）。

**坑在这里**：项目自己的弹窗体系里有两个入口：

| 函数 | 用途 | 它做了什么 |
|---|---|---|
| `openPrompt()` | 需要返回值 | 挂 `promptResolve`，返回 Promise |
| `showPrompt()` | **不需要**返回值（"选歌单"这种自己就把活干完的） | **把 `promptResolve` 清成 `null`** |

第一版用了 `showPrompt()` + `closePrompt(v)`。于是 `closePrompt` 里 `const done = promptResolve` 拿到
`null`，`done(v)` 什么都不做 —— `await askImportTarget()` **永远不返回**。表现是：
弹窗关了、歌没进去、选择集也没清、页面一声不响（`test-round23` 的 C 组一次性 8 条 FAIL）。

正确写法是自己挂等待者：

```js
return new Promise((resolve) => {
  const show = (t, b, f) => { renderPrompt(t, b, f); promptResolve = resolve; $('promptMask').classList.add('show'); };
  ...
});
```

静态自检里那条断言**必须切开 `askImportTarget` 的函数体再查** —— `openPrompt` 里也有一句
`promptResolve = resolve;`，不切的话把 `askImportTarget` 里那句删掉照样"通过"（判别力实测当场抓到）。

另一个细节：取消（`done(null)`）时**不能清选择集** —— 用户只是不想导了，勾选的那些还得留着。

### 24.4 律动条：技术已验可行，这一版按住

探针 `.verify/probe-viz.js` 把四种组合都跑了一遍（`file://` 页面 + `bili://` 音频）：

| 测法 | 元数据 | 真播 | 频谱最大值 | 判定 |
|---|---|---|---|---|
| 裸奔（不补 CORS 头、不设 crossOrigin） | ✅ | ✅ | **236 / 255** | 拿到真频谱 |
| 只补 `Access-Control-Allow-Origin` | ✅ | ✅ | 230 / 255 | 拿到真频谱 |
| 只设 `audio.crossOrigin='anonymous'` | ✅ | ✅ | 230 / 255 | 拿到真频谱 |
| 两个都做 | ✅ | ✅ | 191 / 255 | 拿到真频谱 |

结论：**不需要改 `bili://` 代理、也不需要设 `crossOrigin`**。业界那个"跨源资源被污染、
analyser 静默返回全 0"的坑，在这个组合下没有出现（自定义 scheme + `bypassCSP` + `corsEnabled`
让它按同源处理了）。少改一处，就少一个把音频加载搞坏的机会。

建图之后声音照常走（`currentTime` 1.19s 正常前进），说明 `connect(ctx.destination)` 生效。

**这一版没做**，是因为它要动 Web Audio 音频图，一旦建错会让声音**彻底哑掉**（`suspended` 的上下文、
或建了图没连 destination），必须单独一轮单独验。方案与踩坑清单见
`docs/_local-notes/改造计划/改造计划-v2.9.0-mini律动条与列表工具条常显.md` 的 D 节。

## 25. 「批量下载」→「批量选择」：一个选择集挂四种动作（v2.9.0 追加）

### 25.1 起因：一条工具条只干一件事，太窄了

原来「我喜欢」和歌单右上角那颗按钮叫「批量下载」，点进去是个只能下载的选择模式
（`dlPick` + `dlBarHTML` + 「下载选中的 N 首」）。但"选中一批歌"这件事本身是中性的，
用户选完常常想做的不止一件事 —— 加歌单、收藏、或者反过来清掉一批不要的。

所以这一轮把它改成**通用的选择模式**：按钮改名「批量选择」，选择条上挂
下载 / 加入歌单 / 喜欢 / 移出 四个动作。

### 25.2 动作按视图变，但破坏性的那颗位置和配色永远不变

| 视图 | 动作（从左到右） |
|---|---|
| 我喜欢 | 下载 · 加入歌单 · **取消喜欢**（danger） |
| 歌单 | 下载 · 加入歌单 · 喜欢 · **移出歌单**（danger） |
| 本地歌曲 | 收藏 · 加入歌单 · **移出库**（danger） |

两条规则：

1. **「我喜欢」页不放「喜欢」** —— 那一页每首都已经喜欢了，放了就是个永远点不出反应的死按钮。
   那个位置换成「取消喜欢」（= 从我喜欢里摘掉），本来就是同一件事。
2. **破坏性的那颗永远是最后一个、永远是 danger 配色**。位置和颜色都别跟着视图变 ——
   这是"移除"类操作最容易出事的地方，肌肉记忆必须靠得住。

### 25.3 两条选择条合并成一个渲染器

```js
function pickBarHTML(n, actions, opts) {
  const dis = n ? '' : ' disabled';
  const btns = actions.map((a) =>
    `<button class="ghost-btn${a.danger ? ' danger' : ''}" id="${a.id}"${dis}>${ic(a.icon)}<span>${esc(a.label)}</span></button>`
  ).join('');
  return `
    <div class="imp-bar pick-bar ${opts.cls || ''}">
      <span class="imp-count">已选 <b>${n}</b> 首</span>
      <span class="imp-bar-actions">
        <button class="ghost-btn" id="${opts.allId}">全选</button>
        <button class="ghost-btn" id="${opts.noneId}"${dis}>清空选择</button>
        <span class="bar-sep"></span>
        ${btns}
      </span>
    </div>`;
}
```

「批量选择」和「本地歌曲的批量选择」都走它。以前是各写一份模板，
按钮顺序、间距、"已选 0 首时置灰"全是各写各的，改一处忘一处。

`bar-sep` 那道竖线不是装饰：左边两个按钮改的是"选哪些"，右边三四个改的是"对选中的做什么"，
中间没条线的话六颗按钮挤成一排，一眼看不出分组。

`.imp-bar-actions` 从 1 个动作按钮涨到 4 个，所以必须加 `flex-wrap: wrap` ——
否则窄窗口下整条会被撑出内容区，最右边那颗「移出」直接被裁掉（点了等于没点）。

### 25.4 身份键：歌单里可能同时躺着 B 站歌和本地歌

旧的 `dlPick` 用**裸 `bvid`** 当键。但「加入歌单」对本地歌也开放，所以一个歌单里
可能既有 `bvid` 的歌、也有 `localPath` 的歌。本地歌没有 `bvid`，于是：

- 点它勾不上（`dlToggle` 里 `if (!t.bvid) return`）；
- 全选也跳不过它；
- 用户在歌单里看到的是一行"怎么点都没反应"的歌。

现在统一用 `selKey()`：

```js
function selKey(t) {
  if (!t) return '';
  if (t.bvid) return 'b:' + t.bvid;
  if (t.localPath) return 'l:' + t.localPath;
  return '';
}
```

`trackRow` 原来只认 `opts.pickKey`（一个固定字段名），取不到统一身份，所以加了个口子：

```js
const pickId = opts.pickIdOf ? opts.pickIdOf(track) : track[pickKey];
```

两个列表都传 `pickIdOf: selKey`；本地歌曲页仍然用 `pickKey: 'localPath'`（那边键本来就是统一的）。

### 25.5 下载要筛掉本地歌，而且必须说出来

`enqueueDownloads()` 内部本来就 `filter((t) => t && t.bvid)`，也就是本地歌会被**静默丢掉**。
静默是最糟的：用户选了 5 首，结果只下了 3 首，还没有任何解释。

```js
const dlAble = list.filter((t) => t && t.bvid);
const localN = list.length - dlAble.length;
if (!dlAble.length) { toast('选中的都是本地歌，文件已经在电脑上了，不用下载'); return; }
await enqueueDownloads(dlAble, { note: localN ? `${localN} 首本地歌跳过` : '' });
```

`opts.note` 是这一轮给 `enqueueDownloads` 加的参数，拼进**同一条** toast。
为什么不"先弹一句再调它"：`toast()` 是后来居上的（`clearTimeout` + 直接换文案），
前一句会在几毫秒内被盖掉，等于没说。

### 25.6 干完退不退出模式：按"东西有没有被搬走"分

| 动作 | 做完 |
|---|---|
| 下载 | **退出**（已跳到下载管理） |
| 取消喜欢 / 移出歌单 | **退出**（选中的行已经从列表上消失了，选择集留着只会指向不存在的行） |
| 加入歌单 | 留在模式里（收藏不是"把选中的东西拿走"，用户常常接着还要下载） |
| 喜欢 | 留在模式里（同上） |

另外 `renderAll()` 里那条"换页自动退出"的闸门仍然保留：
`if (selPick && selPick.view !== currentView) selPick = null;`
少了它，从「我喜欢」切到「发现」会发现每一行都带着勾选框、点一下还弹下载。

### 25.7 移出为什么不弹确认框

和行内那个垃圾桶一个口径 —— 移错了重新加回来就行，歌本身也没被删。
批量操作再加一层"确定吗"，反而会让人以为"是不是把歌从硬盘删了"
（本地歌曲那边的「移出库」是例外：它确实动了库记录，所以那里要确认，并写明"不动磁盘文件"）。

### 25.8 两条实测上的坑（都值得记）

**① 点一行勾选会整块重画，测试不能"先查一批再挨个点"。**
`selToggle` 里是 `rerenderKeepScroll()`，点一下就重画。测试里如果先
`querySelectorAll` 拿到 3 个节点再依次 `.click()`，第二次点的是**已经脱离文档的旧节点** ——
事件不会冒泡到 `#content` 上的监听器，等于白点。第一版 `test-round24` 就是这么
"选 3 行只勾上 1 行"的。正确写法：点一行、重查一次 DOM。

**② 静态断言不能在整个 `app.js` 里 grep。**
新代码里 `selDoRemove` 写了一句 `list.some((x) => sameTrack(x, t))`，
而第 60 类那条"加入现有歌单必须按 `sameTrack` 判重"的断言原来是全局 grep
`/sameTrack\(x, t\)/` —— 于是把判重逻辑删掉，那条断言**照样绿**（判别力实测当场抓到）。
现在改成先切出 `addInto` 的函数体再查。

同理，`verify.js` 里的 `appjs` 是**去掉注释之后**的源码（见文件顶部 `stripLine` / `stripBlock`），
所以断言只能按代码形状写，靠注释里的文字去匹配永远不会命中。

## 26. 五处手感修正：吸顶 / 拖选 / 禁选文字 / 列表搜索 / 定位（v2.10.0）

### 26.1 吸顶：那 18px 的"缝"是怎么来的

`.pick-bar` 是 `.content`（唯一那个 `overflow-y: auto`）的**直接子元素**，中间没有
`overflow: hidden` 的祖先，所以 `position: sticky` 直接就能用。

但第一版写了 `top: 8px`，实测条子停在**距内容区上沿 26px** 的地方 —— 8 + `.content` 的
`padding-top: 18px`。滚动时歌曲行会从这 26px 里**冒出来**，看着像"字从条子背后探头"。

两处一起改才干净：

```css
.content:has(.pick-bar) { padding-top: 0; }
.content:has(.pick-bar) .block-head { padding-top: 18px; }

.pick-bar {
  position: sticky;
  top: 0;
  z-index: 30;
  background: color-mix(in srgb, var(--bg-soft) 94%, transparent);
  backdrop-filter: blur(18px) saturate(1.1);
  box-shadow: 0 6px 18px rgb(0 0 0 / 0.45);
}
```

- 出现选择条时，把 `.content` 的上边距**挪到 `.block-head` 的 padding 上** —— 视觉完全一样，
  但条子能真正贴到顶，上面没有缝。
- 用 `:has()` 限定"只有出现选择条才这么干"，其他 11 处 `.block-head` 一个像素都不动。

**背景必须够实**。第一版用的是 `var(--panel)`，那是 4.5% 白的半透明卡片 —— 吸顶后下面的
歌曲行直接透上来，实测截图里「已选 3 首」和下面那行的歌名叠在一起、还露出半个时长数字。
现在压到 94% 不透明的 `--bg-soft`（侧栏同色），再叠一层 `backdrop-filter` 兜住剩下的通透感。

**「退出」也必须在这条里**（v2.10.1）。第一版只把"已选 N 首 + 动作按钮"吸住了，
「退出批量选择」还挂在页面顶部那个开关上 —— 于是滚到列表下半部分想退出，还是得先滚回顶部，
等于只吸了一半。现在 `pickBarHTML` 多一个可选参数 `opts.exitId`：

```js
const exitBtn = opts.exitId
  ? `<span class="bar-sep"></span><button class="ghost-btn bar-exit" id="${opts.exitId}" …>✕<span>退出</span></button>`
  : '';
```

- 放在**动作组之后**、用 `bar-sep` 隔开：左边那排是"对选中的歌做什么"，这颗是"结束这件事"；
- 做成**淡色**（`.bar-exit { border-color: transparent; color: var(--muted) }`）——
  免得和紧挨着的「移出歌单 / 取消喜欢」抢注意力，那两颗才是危险的；
- **可选**：导入页没有"退出选择模式"这个概念（它本身就是一屏，"导入选中的 N 个"就是终点），
  所以不传 `exitId` 就不画。这条有反向断言盯着。
- 页面顶部那颗开关**保留** —— 它是进入模式的唯一入口；进去以后两处走同一个 `toggleSelPick()`，
  点哪颗效果都一样。

### 26.2 拖选：为什么必须"整段置位"

最直觉的写法是"鼠标经过一行就 toggle 一次"。**这是错的** —— 手一抖在同一行上来回动，
那行就会反复勾上又取消。所有拖动多选的 bug 都是这么来的。

正确做法（`applyDragRange`）：

1. 按下时记下**锚点**和"这一行现在勾没勾"，目标状态 = `!当前状态`（和单击翻转后的结果一致）；
2. 拖动过程中只做"设为 X"，不做"切换"；
3. 再记一份**拖动前的快照**（`Map<行号, bool>`），鼠标退回去时把"已经离开区间"的行恢复原样；
4. 每次移动都重新算区间 —— 因为指针可能从下往上拖，`lo/hi` 要用 `min/max`。

```js
const lo = Math.min(d.anchor, cur);
const hi = Math.max(d.anchor, cur);
// ① 先把"上次改过、这次已经不在区间里"的行恢复原状
for (const i of d.touched) {
  if (i >= lo && i <= hi) continue;
  const k = d.ops.keyOf(i);
  if (k) d.ops.set(k, i, d.snap.get(i));
  paintPickRow(d.rows[i], d.snap.get(i));
  d.touched.delete(i);
}
// ② 区间内一律设成 target（第一次碰到的行先记快照）
for (let i = lo; i <= hi; i++) { … }
```

三个配套细节：

- **拖动期间不重画列表**。一千行每帧重画会卡成幻灯片。只改那一行的类
  （`paintPickRow`），松手时再统一 `rerenderKeepScroll()` 一次。
- **边缘自动滚动**用 `requestAnimationFrame`，每帧 `scrollTop += 14`，
  然后用 `document.elementFromPoint(x, y)` 重新算"指针现在压着哪一行" ——
  自动滚动时指针没动、是内容在动，不重新打一枪会一直停在原来那行。
- **松手后浏览器还会补发一次 click**，不吃掉的话"拖 5 行会有 1 行被翻回去"。
  标记 `suppressClick` **不靠定时器清**，而是等下一次 `pointerdown` 时清 ——
  任何 click 都必然由一次 pointerdown 引起，所以"下一次按下"一定早于"下一次 click"。
  用 `setTimeout(0)` 清的话，定时器一响、click 还没来，就会漏吃（这条是测试 `[C4]` 抓出来的）。

### 26.3 禁止选中文字：`user-select` 写在根上，白名单只开必要的地方

```css
html, body { user-select: none; -webkit-user-select: none; }

input, textarea, select, [contenteditable="true"],
.lyric-box,   /* 整页歌词：有人会想复制一句 */
.err,         /* 报错信息：出问题得能复制出来查 */
.copyable {
  user-select: text; -webkit-user-select: text;
}
```

- **为什么写在 `html, body` 而不是 `*`**：`*` 会连输入框一起禁掉，虽然能用白名单盖回来，
  但那是靠"后写的规则"赢，容易在某次改样式时被意外覆盖。写在根上只禁一次，意图更清楚。
- `user-select` 是**继承属性**，所以给 `.lyric-box` 容器开一次，里面每一句都能选，不用逐个开。
- **`Ctrl+A` 光靠 CSS 不保险**。它在快捷键表里**没被占用**，所以按下去就是 Chromium 的"全选"。
  现在在全局 `keydown` 里拦一道，并且顺手把语义做正：批量选择模式下 = 全选歌曲。

```js
if (key === 'Ctrl+a') {
  e.preventDefault();
  if (selPick) selPickAll();
  else if (localPick) localPickAll();
  else if (impState && impState.selected) impPickAll();
  return;
}
```

★ 这段必须排在 `isTypingTarget(e.target)` 那句**之后** —— 输入框里按 `Ctrl+A` 得能全选文字。
静态自检第 62 类有一条专门盯这个先后顺序（锚点用 `if (recordingKeyId) …` 那句，
不能拿 `keyFromEvent(e)` 当锚点：`captureRecordedKey` 里也有一句一模一样的）。

### 26.4 列表搜索：三栏头部 + 只重画列表

头部从"标题 | 按钮"两栏改成"标题 | 搜索 | 按钮"三栏，**但只给这两页加 `.has-search` 修饰类** ——
另外 11 处 `.block-head` 靠 `space-between` 排的，一个字都不动。

真正的坑在**刷新方式**：

> `rerenderKeepScroll()` → `renderAll()` 会重建整个 `#content`。
> 如果搜索框也在这块里，每敲一个字输入框就被重建一次 → **焦点丢失、光标跳回开头**，
> 根本没法连续打字。

所以搜索时只替换列表那一块：

```js
function refreshListOnly() {
  const box = $('listBody');
  if (!box) { renderAll(); return; }        // 兜底：万一列表容器不在（老页面）
  box.innerHTML = currentListHTML();
  const sub = document.querySelector('#content .block-sub');
  if (sub) sub.textContent = listSubText();
}
```

**搜索"看到什么就是什么"**：`currentTracks()` 在搜索中返回筛选后的数组，
于是点行播放、全选、拖选、批量操作**全都自动对齐**，不用每处单独判一次。
`trackRow` 的 `data-i` 是按这个数组编的，索引天然一致。

**合集内部怎么搜**（已拍板：只搜已展开过的）：

```js
function collectInnerHits(track, q) {
  const parts = DB.collectParts && DB.collectParts[track.bvid];   // 展开过一次才有
  if (!parts || !parts.length) return 0;
  let n = 0;
  for (const e of parts) if (searchBlob(e).includes(q)) n++;
  return n;
}
```

- 顶层没匹配、但合集里有匹配 → 这一行**留下**，并在作者名后面挂一个「内含 N 集」小标。
- 小标为什么不塞进徽章：徽章占着网格第 4 列，再挤会让那几行又对不齐（v2.9.0 刚修过这个）。
- 点开面板时把搜索词带进 `#collectSearch` —— 面板本来就有搜索，直接复用，不新写逻辑。
- **从没展开过的合集搜不到内部**：那要联网逐个问 B 站，一个歌单十几个合集就是十几次请求。
  这是明确接受的取舍。

**搜索词要自动带进合集面板**（v2.10.0 修订）。用户搜了「光」、看到某个合集标着「内含 22 集」，
点开就是为了看"哪几集带光"，再让他手打一遍纯属添乱：

```js
// expandCollection() 里
$('collectSearch').value = listSearchCarry();
…
renderCollectList($('collectSearch').value);   // 以前这里硬写的是 ''
```

三处配套：

1. `listSearchCarry()` **只在这两页返回搜索词**，别的页面一律空 ——
   否则从歌单切到「发现」再点开一个合集，会带上一个用户压根没在这页搜过的词。
2. `renderAll()` 里加一道"不在两页就清空 `listSearch`"，双保险。
3. **面板的过滤规则必须和列表页一致**（`searchBlob(e)` = 标题 + 作者）。
   原来面板只搜标题，于是会出现"列表页说内含 22 集，点开一集都搜不到" ——
   因为列表页是按**作者名**匹配到内部的（一个合集里作者基本一致 → 22 集全算命中）。
   这种"两个地方算同一件事、规则却不一样"的错位，用户是绝对看不懂的。
   按序号跳转（搜 `12` 跳到第 12 集）保留。

### 26.5 定位：队列得先知道"从哪来的"

原来队列只有 `{ tracks, index, name }`，`name` 是一句人话（「我的歌单」），
**没有记"是从哪个页面点进来的"**，所以跳不回去。

`playTracks` 加第 4 个参数（只存内存、不写存档 —— 重启后队列本来就是空的）：

```js
function playTracks(tracks, startIndex = 0, name = '', source = null) { … }
// 唯一需要记来源的入口
playTracks(seq.list, at, viewLabel(), { view: currentView });
```

点按钮时按来源分两种走：

| 情况 | 怎么做 |
|---|---|
| 来源能重建（我喜欢 / 歌单 / 本地 / 最近播放 / 搜索页有数据…） | 切过去 → 找到这一首 → 滚到中间 → 闪一下高亮 |
| 来源不明，或那次的数据已经没了（重启过） | 退回打开「播放队列」抽屉并定位 —— **按钮点了必须有反应** |

**滚动不用 `scrollIntoView`**：它会把所有可滚动的祖先一起滚一遍，在抽屉/浮层里会整页抖。
这是项目里的老红线（歌词那边踩过），所以自己算：

```js
function centerInScroll(box, el) {
  const rb = el.getBoundingClientRect();
  const cb = box.getBoundingClientRect();
  box.scrollTop += (rb.top - cb.top) - (cb.height - rb.height) / 2;
}
```

**mini 下必须收起**：`.volume` 在 mini 里是 `display: contents`，子元素会全部上浮到播放条第一行，
多一个按钮就会把 ✕▢ 挤到第二行（v2.8.0 的 `#btnDownload` 就是这么翻的车）。
`body.mini #btnLocate { display: none; }` 是硬性的 —— verify 第 48 类那条哨兵会自动检查，
漏写直接报错。

### 26.6 删「播放全部」留下的死代码

「我喜欢」和「歌单」两页的 `btnPlayFav` / `btnPlayPl` 删掉后，
点击处理里那两行 `startFromView(...)` 也必须删 —— 留着就是永远走不到的死代码。
静态自检加了一条**反向断言**："这两个 id 不许复活"（和 v2.4.0 那条「删掉的
`btnQueueCollect` 不许复活」一个套路）。

顺带修了第 25 类那条"至少 7 处 `startFromView`"的断言：数量会因为加删按钮一直变，
改成**点名要求**「发现 / UP主页 / 解析页 / 点行播放」这几个入口必须在，才有意义。

> **本机跑 electron 测试的两个坑**（都是环境产物，不是应用缺陷）：
> **①** 若 shell 里存在 `ELECTRON_RUN_AS_NODE=1`，electron 会被当成普通 node 跑（`app` 是 `undefined`，
> 脚本会以退出码 9 报"找不到模块"）—— 必须真正 **unset** 它：用 `env -u ELECTRON_RUN_AS_NODE electron …`
> 或先 `unset ELECTRON_RUN_AS_NODE`（**注意 `export ELECTRON_RUN_AS_NODE=` 空值不算 unset**，v2.8.0 踩过这个）。
> **②** electron 在这个环境里**不会自己退出**，用 `timeout N npx electron …` 包一层，
> **以 `*-report.txt` 的内容为准**（结尾会写"退出码 N"）；外层 `timeout` 报 124 是预期现象。
> 另外离屏窗口**不产生帧**，带 `transition` 的属性会"卡在切换前的旧值"上 ——
> 取样这类属性前要先注入 `* { transition: none !important }` 并强制一次重排。

> 这些脚本**不参与打包**，只是开发期的保险。
