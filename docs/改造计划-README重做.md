> 你的要求：把 GitHub 主页那份 `README.md` 重做，按**正规开源项目的写法**，**图文并茂**，
> 每次更新也要在主页有体现；并且你不确定"更新是不是应该写在 Release 里"。
> 这份是**动手前的施工图**：先对账现状 → 回答 Release 的疑问 → 参考高星项目 → 给新结构 → 验证判据。

## 一、先回答你的疑问：更新日志到底该放哪？

**三个地方分工不同，都要有**（这是高星项目的通行做法）：

| 放哪 | 是什么 | 给谁看 | 你现在 |
|---|---|---|---|
| `CHANGELOG.md` | **完整**的逐版本变更记录 | 想知道"某版本具体改了什么"的人 | ✅ 有，而且写得很细 |
| **GitHub Releases** | 每个版本的**发布页**，可挂安装包，自动列"自上一版以来的提交" | 想**下载**某个版本的人 | ❌ 完全没有 |
| `README.md` | 只放**最近一版的摘要**（3~5 条）+ 跳转链接 | 第一次来的访客 | ❌ 没有 |

**一句话**：
- README 放「**最近**发生了什么」
- CHANGELOG 放「**所有版本**发生了什么」
- Releases 放「**这一版能下载什么**」

**所以：Releases 不是用来"读历史"的**（真去翻会累死，而且 Releases 页面不带导航）。
它的核心价值是 **① 挂安装包 ② 给版本打节点 ③ 让 `.../releases/latest` 这个链接永远指向最新版**。
你想"每次更新在主页有体现"，正确做法是 **README 放摘要 + Releases 发一版 + CHANGELOG 记全**，三件一起。

**实测你仓库的现状**（`gh` 查的）：

```
仓库：xingkinglb/neko-music   公开   1 star
licenseInfo: null          ← 仓库里没有 LICENSE 文件
Releases: []               ← 一个都没有
Tags:     []               ← 一个都没有
```

## 三、参考了哪些高星项目（我真的去读了）

以 **`th-ch/youtube-music`**（同类项目：Electron 音乐播放器，star 数很高）为例，它 README 从上到下的顺序是：

1. `<div align="center">` 居中的**标题 + 一排徽章**（release / license / build / downloads）
2. 一句话定位
3. `> [!IMPORTANT]` **免责声明**（非官方、与 Google/YouTube 无关联、AS IS）
4. **目录（Content）** —— 带锚点链接，可点跳转
5. **Download** —— 分平台给安装方式（winget / scoop / brew / AUR）
6. Dev / Build / Tests —— 开发者区
7. License
8. FAQ

另外参考了 `matiassingers/awesome-readme`（专门收集"漂亮 README"的高星清单），
它总结的要素是：**图片、截图、GIF 演示、清晰的排版**。
其中**"放一个 GIF 演示"**被认为是**最快让人看懂项目在干什么**的手段。

**结论**：新 README 就按上面那个骨架来。

## 五、图片怎么来（**这里有隐私红线，必须处理**）

**绝对不能直接拿你现在的界面截图当主页图** —— 会把你**真实的使用数据**（最近播放里的歌单、歌名、播放记录）一起公开到互联网上。

| 文件 | 内容 |

| `docs/images/hero.png` | 主图：发现页（带动态背景，最上镜） |

## 九、已知取舍 / 待你拍板

1. **不做英文版 README**。理由：应用界面是中文的、目标用户是中文用户；
   高星项目做英文是因为面向全球用户，这里做英文版没有实际价值（还多一份要维护）。
2. **不做"一键下载 exe"直链**。因为 Release 还没发；发完之后才能挂直链。
   （顺序：先补 Release → 再把链接写进 README）
3. **GIF 演示尽力而为**，做不出就用 4 张静态图。
4. **和上一轮的「动态背景」施工图有版本号冲突**：两份计划都写着 → 1.9.0。
   需要你定个先后（见下）。

### 需要你拍板的 3 件事

1. **先做哪个？** ① 先做「动态背景」修复（上一份计划）再重做 README；② 先重做 README；
   ③ 两件一起做（README 里一次写到位）。
   → 我的建议：**① 先修动态背景**。因为 README 要配图，而**动态背景的截图正是主图**，
   修完再截图，图才是对的；否则截图里带着"缩放错位"的 bug，回头还要重截。
2. **补 tag 补到什么程度？** ① 只给最新版打 tag + 发 Release；② v1.0.0~v1.9.0 全部补齐。
   → 我的建议：**② 全部补齐**，历史看起来才完整（成本很低，就是几条 git 命令）。
3. **要不要顺带开 Issues 模板 / Discussions？**（你仓库现在 Issues 已开、Discussions 未开）
   → 我的建议：**先不开**，1 star 的项目还没有人提 issue，属于过度设计。
