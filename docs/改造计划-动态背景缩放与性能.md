# 改造计划：动态背景「随窗口缩放」+「显卡占用」优化 + 改名

> 本轮来自你的 3 条反馈：① 视频背景不随窗口等比缩放，只有全屏才正常；
> ② 选了视频背景后 GPU 占到 60%，优化空间很大；③ 这东西应该叫「动态背景」而不是「视频背景」。
> 这份是**动手前的施工图**，逐条对账到代码行号 + 实测证据 + 方案 + 验证判据，确认后再改代码。

---

## 〇、先说结论：改完以后是什么样

| 你现在看到 | 改完以后 |
|---|---|
| 窗口化时视频被裁成"只看到左上角一块"，人物跑到屏幕外；全屏才正常 | 视频**永远等比铺满窗口**，窗口怎么拉、怎么最大化都正常 |
| 一开视频背景，GPU 直接 60% | **大幅下降**（真机实测数字见第四节；毛玻璃不再对会动的画面每帧重算） |
| 设置里写「视频背景」 | 统一叫 **「动态背景」**（子项才是"图片 / 视频"） |
| 背景模糊滑杆对视频也生效 | 背景是视频时**自动禁用并说明原因**（每帧重算模糊太费显卡），图片照旧 |

## 一、逐条对账：每个现象对应哪一行代码（含实测证据）

### 1）视频不随窗口缩放 —— 已定位到根因，并**实测复现**

**现状**：`src/ui/style.css:147-153`

```css
.bg-layer #bgVideo {
  position: absolute;
  inset: 0;            /* ← 就是这里不管用 */
  object-fit: cover;
  z-index: -1;
  display: none;
}
```

**根因**：`<video>` 是**替换元素**（replaced element）。按 CSS 规范，对**绝对定位的替换元素**，
当 `width/height` 是 `auto` 时，取值是**元素的内在尺寸**（= 视频真实分辨率），
`inset: 0` 里的 `right` / `bottom` 会被**直接忽略**。
所以 `inset:0` 那套"撑满父容器"的写法**只对普通元素有效，对 `<video>` 无效**。

**实测证据**（`.verify/_diag_scale.js`，真跑 Electron，三种窗口尺寸各量一次）：

| 窗口内尺寸 | `.bg-layer` 盒子 | `#bgVideo` 盒子 | 结论 |
|---|---|---|---|
| 1181 × 761 | 1229 × 809 | **300 × 150** | 不随窗口变 |
| 802 × 602 | 850 × 650 | **300 × 150** | 不随窗口变 |
| 1500 × 900 | 1548 × 948 | **300 × 150** | 不随窗口变 |

（`300×150` 是浏览器给"还没有内在尺寸的 `<video>`"的默认值。换成真实素材，`videoWidth/videoHeight` 是多少，元素盒子就是多少 —— 你那段是 1920×1080，所以元素盒子就是 **1920×1080**，锚在左上角 `(-24,-24)`。）

**这就完整解释了你看到的现象**：窗口 1180×760 时，一个 1920×1080 的盒子只有**左上角 1180×760 那一块**露在窗口里 ——
看起来就是"被放大了、人物跑到右下角外面"（正是你第一张截图）；
窗口拉到 ≥1920×1080（全屏）时，盒子正好差不多盖住窗口 —— 看起来就"正常"了（你第二张截图）。

> 顺带说明：**图片背景一直是好的**，因为它走的是 `background-size: cover`（CSS 背景图，不是替换元素），不吃这个坑。所以这个 bug 只在视频上出现。

**修**：给 `#bgVideo` 补上 `width: 100%; height: 100%;`。
有了确定尺寸，`object-fit: cover` 才真正生效（等比铺满 + 裁掉多出来的边）。

### 2）GPU 60% —— 四个原因，其中一个是主因

**根因 A（主因）：4 个常驻"毛玻璃"面板压在会动的画面上**

`backdrop-filter: blur(18px)` 出现在这 4 个**一直显示**的面板上：

| 行号 | 选择器 | 面积 |
|---|---|---|
| `style.css:192` | `.titlebar`（顶部标题栏） | 整宽 |
| `style.css:232` | `.sidebar`（左侧栏） | 整高 |
| `style.css:329` | `.topbar`（搜索栏那一行） | 整宽 |
| `style.css:532` | `.player`（底部播放条） | 整宽 |

`backdrop-filter` 的含义是"**把我背后那块画面实时糊一遍**"。
背后是**静态图片**时，糊一次就缓存住了，几乎不花钱；
背后是**视频**时，**每一帧都要重新采样 + 重新模糊**这 4 块大面积区域。
60fps 下 = 每秒约 **240 次大区域高斯模糊**。这就是 GPU 被打满的主因。

**根因 B：模糊挂在"视频的父层"上**

`style.css:121` `.bg-layer { filter: blur(var(--bg-blur)); }`，而 `#bgVideo` 是 `.bg-layer` 的**子元素**。
等于"先解码一帧 → 整层（含视频）糊一遍 → 再合成"。只要背景模糊滑杆 > 0，**每帧都做一次**。
（`app.js:237` 在 blur=0 时会把它设成 `none`，所以默认不花钱；但一旦你调过模糊，视频也在挨糊。）

**根因 C：缩放 bug 的副作用**

视频按 1920×1080 渲染进一个 1229×809 的层 —— **多算了近 1 倍的像素**，
毛玻璃要采样的面积也更大。修了 P1 之后这项自动消失。

**根因 D：没有"该停就停"的规则**

现在只在 `visibilitychange`（= **最小化**）时暂停（`app.js` 的 `bindSettings()` 里那段监听）。
**窗口失焦**（切到浏览器/文档，窗口还露着）不会停；**被别的窗口盖住**也不会停；
**打开设置面板**（一块大遮罩盖在视频上）也不会停。

### 3）命名

`index.html:473` 附近的分区标题写的是「背景（图片 / 视频）」，`app.js` 的 `bgHint` 写「自定义视频背景 ✓」，
README / CHANGELOG 里也全是「视频背景」。

**改**：用户可见处统一改成 **「动态背景」**（这是行业通用叫法，"视频背景"只是它的一个子类）。
**内部字段名 `settings.bg.kind` 不动** —— 改了就要写存档迁移，不值当，用户也看不见。

## 二、市面做法调研（你让我查的）

**① 开源动态壁纸 Lively Wallpaper**（GitHub `lively-community/lively`，官方 Performance 文档）：

- 视频壁纸**走 GPU 的专用视频解码硬件**（任务管理器里会显示 `Video Decode` 引擎）；
  它的文档明确说"同一段视频，资源开销应该是稳定的" —— 前提是**确实走了硬解**。
- **"不管什么类型的壁纸，只要全屏应用/游戏在跑，Lively 会完全暂停壁纸播放"**。
- 还有几档暂停策略：**其它应用获得焦点就暂停** / **电池供电就暂停** / **屏幕被窗口盖住 95% 就暂停**（网格覆盖检测）。
- 它文档里还有一句值得记的：任务管理器里的 GPU% 是**相对当前频率**的，
  显卡处于低频待机时百分比会显得虚高，不代表真的耗电。

**② 主流"动态背景"其实分三类**（这是行业现状）：

| 类型 | 代表 | 开销 |
|---|---|---|
| 静态图 + 缓慢缩放/视差（Ken Burns） | Windows 聚焦、macOS 动态壁纸 | 极低 |
| **低分辨率循环视频** | Lively、Wallpaper Engine | 中（靠硬解） |
| WebGL / Canvas 着色器动画 | Wallpaper Engine 的 Scene 壁纸 | 高（但可降帧） |

**③ 关于你说的"视频转 GIF"—— 我建议不要，反而更贵**：

- GIF 只有 **256 色**、没有半透明 → 你这个星空 + 人物渐变会出色带，画质明显掉
- GIF **没有硬件解码**，靠 CPU 逐帧解 → 你现在的 **GPU 60% 会变成 CPU 飙升**，而且没法降
- 同画质下 **文件体积是 mp4 的 5~20 倍**（几十上百 MB）
- 参考里 Lively 这类工具**全都用视频而不是 GIF**，就是因为这个

**④ 真正省显卡的方向**（按性价比排序）：

1. **别让毛玻璃每帧重算**（本项目的根因 A，最大收益）
2. **窗口不在前台就停**（Lively 的默认行为）
3. **源视频压到 720p / 24~30fps** —— 同一段素材，体积和解码开销都降一大截
4. 降帧（WebGL 类壁纸才有意义，`<video>` 没有可靠的降帧接口）

## 三、改造方案

### P1 修缩放（1 行 CSS，但这是主 bug）

`style.css:147-153` 的 `#bgVideo` 补 `width: 100%; height: 100%;`。

### P2 把"模糊"从视频身上摘掉（治根因 B）

- `.bg-layer` **不再挂 `filter`**。
- 新增一个只管图片的子元素 `<div class="bg-image" id="bgImage">`：
  `background-image: var(--bg-image); background-size: cover; filter: blur(var(--bg-blur));`
- `#bgVideo` 变成它的**兄弟节点**，不参与模糊。
- `app.js:237` 那行 `layer.style.filter = ...` 挪到 `#bgImage` 上。
- **设置面板**：「背景模糊」滑杆在**背景是视频时置灰 + 提示**「视频背景不支持模糊（每帧重算太费显卡）」。
- **图片背景行为完全不变**（还是 `background-size:cover` + 同样的模糊）。

### P3 动态背景时自动降毛玻璃（治根因 A，最大收益）

- 给 `<body>` 加一个类 `perf-lite`。
- CSS 里在 `body.perf-lite` 下，把上述 4 个面板的 `backdrop-filter` 设成 **`none`**，
  同时把它们的 `background` 透明度**调实一点**（`--glass-alpha` +0.12 左右），
  视觉上仍然是"磨砂面板"，只是不再实时透视背后的视频。
- **只在 `settings.bg.kind === 'video'` 时加这个类**；图片背景不加（图片不动，毛玻璃不花钱）。
- **给用户开关**：设置面板新增 **「动态背景时降低毛玻璃（省显卡）」默认开**。
  关掉 = 恢复现在的样子（用户自己权衡观感 vs 显卡）。

> 为什么是 `none` 而不是 `blur(0px)`：`blur(0px)` 仍然会触发一次"把背后画面拷进纹理"的动作，
> 真正省下的是 `none`。这一点会在离屏实测里验证（量 computed `backdrop-filter`）。

### P4 补齐"该停就停"的规则（治根因 D）

现在只有"最小化"会停。补上：

- **窗口失焦**（`window` 的 `blur` / `focus` 事件）→ 暂停 / 恢复
- **打开任何遮罩**（设置面板 / 歌单选择 / 合集面板 / 队列抽屉，即 `.modal-mask.show` 之类）→ 暂停
- 保留现有的 `visibilitychange`
- 新增设置项 **「窗口不在前台时暂停动态背景」默认开**

### P5 提示源视频规格（不做自动转码）

- 选视频时读 `videoWidth/videoHeight`：**宽度 > 1920** 时提示一句
  「这段视频是 2560×1440，动态背景建议用 720p/1080p，更省显卡」。
- **不做**自动转码（要带 ffmpeg，会让安装包大几十 MB，不值当）；
  **不做**帧率探测（`requestVideoFrameCallback` 估算在文件刚加载时容易误判，收益低）。
- README 里加一段"想要更省？把源视频压到 720p / 30fps"的说明。

### P6 改名「动态背景」

- `index.html` 设置面板分区标题、`app.js` 的 `bgHint` 文案、`README.md`、`CHANGELOG.md`。
- 存档字段 `settings.bg.*` **一律不动**（零迁移不变）。

## 六、已知取舍（说在前面，免得改完你觉得怪）

1. **动态背景 + 降毛玻璃 = 面板会显得"实"一点**（不再实时透视背后在动的画面）。
   这是拿观感换显卡，所以做成了开关，默认开、可以关。
2. **不做 GIF 转码**：更费 CPU、更糊、文件更大（见第二节 ③）。
3. **不做源视频自动转码**：要带 ffmpeg，安装包会大几十 MB；改为提示你自己压到 720p/30fps。
4. **沙箱测不了真实 GPU%**：只能给相对帧时间，真实数字要你本机任务管理器对照。
5. **改名只改用户可见文案**：存档字段不动，老存档零迁移不变。
