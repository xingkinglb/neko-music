## 一、一句话说清这个改动

歌词现在**原样照搬 B 站字幕的分段**，字幕怎么切我们就怎么显示。有些字幕把一句完整的话切成了两半，
这一版在**只改 `src/bilibili.js` 一处**的前提下，把「明显是被切碎的相邻两段」自动并回去。

**核心原则：宁可不并，也不并错。** 只有当我们**有把握**认定是切碎时才动手，否则原样不动。

## 二、为什么要这样做（真实数据，不是拍脑袋）

### 2.1 现状

`src/bilibili.js:818-824`：从字幕 JSON 的 `body[]` 只取了 **`from`（开始秒）+ `content`（文本）**，
做「去空行 + 按时间排序」就完事。**`to`（结束秒）和 `music` 字段一直没被使用**（白扔了两个有用信息）。

### 2.2 关键发现：字幕的 `to` 有两种风格，决定「间隙」有没有判别力

| 曲目 | 行数 | `music` 均值 | 真停顿边界占比 | 风格 |
|---|---|---|---|---|
| 《花海》 | 49 | 1.00 | **88%** | **A**：`to` 精确，句间有 0.5~1.8s 真停顿 |
| 《霓虹甜心》 | 50 | 1.00 | 55% | 中间态 |
| 《嘉宾》 | 59 | 1.00 | 34% | B |
| 《朋友的酒》 | 25 | 0.97 | 21% | B |
| 《荷塘月色》 | 56 | 0.93 | 20% | B |
| 《不醉不会》 | 63 | 1.00 | 13% | B |
| 《第二杯半价》 | 40 | 1.00 | 13% | B |
| 《处处吻》 | 74 | 1.00 | **1%** | **B**：`to` 铺满，整条时间轴无缝 |
| 漫展大征兵（vlog） | 209 | **0.01** | 3% | 不是歌 |

- **风格 A**：`gap = 下一句.from − 这一句.to` 能区分「真停顿」和「切碎点」。花海实测切碎点 gap 全为 0，
  真停顿 gap 1.1~1.8s。
- **风格 B**：`to` 被直接填成下一句的 `from`，gap 几乎全是 0 —— 此时 gap **没有判别力**，
  照它合并会把整首歌糊成一团（处处吻 74→42 行就是这么来的）。

### 2.3 三个必须挡住的反例（所以不能"简单合并所有相邻段"）

1. **vlog 口播**（漫展大征兵）：201/208 边界无缝，合并会把说话糊成一团 → 靠 `music` 挡。
2. **霓虹甜心**：`你慢慢靠近耳边说了句baby` + `我闻到你的香味` 是两句真歌词，按 gap=0 合并就粘错了
   → 靠「真停顿占比 55% < 60%」挡。
3. **花海副歌**：`手中的风筝 放太快回不来` + `不要你离开` 是两句，但 gap=0 → 靠「合并后 16 字 > 15 字上限」挡。

### 2.4 顺带确认：**不能按标点断句**

这些人工歌词字幕每行被 `♪ ... ♪` 包裹，**句末字符 100% 是 `♪`**，一句内部也没有标点。
所以「找标点重新断句」这条路直接走不通 —— 这也是为什么只能用时间轴 + 字数组合判据。

## 三、★ 核心设计：三道闸门

只有**三道闸门全开**才动手，任何一道不过就**原样返回**。

```
闸门 1  是歌吗？          music 均值 ≥ 0.5          → 挡掉口播 / vlog / 对白
闸门 2  时间轴可信吗？     真停顿边界(gap>0.4s) ≥ 60%  → 挡掉 to 铺满的风格 B
闸门 3  这个点该并吗？     gap ≤ 0.05s 且 并完 ≤15 字  → 挡掉"作者因显示限制才拆的"
```

### 3.1 阈值表（都提成了常量，方便调）

| 常量 | 值 | 含义 |
|---|---|---|
| `LYRIC_MUSIC_MIN` | 0.5 | `music` 均值达到多少算"在唱歌" |
| `LYRIC_GAP_REAL` | 0.4 s | 大于它才算"真停顿"（唱歌换气至少 0.4s） |
| `LYRIC_GAP_TRUST` | 0.6 | 真停顿边界占比达到多少才认为这条时间轴可信 |
| `LYRIC_GAP_MERGE` | 0.05 s | 两段间隔不超过它就认为"无缝"；比较时额外加 `1e-6`，防浮点误差把刚好 0.05s 误判成大于阈值 |
| `LYRIC_MERGE_MAX` | 15 字 | 合并后纯文本上限（≈ B 站字幕单行显示上限） |

### 3.2 闸门 3 为什么是 15 字

B 站字幕一行最多显示约 15~20 字。如果两段并起来**超过**这个数，说明作者**本来就是因为一行放不下才拆的**，
那是显示限制，不是句式切碎 —— 不能动。只有并起来仍然放得下，才说明"作者没必要拆却拆了" = 切碎。

### 3.3 文本拼接要处理 `♪` 包裹

```
"♪ 距离 ♪"  +  "♪ 隔不开 ♪"
   ↓ 去掉前一个的尾 ♪ 和后一个的头 ♪，中间留一个空格
"♪ 距离 隔不开 ♪"
```
字数按**去掉 `♪` 和空白**后计算（`♪ 距离 隔不开 ♪` → `距离隔不开` = 5 字）。

## 四、技术实现（逐条对账）

### 4.1 `src/bilibili.js`（**唯一改动文件**）

**4.1.1** 在文件靠前的常量区新增 5 个阈值常量（见 3.1 表）。

**4.1.2** 新增两个纯函数（放在 `getSubtitle` 之前）：

```js
function plainLyricLen(s)            // 去掉 ♪ 和空白后的字数
function joinLyricText(a, b)         // 拼两段，去掉接缝处的 ♪
function mergeShatteredLines(segs)   // 三闸门主算法，入参/出参都是 [{t, tEnd, music, text}]
```

`mergeShatteredLines` 内部顺序：
1. 不足 2 段直接返回；
2. 算 `music` 均值，不过闸门 1 就原样返回；
3. 算所有 `gap = max(0, 下一.t − 这一.tEnd)`，统计 `> LYRIC_GAP_REAL` 的占比，不过闸门 2 就原样返回；
4. 逐段扫描：能并就并进前一段（`prev.text = join(...)`，`prev.tEnd = max(prev.tEnd, seg.tEnd)`），
   不能并就 `push` 新段。

**4.1.3** 改 `src/bilibili.js:818-824` 的 lines 生成处：

现在（改前）：
```js
let lines = body
  .map((it) => ({ t: Number(it.from) || 0, text: String(it.content || '').trim() }))
  .filter((l) => l.text)
  .sort((a, b) => a.t - b.t);
```

改后：先把 `to` / `music` 一起留下来交给算法，算完再丢掉多余字段（对外格式不变，仍是 `{t, text}`）：
```js
const rawSegs = body
  .map((it) => ({
    t: Number(it.from) || 0,
    tEnd: it.to == null || it.to === '' ? NaN : Number(it.to),
    music: Number(it.music) || 0,
    text: String(it.content || '').trim(),
  }))
  .filter((l) => l.text)
  .sort((a, b) => a.t - b.t);
let lines = rawSegs.map(({ t, text }) => ({ t, text }));

// 完成诱饵/乱码/空字幕检查后，再对原始片段应用保守合并
lines = mergeShatteredLines(rawSegs).map(({ t, text }) => ({ t, text }));
```

**★ 对外契约不变**：`lines` 仍然是 `[{t, text}]`。整页歌词（`src/ui/app.js:4329`）和桌面歌词
（`pushLyricToDesktop`）都吃这一份，**一处改、两处受益，界面代码零改动**。

### 4.2 不改的东西（明确列出，防止手痒）

- 不改 IPC、不改 preload、不改 main
- 不改界面、不加设置项、不加开关（理由见第七节）
- 不改 `to` 之外的数据结构（`lines` 仍然只有 `{t, text}`）
- 不动 `subtitleCache`（缓存的是合并后的结果，语义一致）

### 4.3 边界与异常（都要安全）

| 情况 | 行为 |
|---|---|
| `body` 只有 1 段 | 直接返回，不做任何处理 |
| 任一段缺 `to` / `to` 非数字 | `tEnd` 设为 `NaN`，算法 fail-closed，全曲原样返回 |
| `music` 缺失或低置信度 | 缺失按 0 纳入均值；均值低于阈值时全曲原样返回 |
| `tEnd` 小于 `t`（脏数据） | 认为时间轴无效，直接 fail-closed，全曲原样返回 |
| 合并后 `t` 取谁 | 取**前一段的 `t`**（句子开始时间），`tEnd` 取更大的那个 |
| 全曲没有任何真停顿 | 闸门 2 不过，原样返回 |

## 九、★ 方案 2 归档（第三方 LRC 歌词源，后续再做）

> Neo 2026-10-14：「方案 2 先计划归档记录，后续再说」。以下内容是为了将来接手时不必重新调研。

### 9.1 为什么要它

方案 1 只能修**风格 A** 的字幕（`to` 精确）。实测 9 首里只有花海是风格 A，**其余 8 首都是风格 B**
（时间轴铺满，gap 无判别力）—— 这些歌的句式问题**方案 1 修不了**。LRC 是按乐句切的，句式天然准，
是**唯一能根治风格 B** 的路。

### 9.2 怎么做（预研结论）

1. **提取歌名**：从视频标题里取 `《...》` 的内容。实测样本 5/9 能干净提取
   （《花海》《霓虹甜心》《嘉宾》+ 标题即歌名的《处处吻》《荷塘月色》）；
   **《朋友的酒》那种 DJ 脏标题（"🥳每天来上一段…🍺DJ⚡️"）基本没戏**。
2. **匹配**：调第三方搜索接口拿候选，按「歌名 + 歌手 + 时长接近」打分取最佳。
3. **取 LRC**：解析成 `[{t, text}]`，**直接替换**现有 lines（复用同一份对外契约）。
4. **时间轴对齐**：翻唱版常有前奏口播，LRC 与视频可能整体偏移 → **需要新增「歌词偏移」设置**
   （项目目前没有这个设置）。

### 9.3 代价（必须让用户知情才可做）

- 外部非官方接口，**随时可能失效或被限流**
- 翻唱 / DJ / remix / 纯音乐 / 口播类**匹配不上**，只能退回方案 1 的结果
- 需要联网，首次加载变慢
- **合规灰区**（第三方音乐平台歌词）

### 9.4 建议的落地形态

做成**可选开关**（默认关）：设置里给「联网查找更准歌词」；开启后，只有当本地字幕
**没通过闸门 2**（即方案 1 无能为力）时才去联网找，失败就静默退回本地结果，**绝不弹错误打断听歌**。

### 9.5 依赖

- 需要新增设置项 → 动 `src/ui/app.js` 的 `DEFAULT_SETTINGS` 与迁移逻辑（新字段要逐项夹范围，
  见 `app.js:270` 附近对 `lyricWin` 的处理方式）
- 需要新增 IPC：`bili:lyricSearch` 一类
- 需要新增 `src/bilibili.js` 里的第三方请求函数，且要**走 `toHttps()`**（CSP 要求）
